## 1. 交付方式

- **一个开关管住全部新行为**：`NODE_ROLE`（`master` 默认 / `relay`）+ 后台"主从分流"总开关（默认关）。开关关闭时，主节点的行为与现在的单机版逐字节一致（设计不变量 4）。
- **全部工作在 `feat/master-relay-nodes` 分支上进行**，每个工作包完成后在分支上提交。合并到 main 不在本计划内，由负责人另行要求。每个工作包提交前的门槛：
  1. 现有全部测试通过（单机回归是每个工作包的硬门槛）；
  2. 本工作包的单元测试、集成测试通过；
  3. 开关关闭时没有新的数据库写入、没有新的后台任务、没有新的对外端口；Key 页面和导出仍用全局 `api_base_url`，不给 Key 分配节点。
- 数据库迁移从 `259_` 开始编号（现有最后一个是 `258_remote_pairings.sql`；开工和每次同步 main 后再看一眼，被别的改动占了就顺延），全部向前兼容：只加表、加列（带默认值）、加索引，不改不删现有列。
- 全部完成后做一次总验收（第 9 节），通过后打开开关上线，按设计 10.7 迁移。

## 2. 定下来的实现方式

### 2.1 从节点单独装配

- `cmd/server/wire.go` 增加第二个装配入口 `initializeRelayApplication`，使用新的 `RelayProviderSet`。它**不包含** `repository.ProviderSet` 里连接 Postgres、Redis 的部分，也不包含迁移、定时任务、支付、后台接口。
- 转发用的服务结构体（`OpenAIGatewayService`、`GatewayService`、`AntigravityGatewayService` 等）照常复用，只把它们依赖的仓储、缓存接口换成从节点实现（2.2）。
- **装配守卫测试**：构造从节点对象图，断言其中没有 `*ent.Client`、`*sql.DB`、`*redis.Client`，也没有这三者的任何持有者。这条测试进 CI，把"从节点不连库"变成编译、测试层面的保证。
- 从节点实现里"只该在主节点调用"的方法（比如 `ListSchedulable*`），测试环境下直接 panic，生产环境返回错误并报警，漏迁的调用路径会立刻暴露。

### 2.3 主从协议

- gRPC + protobuf，代码放 `internal/relay/proto`，消息带协议版本号（设计 7.4）。
- **连接按优先级分开**，避免 HTTP/2 队头阻塞和流控互相拖累：
  - 控制连接（2~4 条，轮流用）：选号、上游错误决策、额度申请、Key 查询、查询接口转交；
  - 事件连接（1 条）：释放、账号事件、心跳、收回确认、主节点下发的指令；
  - 批量连接（1 条）：扣费批次；
  - 日志连接（1 条，最低优先级）：主节点转来的日志和记录查询（设计 12.3，后续加）。
- **每个会改状态的调用都带幂等键**（选号、额度申请、收回确认、扣费批次、账号事件、释放）。从节点超时重发、断线重连后重发，主节点按幂等键返回第一次的结果（主节点在内存保留最近 10 分钟的幂等结果；每台节点另有字节上限，默认 64MB，超出淘汰最旧的。被淘汰的键再重发会重新执行，重复占用的并发槽和额度由心跳核对兜底）。同一个键在第一次还没执行完时重发，会等第一次的结果，不会执行两次；只保存成功的结果，失败后重发重新执行。
  幂等键**绑定纪元**：主节点重启后内存里的幂等结果没了，从节点发现纪元变化就不再重发旧键，重新发起（选号重新选、额度重新申请）。扣费批次不依赖这层，靠凭证去重表（持久化）保证不重复。额度退回（ReleaseQuota、收回确认）也不依赖这层：从节点报的是这份租约至今累计退回多少，主节点把累计记在租约上（`relay_quota_leases.returned_total`，迁移 261），只处理多出来的部分；主节点重启、回复丢失后重发都只生效一次。
- 每个调用都有截止时间、消息大小上限；主节点过载时返回"稍后重试 + 建议等待时间"，不排长队。
- **主节点纪元**：主节点每次启动生成一个纪元 ID，握手时下发。从节点发现纪元变了，就清空 Key 缓存、凭据缓存、票据吊销表，重新拉配置，并上报自己手里的租约，由主节点核对（设计 4.2 以主节点为准）。

### 2.4 金额

主从之间和从节点本地一律用整数微单位（int64，1 = 10⁻⁸），不用浮点。主节点入账时再转成现有扣费函数用的类型。报价、额度、临时费用、上报用量都用这个单位。

### 2.5 代码位置

```
internal/relay/
  proto/        协议定义与生成代码
  transport/    mTLS、连接池（按优先级）、重连、纪元、幂等
  identity/     节点长期密钥、加密密钥（X25519，随证书续签更换）、注册、证书续签、恢复（从节点侧）
  master/       主节点侧：节点管理、选号服务、额度服务、入账、配置推送（含设置白名单、按节点加密下发的密钥）、Key 查询、违规事件与命中名单下发、联网搜索配额汇总、分配、域名解析检查、日志查询转发
  node/         从节点侧：装配、接口白名单、本地额度、Key 缓存、凭据缓存、配置快照、事件发送
  wal/          本地扣费队列
  sign/         票据、扣费凭证的签名与验证，私钥加载与轮换
  acme/         从节点自己申请和续期 HTTPS 证书（TLS-ALPN-01）
  nodestore/    从节点本机的日志和记录存储（分段文件、保留期清理、索引）与查询接口
```

转发服务本身只做两类改动（中间件、路由、前端、小白端的改动见各工作包）：转发处理函数的"选号 → 转发 → 换号 → 上报"循环改为走一个 `Dispatcher` 接口（主节点实现就是现有逻辑，从节点实现走协议）；4.3 列出的"可花余额"判断统一换成一个函数。

## 3. 性能设计

先测基线，再定目标。所有目标写成"相对单机基线的增量"，不拍绝对数字。

### 3.0 基线（WP0）

用假上游（可配置首字延迟、流式速率、错误注入）+ testcontainers 起的 PG/Redis，测现有单机版：首字延迟 p50/p99、整体耗时、每秒请求数、并发流数、CPU、内存、每请求分配字节数。之后每个工作包用同一套压测对比。

### 3.1 从节点

| 方面 | 做法 |
|---|---|
| 鉴权 | Key 哈希缓存（现有依赖 ristretto），容量有上限；命中只做一次 SHA-256 + 查表。未命中按 Key 合并请求（singleflight），同一个新 Key 并发 100 个请求只问主节点一次。查不到的缓存 30 秒 |
| 票据 | Ed25519 验签，结果按票据缓存到过期；吊销表是内存集合 |
| 本地额度 | 每个（用户, 维度）一个结构，剩余额度用原子整数，预扣用 CAS，不加锁。补充按（用户, 维度）合并，30 个并发请求同时发现不够只发一次申请。低于 30% 时后台补充，随下一次选号顺带 |
| 选号 | 控制连接上的单次调用，截止时间 1.5 秒；带幂等键，超时可以安全重发 |
| 凭据 | 选号只返回（账号, 凭据版本）；本地已有这个版本就不重新下发。第一次用到时多一次往返 |
| 配置 | 快照整体替换（原子指针），读配置不加锁 |
| 释放、账号事件 | 攒 20 毫秒或 256 条发一次，不等回复 |
| 转发 | 复用现有流式代码，从节点这层不做整包缓冲；缓冲区用对象池。请求体只读一次 |
| 内存 | 按容器内存设 `GOMEMLIMIT`；所有进行中请求体的总字节数有上限（默认内存上限的 25%），超出返回 503，不让进程被 OOM 杀掉 |
| 慢客户端 | 读请求头超时 10 秒；向客户端写数据被阻塞（客户端不读）超过 60 秒就断开，并按已产生的用量计费。上游长时间没有输出（比如模型在思考）不算，不受这条影响；每个 IP 的连接数有上限 |
| 本地扣费队列 | 分段追加文件（每段 64MB），每条记录 = 长度 + CRC32C + protobuf；单独一个写入协程，每 20 毫秒或 256 条一起落盘（组提交）；主节点确认到哪个序号就删到哪一段 |
| 日志和记录 | 全部写本机（分段文件、总大小上限、按请求 ID 和时间建索引），不回传；主节点只收心跳里的分钟计数（设计 12.2、12.3） |
| 关闭 | 收到停止信号：不接新请求 → 按设计 10.4 等进行中请求 → 把队列发完（有超时）→ 退出 |

### 3.2 主节点

| 方面 | 做法 |
|---|---|
| 选号服务 | 直接调用现有调度器，额外开销只有签凭证（Ed25519，微秒级）和编解码。每台节点的选号并发有上限，超出返回"稍后重试" |
| 额度申请 | 同一用户的申请在进程内串行（按用户分片的锁），再开一个短事务：锁用户行、写租约、改 `relay_reserved_balance`。避免多个请求在数据库里排队抢同一行锁。"每次一半、每台上限 5"本身就把申请频率压低了 |
| 入账 | 每批里的记录并行处理（复用现有扣费 worker 池，有并发上限），每条一个事务；凭证去重表和现有 `usage_billing_dedup (request_id, api_key_id)` 同事务写入。整批都处理完才回确认，坏记录单独隔离 |
| 凭证去重表 | `relay_voucher_consumed`，按月分区，保留 90 天，过期整分区删除。签发超过 60 天的凭证不再入账（按丢失处理，设计 5.4），保证去重记录永远比可入账的凭证活得久 |
| 签发过的凭证 | 不逐条落库（每请求一条太重）。按节点、按分钟在 Redis 计"签发数 / 入账数"，用于"选号后未上报"检测；进行中的选号 ID 由心跳上报核对 |
| 配置推送 | 后台修改后等 200 毫秒合并，生成一份快照（压缩），推给所有节点；作废通知每 50 毫秒合并一次 |
| 重连风暴 | 主节点重启后，握手按速率放行；从节点重连用指数退避 + 随机抖动（0.5~30 秒） |
| 按节点限流 | 每台节点、每类调用单独限流（设计 7.4）；日志、指标最先被限 |
| Key 查询 | 主节点内存缓存 + 合并请求，改动时作废 |
| 心跳 | 最新状态放内存，每分钟汇总一次批量写库 |
| 主节点转发上限 | 并发数用信号量，带宽用令牌桶限制响应写出；只作用于转发路由，登录、后台、主从通信不受影响 |

### 3.3 压测与目标

| 指标 | 目标 |
|---|---|
| 经从节点转发的首字延迟 p99 | ≤ 单机基线 + 10 毫秒（同地域） |
| 选号调用 p99 | ≤ 单机版本地选号耗时 + 5 毫秒 |
| 从节点每请求额外分配内存 | 与单机转发路径持平（±10%） |
| 主节点入账吞吐 | ≥ 单机版扣费 worker 吞吐 |
| 额度申请 | 单用户 30 并发、10 台节点同时申请，总锁定不超过可用额度，p99 ≤ 20 毫秒（单机版没有这一步，这是唯一的绝对目标） |
| 从节点极限 | 找出单台在目标机型上的最大并发流数和带宽，写进部署文档，作为管理页"带宽上限"的参考 |
| 长稳 | 从节点满载连续 24 小时：内存不涨、协程数不涨、文件句柄不涨 |

## 4. 边界与异常

每一行都要有对应的自动化测试（单元、集成或故障注入），测试名写进工作包的验收清单。网络故障用 testcontainers 的 toxiproxy 注入。

| 场景 | 预期 | 验证 |
|---|---|---|
| 请求进行中主从断线 | 进行中的流继续到结束（凭据、凭证已在手），扣费记录进队列，重连后补发 | 注入断线，比对入账 |
| 断线期间来新请求 | 等重连最多 2 秒，仍不通就返回 503（OpenAI / Anthropic 格式） | 注入断线 |

### WP10-3 Codex WebSocket（Responses WS）的设计

单机的做法（`OpenAIGatewayHandler.ResponsesWebSocket`）：一条连接绑定一个上游账号；每一轮开始时不排队地抢用户槽和账号槽、按当时的利润门复核账号、冻结这一轮的计价时间，轮结束放槽；连接内换号时放账号槽、需要时补用户槽再选号。主从下照这个结构，**每一轮是主节点上的一次选号（一张凭证）**：

- **处理函数不分叉**：选号 + 抢槽 + 利润终检、抢放用户槽和账号槽、每轮准入（复核 + 定价 + 凭证）、每轮渠道映射经接缝；单机实现是原来的代码，从节点实现是远程调用。其余（读帧、模型白名单、续链判断、转发、换号分类）两边同一份。
- **升级之前**：每 Key 连接数租约（Redis 全局租约在主节点申请：带 Key 原文、上限用主节点的配置、主节点按节点记租约归属，别的节点不能续期或释放；续期失败的容忍与单机一样是一个租约周期）。要交给主节点的连接原样反向代理（已有测试）。
- **连接选号**（`SELECT_ENDPOINT_OPENAI_RESPONSES_WS`）：主节点按单机顺序：cyber 会话屏蔽 → 用户槽（不排队）→ 计费资格 → 计价上下文 → 选号（WS 传输、能力、续链可迁移、生图意图）+ 不排队抢账号槽 + 利润终检（否决后排除重选，次数上限同单机）→ 粘性绑定。回复带账号、渠道映射（第 1 轮）、`StickyPreviousHit`（从节点据此剥掉首帧的 `previous_response_id`）、换号上限；不带凭证。拒绝按 WebSocket 关闭码和原因写（cyber 屏蔽按单机写错误帧再关闭）。换号时从节点先放这次选号的账号槽，再以同一请求 ID 选号；用户槽没占着时主节点先补占。
- **每一轮**：`BeforeTurn` 同步调一次主节点：第 2 轮起先补占用户槽和这个账号的槽（不排队），再按当时的利润门复核账号、冻结计价时间、按这一轮的模型签凭证并给额度；否决和占不到槽按单机的关闭码关闭连接。`AfterTurn` 放这一轮的槽（带 response id，主节点记归属），用量带这一轮的凭证进扣费队列，cyber 按这一轮的选号上报。同账号重试（429）按单机补占账号槽。
- **每轮的渠道映射**：钩子顺序随接入模式不同（直通模式 BeforeRequest → BeforeTurn → MapRequestModel，其他模式 MapRequestModel 可能在 BeforeTurn 之前），所以映射不随每轮准入返回：第 1 轮用连接选号回复里的，之后按模型缓存，模型变了才同步问主节点；凭证里的映射由主节点按这一轮的模型自己算。
- **连接记录**：主节点上连接就是一次请求的记录；两轮之间不占槽，只占内存，空闲上限单独放长（不按 15 分钟的占槽上限清理）。记录没了或主节点换了纪元，下一轮按"请重连"（TryAgainLater）关闭。
- **Codex 审查子代理跟随父会话**：选号请求带父会话哈希（已加，HTTP 同样用）。
- **轮的归属**：轮结束走事件连接（异步），下一轮的 `BeginTurn` 是同步调用，可能先到。所以每一轮有 ID（`BeginTurn` 回、结束消息带回），主节点只放这一轮还开着时占的槽；`BeginTurn` 发现上一轮还开着就先放它的槽再占（同本地 `BeforeTurn`）；连接的用户槽记在"选号/轮"名下，换号后的选号接手，旧选号迟到的结束消息不动它。
- **与单机的差异**：会话抢占（同一会话的新连接顶掉旧连接）只在从节点进程内生效，客户端一条连主节点、一条连从节点时互不抢占。每一轮额度不够也不拒绝（与单机一致：只在建连时查计费资格）。
- **还没覆盖的**：真机只走过 API Key 账号的 `ctx_pool` 接入；OAuth 账号（凭据快照、会话抢占）、直通和 HTTP 桥接模式没在从节点上跑过。`/backend-api/codex/responses`（Codex 直连路径）仍交给主节点。
- **测试**：主节点单测（顺序、否决、槽、记录丢失）；进程内端到端用 coder/websocket 假上游，覆盖默认的 `ctx_pool` 接入模式（`mode_router_v2_enabled` 默认关）；本机真机另用 HTTP 桥接模式的账号补充。

按纵向切片做，第 1 片 = OpenAI Responses + API Key，已完成（WP7-1 ~ WP7-9）：

- **共用而不是照抄**：主节点选号调用的是本地同一段代码——`middleware.EvaluateRelayAPIKeyAdmission`（本地 /v1 中间件链的复查，拒绝时用中间件自己的写法生成响应，一致性测试逐字节对比真实中间件链）、`handler.OpenAIAccountAdmitter.SelectAndAdmit`（选号、续链跳过 OAuth 账号、池模式会话哈希、准入、利润否决重选）、`handler.OpenAIGatewayRejection` 系列（选号阶段的错误）、`ConcurrencyHelper.AcquireUserSlotWithWaitNoGin`。本地 Responses 已改成调这些函数。
- **实现放在 `internal/relay/relayselect`**（master 不能导入 handler），经 `relaywire` 以 `RuntimeDeps.NewSelector` 挂上。
- **协议**：`Select`（幂等键 = 请求 ID/第几次）、`FetchCredentials`（节点缓存里没有这个凭据版本时取，只给进行中选号选中的账号）、`RefillQuota`（按进行中的选号提前补额度）、事件连接上的 `SelectionRelease`（带 response id 和凭证）。拒绝是正常回复，四种格式：网关错误（从节点按入口协议写，流式已开始写流内错误）、原样响应（中间件的）、换号用完（从节点按自己最近的上游错误写）、暂不支持（交给主节点转发）。
- **按请求记、按选号记**：用户并发槽、固定的计价上下文、否决次数、已排除账号按请求记；账号槽按选号记。释放消息放账号槽、写响应归属；请求结束放用户槽。没有成功选出账号就结束请求。
- **额度**：每项只要求"有一点"（1 微单位）——本地计费检查只要求剩余大于 0，主节点多要就会拒掉单机能用的请求；并发超支由设计 4.5 的上限兜住。额度在回复的最后一步给；给出后回复没送到就原样收回。余额预检加回这台节点自己锁着的部分（不超过主节点记着的数）。
- **占用上限**：选号和请求占用超过 15 分钟（与 Redis 并发槽过期一致）由定时清理放掉；之后到的释放按凭证记响应归属。从节点一次选号调用最长等 5 分钟（排队在主节点，单机没有总时限）。
- **暂时留在主节点的**：非 OpenAI 分组（自动分组选到的、组合平台选中的目标不是 OpenAI 的也一样）。（自动分组 Key、组合平台分组、会被安全审计处理的请求原来也在这里，现在照常走从节点。）

| 主干在开发期间继续加功能（这两天就加了 TypeSafe、游客试用、手机同步） | 每个工作包合入前重跑 2.2 脚本和转发路由清单比对（新增的 API Key / 票据路由必须在设计 8.3 里有归属，否则测试失败） |
| WP10 工作量超预期 | 先做 Codex（小白端）和 OpenAI Responses 这条主路径，打通 `Dispatcher` 后其余平台是同一模式的重复 |
| 选号往返拖慢首字延迟 | 3.3 的目标进 CI 压测；凭据版本缓存、连接分级 |
| 主节点成为单点 | 设计已接受（设计 10.6）；靠独立外部监控尽快发现（WP18） |

## 9. 总验收

全部通过才上线：

1. **单机回归**：开关关闭，现有全部测试通过；与改造前版本对比压测无退化。
2. **主从一致性**：同一批覆盖所有平台和路径（含 TypeSafe、自动分组换组、兜底池、组合平台、贡献房间、内容审核命中）的请求，分别在单机和主从（3 台从节点）模式下跑，所有受影响的表逐字段一致（设计 5.2）。
3. **性能**：3.3 节全部目标达标；24 小时长稳通过。
4. **边界**：第 4 节每一行的测试全部通过。
5. **安全**：抓包确认主从之间、客户端到从节点之间没有明文；从节点磁盘和内存里找不到数据库凭据、私钥、Key 原文；未激活节点、伪造票据和凭证、复制证书全部被拒；用从节点域名访问主节点后台被拒；从节点配置快照里没有任何密钥（包括 JSON 设置值里的）；贡献账号连不到内网地址；主从之间日志流量占转发流量不到 1%。
6. **故障演练**：关掉一台从节点（再手动把解析改到主节点）；封掉一台的对外端口但保留心跳；制造一台从节点的错误风暴；关掉所有从节点（比例 >0 和 =0 各一次）；重启主节点；停掉主节点 Redis；模拟节点虚报用量。每次演练的结果和通知都符合设计。
7. **运维**：按 WP18 手册从零部署、激活、升级、换机器各走一遍。
8. **小白端**：实机完成分配、切节点、回退主节点、服务不可用四种情况。
