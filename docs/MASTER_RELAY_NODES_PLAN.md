# 主从节点分流开发计划（一次交付，2026-09-23）

> 依据：`docs/MASTER_RELAY_NODES.md` v0.14（下称"设计稿"，引用写作"设计 x.y"）。本文只写怎么做、按什么顺序做、怎么验收；设计细节不重复，以设计稿为准。

## 1. 交付方式

- **一个开关管住全部新行为**：`NODE_ROLE`（`master` 默认 / `relay`）+ 后台"主从分流"总开关（默认关）。开关关闭时，主节点的行为与现在的单机版逐字节一致（设计不变量 4）。
- **每个工作包完成即合入 main**，不开长期分支。合入门槛：
  1. 现有全部测试通过（单机回归是每个工作包的硬门槛）；
  2. 本工作包的单元测试、集成测试通过；
  3. 开关关闭时没有新的数据库写入、没有新的后台任务、没有新的对外端口；Key 页面和导出仍用全局 `api_base_url`，不给 Key 分配节点。
- 数据库迁移从 `257_` 开始编号（现有最后一个是 `256_remove_legacy_openai_oauth_passthrough.sql`），全部向前兼容：只加表、加列（带默认值）、加索引，不改不删现有列。
- 全部完成后做一次总验收（第 9 节），通过后打开开关上线，按设计 10.7 迁移。

## 2. 定下来的实现方式

### 2.1 从节点单独装配

- `cmd/server/wire.go` 增加第二个装配入口 `initializeRelayApplication`，使用新的 `RelayProviderSet`。它**不包含** `repository.ProviderSet` 里连接 Postgres、Redis 的部分，也不包含迁移、定时任务、支付、后台接口。
- 转发用的服务结构体（`OpenAIGatewayService`、`GatewayService`、`AntigravityGatewayService` 等）照常复用，只把它们依赖的仓储、缓存接口换成从节点实现（2.2）。
- **装配守卫测试**：构造从节点对象图，断言其中没有 `*ent.Client`、`*sql.DB`、`*redis.Client`，也没有这三者的任何持有者。这条测试进 CI，把"从节点不连库"变成编译、测试层面的保证。
- 从节点实现里"只该在主节点调用"的方法（比如 `ListSchedulable*`），测试环境下直接 panic，生产环境返回错误并报警，漏迁的调用路径会立刻暴露。

### 2.3 主从协议

- gRPC + protobuf，代码放 `internal/relay/proto`，消息带协议版本号（设计 7.4）。
- **连接按优先级分开**，避免 HTTP/2 队头阻塞和流控互相拖累：
  - 控制连接（2~4 条，轮流用）：选号、上游错误决策、联网搜索、额度申请、Key 查询、查询接口转交；
  - 事件连接（1 条）：释放、账号事件、心跳、收回确认、主节点下发的指令；
  - 批量连接（1 条）：扣费批次；
  - 日志连接（1 条，最低优先级）：日志摘要、日志计数、指标（只有主要字段，设计 12.2）。
- **每个会改状态的调用都带幂等键**（选号、额度申请、收回确认、扣费批次、账号事件、释放）。从节点超时重发、断线重连后重发，主节点按幂等键返回第一次的结果（主节点在内存保留最近 10 分钟的幂等结果）。
  幂等键**绑定纪元**：主节点重启后内存里的幂等结果没了，从节点发现纪元变化就不再重发旧键，重新发起（选号重新选、额度重新申请）。扣费批次不依赖这层，靠凭证去重表（持久化）保证不重复。
- 每个调用都有截止时间、消息大小上限；主节点过载时返回"稍后重试 + 建议等待时间"，不排长队。
- **主节点纪元**：主节点每次启动生成一个纪元 ID，握手时下发。从节点发现纪元变了，就清空 Key 缓存、凭据缓存、票据吊销表，重新拉配置，并上报自己手里的租约，由主节点核对（设计 4.2 以主节点为准）。

### 2.4 金额

主从之间和从节点本地一律用整数微单位（int64，1 = 10⁻⁸），不用浮点。主节点入账时再转成现有扣费函数用的类型。报价、额度、临时费用、上报用量都用这个单位。

### 2.5 代码位置

```
internal/relay/
  proto/        协议定义与生成代码
  transport/    mTLS、连接池（按优先级）、重连、纪元、幂等
  identity/     节点长期密钥、加密密钥（X25519，随证书续签更换）、注册、证书续签、恢复（从节点侧）
  master/       主节点侧：节点管理、选号服务、额度服务、入账、配置推送（含设置白名单）、Key 查询、联网搜索代理、分配、域名解析检查、日志摘要接收
  node/         从节点侧：装配、接口白名单、本地额度、Key 缓存、凭据缓存、配置快照、事件发送
  wal/          本地扣费队列
  sign/         票据、扣费凭证的签名与验证，私钥加载与轮换
  acme/         从节点自己申请和续期 HTTPS 证书（TLS-ALPN-01）
  logship/      从节点日志摘要生成、截断、限流、本机错误详情索引与按需取回
```

转发服务本身只做两类改动（中间件、路由、前端、小白端的改动见各工作包）：转发处理函数的"选号 → 转发 → 换号 → 上报"循环改为走一个 `Dispatcher` 接口（主节点实现就是现有逻辑，从节点实现走协议）；4.3 列出的"可花余额"判断统一换成一个函数。

## 3. 性能设计

先测基线，再定目标。所有目标写成"相对单机基线的增量"，不拍绝对数字。

### 3.0 基线（WP0）

用假上游（可配置首字延迟、流式速率、错误注入）+ testcontainers 起的 PG/Redis，测现有单机版：首字延迟 p50/p99、整体耗时、每秒请求数、并发流数、CPU、内存、每请求分配字节数。之后每个工作包用同一套压测对比。

### 3.1 从节点

| 方面 | 做法 |
|---|---|
| 鉴权 | Key 哈希缓存（现有依赖 ristretto），容量有上限；命中只做一次 SHA-256 + 查表。未命中按 Key 合并请求（singleflight），同一个新 Key 并发 100 个请求只问主节点一次。查不到的缓存 30 秒 |
| 票据 | Ed25519 验签，结果按票据缓存到过期；吊销表是内存集合 |
| 本地额度 | 每个（用户, 维度）一个结构，剩余额度用原子整数，预扣用 CAS，不加锁。补充按（用户, 维度）合并，30 个并发请求同时发现不够只发一次申请。低于 30% 时后台补充，随下一次选号顺带 |
| 选号 | 控制连接上的单次调用，截止时间 1.5 秒；带幂等键，超时可以安全重发 |
| 凭据 | 选号只返回（账号, 凭据版本）；本地已有这个版本就不重新下发。第一次用到时多一次往返 |
| 配置 | 快照整体替换（原子指针），读配置不加锁 |
| 释放、账号事件 | 攒 20 毫秒或 256 条发一次，不等回复 |
| 转发 | 复用现有流式代码，从节点这层不做整包缓冲；缓冲区用对象池。请求体只读一次 |
| 内存 | 按容器内存设 `GOMEMLIMIT`；所有进行中请求体的总字节数有上限（默认内存上限的 25%），超出返回 503，不让进程被 OOM 杀掉 |
| 慢客户端 | 读请求头超时 10 秒；向客户端写数据被阻塞（客户端不读）超过 60 秒就断开，并按已产生的用量计费。上游长时间没有输出（比如模型在思考）不算，不受这条影响；每个 IP 的连接数有上限 |
| 本地扣费队列 | 分段追加文件（每段 64MB），每条记录 = 长度 + CRC32C + protobuf；单独一个写入协程，每 20 毫秒或 256 条一起落盘（组提交）；主节点确认到哪个序号就删到哪一段 |
| 日志 | 只回传摘要：请求错误日志和警告及以上的程序日志，每条截断到 1KB 以内，每台每秒最多 50 条，超出只计数；错误响应体、上游错误详情等大字段只写本机文件，按请求 ID 建索引供按需取回（设计 12.2、12.3） |
| 关闭 | 收到停止信号：不接新请求 → 按设计 10.4 等进行中请求 → 把队列发完（有超时）→ 退出 |

### 3.2 主节点

| 方面 | 做法 |
|---|---|
| 选号服务 | 直接调用现有调度器，额外开销只有签凭证（Ed25519，微秒级）和编解码。每台节点的选号并发有上限，超出返回"稍后重试" |
| 额度申请 | 同一用户的申请在进程内串行（按用户分片的锁），再开一个短事务：锁用户行、写租约、改 `relay_reserved_balance`。避免多个请求在数据库里排队抢同一行锁。"每次一半、每台上限 5"本身就把申请频率压低了 |
| 入账 | 每批里的记录并行处理（复用现有扣费 worker 池，有并发上限），每条一个事务；凭证去重表和现有 `usage_billing_dedup (request_id, api_key_id)` 同事务写入。整批都处理完才回确认，坏记录单独隔离 |
| 凭证去重表 | `relay_voucher_consumed`，按月分区，保留 90 天，过期整分区删除。签发超过 60 天的凭证不再入账（按丢失处理，设计 5.4），保证去重记录永远比可入账的凭证活得久 |
| 签发过的凭证 | 不逐条落库（每请求一条太重）。按节点、按分钟在 Redis 计"签发数 / 入账数"，用于"选号后未上报"检测；进行中的选号 ID 由心跳上报核对 |
| 配置推送 | 后台修改后等 200 毫秒合并，生成一份快照（压缩），推给所有节点；作废通知每 50 毫秒合并一次 |
| 重连风暴 | 主节点重启后，握手按速率放行；从节点重连用指数退避 + 随机抖动（0.5~30 秒） |
| 按节点限流 | 每台节点、每类调用单独限流（设计 7.4）；日志、指标最先被限 |
| Key 查询 | 主节点内存缓存 + 合并请求，改动时作废 |
| 心跳 | 最新状态放内存，每分钟汇总一次批量写库 |
| 主节点转发上限 | 并发数用信号量，带宽用令牌桶限制响应写出；只作用于转发路由，登录、后台、主从通信不受影响 |

### 3.3 压测与目标

| 指标 | 目标 |
|---|---|
| 经从节点转发的首字延迟 p99 | ≤ 单机基线 + 10 毫秒（同地域） |
| 选号调用 p99 | ≤ 单机版本地选号耗时 + 5 毫秒 |
| 从节点每请求额外分配内存 | 与单机转发路径持平（±10%） |
| 主节点入账吞吐 | ≥ 单机版扣费 worker 吞吐 |
| 额度申请 | 单用户 30 并发、10 台节点同时申请，总锁定不超过可用额度，p99 ≤ 20 毫秒（单机版没有这一步，这是唯一的绝对目标） |
| 从节点极限 | 找出单台在目标机型上的最大并发流数和带宽，写进部署文档，作为管理页"带宽上限"的参考 |
| 长稳 | 从节点满载连续 24 小时：内存不涨、协程数不涨、文件句柄不涨 |

## 4. 边界与异常

每一行都要有对应的自动化测试（单元、集成或故障注入），测试名写进工作包的验收清单。网络故障用 testcontainers 的 toxiproxy 注入。

| 场景 | 预期 | 验证 |
|---|---|---|
| 请求进行中主从断线 | 进行中的流继续到结束（凭据、凭证已在手），扣费记录进队列，重连后补发 | 注入断线，比对入账 |
| 断线期间来新请求 | 等重连最多 2 秒，仍不通就返回 503（OpenAI / Anthropic 格式） | 注入断线 |
| 主节点重启 | 纪元变化 → 从节点清缓存、重拉配置、上报租约，主节点核对；重启前签发的凭证照常入账 | 重启主节点 |
| 从节点重启 | 队列回放继续发；内存里的额度没了，重连时上报"没有这些租约"，主节点立即释放 | 杀进程重启 |
| 租约快到期 | 从节点在"到期时间 − 30 秒 − 测得的时钟偏差"时就停止使用这份额度，保证主节点收回时它已不再用（设计不变量 3） | 冻结续期，检查放行时间点 |
| 时钟偏差 | 心跳测偏差；超过 30 秒拒绝服务并告警 | 注入偏差 |
| 配置版本落后且拉取失败 | 这个请求返回 503，不用旧配置转发 | 注入拉取失败 |
| 选号超时后重发 | 幂等键返回同一个结果，不重复占并发槽 | 注入延迟 |
| 选号发出后主节点重启 | 纪元变化，从节点不重发旧键，重新选号；重启前占的并发槽由心跳核对释放，兜底 15 分钟过期 | 选号中途重启主节点 |
| 主节点不可达时上游出错（进行中请求） | 上游错误决策调用不了：不重试、不换号，按配置快照里的错误透传规则把错误返回客户端；原始事实作为账号事件排队，重连后主节点照常判定、标记账号 | 断线后注入上游错误 |
| 主节点不可达时需要 Grok 视频计费认领 | 认领调用不了：这次查询返回 503，不在本地认领，避免重复计费 | 断线后查询视频 |
| 选号成功但本地预扣失败 | 立即发释放，并发槽归还 | 单元测试 |
| 释放消息丢失 | 心跳里的进行中选号 ID 对不上时，主节点释放；兜底是现有 15 分钟过期 | 丢弃释放消息 |
| 客户端中途断开 | 按现有规则处理上游，已产生的用量照计 | 集成测试 |
| 上游部分输出后失败 | 上游错误决策返回换号；前一次尝试单独结算（设计 3.1 第 10 步） | 假上游注入 |
| 上游 401 | 决策调用让主节点刷新凭据；从节点清掉这个凭据版本，重新选号 | 假上游注入 |
| 30 个并发请求同时把额度用完 | CAS 预扣保证不超；只发一次补充；补充不到的请求按余额不足拒绝 | 并发测试 |
| 收回时有请求在进行 | 只退未使用部分，进行中请求的预扣保留，结束后退 | 单元测试 |
| 多台节点同时为同一用户申请 | 主节点串行，总和不超过可用额度 | 并发测试 |
| 扣费批次重复、乱序、缺号 | 按序号和凭证去重；缺号时要求从节点重发 | 注入重放、乱序 |
| 单条坏记录 | 隔离并报警，同批其他记录照常入账 | 构造坏记录 |
| 磁盘满 | 启动时预留一个 256MB 占位文件；写不进时删掉占位文件，让进行中请求的记录能写完，同时停止接新请求并报警 | 填满磁盘 |

| Key 删除或停用 | 推送作废，下一个请求就被拒 | 集成测试 |
| 刚新建的 Key | 推送哈希清掉"查不到"缓存，立即可用 | 集成测试 |
| 随机 Key 攻击 | 格式检查、负缓存、按 IP 限失败次数；主节点 Key 查询量不随攻击线性增长 | 压测 |

## 9. 总验收

全部通过才上线：

1. **单机回归**：开关关闭，现有全部测试通过；与改造前版本对比压测无退化。
2. **主从一致性**：同一批覆盖所有平台和路径的请求，分别在单机和主从（3 台从节点）模式下跑，所有受影响的表逐字段一致（设计 5.2）。
3. **性能**：3.3 节全部目标达标；24 小时长稳通过。
4. **边界**：第 4 节每一行的测试全部通过。
5. **安全**：抓包确认主从之间、客户端到从节点之间没有明文；从节点磁盘和内存里找不到数据库凭据、私钥、Key 原文；未激活节点、伪造票据和凭证、复制证书全部被拒；用从节点域名访问主节点后台被拒；从节点配置快照里没有任何密钥；主从之间日志流量占转发流量不到 1%。
6. **故障演练**：关掉一台从节点（再手动把解析改到主节点）；封掉一台的对外端口但保留心跳；制造一台从节点的错误风暴；关掉所有从节点（比例 >0 和 =0 各一次）；重启主节点；停掉主节点 Redis；模拟节点虚报用量。每次演练的结果和通知都符合设计。
7. **运维**：按 WP18 手册从零部署、激活、升级、换机器各走一遍。
8. **小白端**：实机完成分配、切节点、回退主节点、服务不可用四种情况。
