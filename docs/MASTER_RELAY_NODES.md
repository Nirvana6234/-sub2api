# 主从节点架构设计（v0.14，2026-09-23）

> 状态：设计阶段，未写代码。本文只记录当前结论；历史版本不再保留在正文里。开发计划见 `docs/MASTER_RELAY_NODES_PLAN.md`。

## 1. 目标与已定决策

**目标**：单台服务器的公网带宽不够，把中转的大流量分到多台从节点上。
主节点负责登录、鉴权、选号、计费、节点管理和分配；从节点只负责转发，不连数据库。

| 项 | 决定 |
|---|---|
| 瓶颈 | 服务器公网带宽 |
| 从节点数据访问 | 不连 Postgres，不连 Redis，只连主节点 |
| 选号 | 每个请求向主节点要一个上游账号（第 3 节） |
| 额度 | 从节点每次向主节点申请用户未锁定额度的一半，每台为同一用户最多持有 5，最小锁定单位 0.05；不够再申请，申请不到就拒绝（第 4 节） |
| 扣费 | 从节点本地记账，异步批量回报；主节点逐条走现有扣费函数入账（第 5 节） |
| 从节点丢失的用量 | 不扣用户的钱，服务端承担 |
| 迟到的扣费记录 | 签发 60 天内照常扣，余额可能变成负数；超过 60 天按丢失处理（5.4） |
| 用户看到的余额 | 冻结是服务端内部的事，用户不感知；扣费回报后客户端刷新可见，略慢可接受 |
| 倍率、价格、配置修改 | 实时生效（第 6 节） |
| 主从通信 | 从节点主动建立的长连接，TLS 1.3 双向认证，不允许任何明文（第 7 节） |
| 从节点接入 | 从节点直接注册，管理员在从节点管理页核对指纹后激活才能用（第 11 节） |
| 从节点鉴权 | 从节点按凭据类型开放不同接口：中转票据只能用小白端转发接口，API Key 只能用网关接口（8.3） |
| 按账号分配节点 | 只有小白端：登录后由主节点分配一台从节点，同一用户所有请求走这台（10.1） |
| 从节点域名 | 管理员在域名服务商处自己配解析，在从节点管理页给每台填写对外域名；暂不接域名服务商接口，系统不改解析（10.3） |
| API Key 用户 | 直接访问从节点，从节点向主节点认证。每个 Key 生成时由后台分配一台从节点，导出和推荐配置时取这台的域名（10.2） |
| API Key 节点规则 | 从节点通用配置项，只有管理员能改：API Key 仅能在分配的从节点使用，或可在全部从节点使用（10.2） |
| 主从分配比例 | 从节点管理页通用配置：主节点承担多少比例的新分配（0~100%），其余按带宽分给从节点。**为 0 时主节点不做任何中转**（10.8） |
| 分配查询接口 | 客户端向主节点查询自己分到的中转地址，返回从节点或主节点（10.9） |
| 从节点故障 | 告警并列出受影响的 Key；管理员可以手动把这台的域名解析改到主节点（主节点分配比例须大于 0），用户不用改地址（10.3） |
| 主节点域名 | 保持现有域名不变，用于网页、后台、登录、小白端控制。API Key 请求打到主节点时：分配比例大于 0 照常处理，计入主节点转发上限；为 0 时拒绝，并提示这个 Key 分配的地址（10.5） |
| 现有 API Key 用户 | 上线时为现有 Key 批量分配从节点，用户需要改成新地址；迁移期间主节点分配比例保持大于 0，旧地址继续可用（10.7） |
| 从节点全部不可用 | 主节点分配比例大于 0 时，小白端转到主节点，从节点域名可由管理员手动改到主节点，主节点转发设上限；为 0 时服务中断（10.5） |
| 静态 API Key 类型的上游账号 | 后台开关，可设为"仅主节点使用"（第 9 节） |
| 异步图片任务 | 谁接到谁处理（第 14 节） |
| 下发给从节点的配置 | 按白名单下发，只含转发需要的项；系统设置里的各种密钥（管理员 API Key、SMTP 密码、OAuth / 验证码密钥、联网搜索服务密钥等）一律不下发（6 第二类） |
| 联网搜索模拟 | 在主节点执行，从节点把搜索请求转给主节点，搜索服务密钥不离开主节点（3.3） |
| 从节点日志 | 只回传几个主要字段的摘要，完整内容留在从节点本机、按需单条获取；后台日志列表新增"来源"列（第 12 节） |
| 通知 | 从节点离线等事件发飞书或后台已设定的渠道（第 13 节） |
| 本次范围 | 所有转发路径和 API Key 用户都做（一次交付，不分期） |
| 本次部署 | 从节点与主节点同一地域 |

## 2. 总体结构

```
                           ┌──────────────── 主节点（控制流）────────────────┐
 小白端 ─登录/刷新/仪表盘/分配─▶│ 鉴权 · 额度锁定 · 选号 · 计价 · 记账 · 节点管理 │── Postgres / Redis
 网页、后台 ──────────────────▶│ 网页 playground/聊天、批量图片等只在这里         │   （只有主节点能访问）
   │                       └──────────────▲─────────────────────────────────┘
   │ 小白端：中转票据                       │ 加密长连接：认证 / 额度 / 选号 / 扣费 / 配置 / 日志 / 指令
   │ API Key 用户：分配的从节点域名          │
   │ 请求体、流式响应（MB 级）              │
   ▼                                      │
 从节点 1..N ─────────────────────────────┘
   │  本地：验票据 / 查 Key 缓存 · 查额度 · 本地记账 · 异步回报
   │  用上游凭据直连上游（经账号绑定的代理）
   ▼
 上游（OpenAI / Anthropic / ...）
```

**不变量**：
1. 请求体和响应体不经过主节点。例外只有这些，都计入主节点转发上限（10.5）：
   - 按主从分配比例分到主节点的小白端用户和 Key（10.8）；
   - 从节点全部不可用时小白端回退到主节点（10.5）；
   - 管理员把故障从节点的域名手动改到主节点期间，这台的 API Key 流量（10.3）；
   - 分组里只有"仅主节点使用"账号的用户（第 9 节）；
   - API Key 请求直接打到主节点域名（旧地址、手动改用）（10.2、10.7）；
   - 网页上的 playground 和聊天（登录态，不走从节点）；
   - 只在主节点提供的接口，如批量图片（8.4）。

   主节点分配比例为 0 时，前五种都不会发生（10.8），只剩网页功能和只在主节点提供的接口。
2. 从节点没有数据库、Redis、对象存储凭据，也没有能签发用户票据、扣费凭证的私钥，也没有 JWT 密钥，也拿不到系统设置里的任何密钥（6 第二类）。
3. 任何时刻，所有从节点为同一用户锁住的额度加起来都不超过用户的可用额度。
4. 主节点保留完整的单机能力，现有单机部署不受影响。
5. 一套代码、一个程序，`NODE_ROLE=relay` 时换一套内部接线。现有的 `RUN_MODE`（standard/simple）是计费简化模式，与此无关。

## 3. 一次请求

### 3.1 流程

1. **客户端 → 从节点**：小白端带中转票据访问小白端转发接口；API Key 用户带 Key 访问网关接口（8.3）。
2. **本地鉴权**：验票据签名；或查本地 Key 缓存（未命中时问主节点），检查 Key 状态、到期、IP 白名单，以及节点规则是否允许这个 Key 在这台使用（8.2）。全局 IP 黑名单在这一步之前检查。
3. **粗查额度**：这个用户在本机有没有可用额度。没有就申请（第 4 节），申请不到就拒绝。
   小白端第一次申请时，主节点替它解析内部 Key（8.1），结果随额度返回并缓存。
4. **本地预处理**：从请求体提取模型、是否流式、会话哈希、`previous_response_id`、是否生成图片。
5. **选号（→ 主节点）**：发送凭据类型、用户、Key（小白端为内部 Key）、请求的分组（小白端按请求头；自动分组 Key 为候选池）、模型、会话哈希、`previous_response_id`。
   主节点先做只有它能做的检查和决定：自动分组按模型选定分组、组合平台分组选目标平台、分组模型白名单、全局用户黑名单、后台模式下只允许管理员（3.2）。
   然后选号、占并发槽，返回：
   - 账号和分组快照、上游地址、代理（地址和凭据）、TLS 指纹配置、Anthropic OAuth 的身份指纹（`identityService.GetOrCreateFingerprint` 在主节点执行）、模型映射；
   - 上游短期凭据（额外加密，见 7.1）。只返回凭据版本号，从节点内存里已有这个版本时不重复下发，没有时单独取一次；
   - 本次使用的分组和计费模式（余额或订阅）；
   - **扣费凭证**（5.3），里面包含这次请求的报价；不计费的请求（如 `count_tokens`）不签发凭证；
   - 当前配置版本号（6.2）；
   - 需要时顺带补充额度。
6. **精查额度并预扣**：按返回的分组和计费模式，检查用到的每一项子额度都够，并在本地**预扣这次请求的最低预估费用**。
   同一用户的并发请求（默认可同时 30 个）因此不会重复使用同一笔额度。
7. **转发**：本地配置版本落后时先同步拉取；改写请求体，直连上游，流式回传。
8. **本地记账**：从响应解析用量，按凭证里的报价算临时费用，多退少补预扣，写入本地扣费队列。
9. **异步回报**：扣费队列批量发给主节点，主节点正式入账（第 5 节）。
10. **失败重试**：上游返回错误或超时时，从节点**同步**发"上游错误决策"给主节点，带原始事实（状态码、关键响应头、错误分类、耗时、已输出字节数）。
    主节点用现有 `RateLimitService`（`CheckErrorPolicy`、`HandleUpstreamError`、`HandleStreamTimeout`）判定并落库（标限流、临时不可调度、记错误），返回"重试 / 换号 / 透传 / 失败"。
    要换号时重新选号（带已试过的账号）再重试。每次选号各有一张凭证，每次尝试各自结算；前一次已经产生的部分输出照现有规则计费。
    这一步不能做成异步事件：它决定这次请求接下来怎么走，从节点手里只有过期的账号状态，不能自己判定。只在出错时发生，不影响正常请求的延迟。
    主节点不可达时：不重试、不换号，按配置快照里的错误透传规则把错误返回客户端；原始事实作为账号事件排队，重连后主节点照常判定、标记账号。

并发槽的释放不等扣费批次：请求一结束就单独发一条释放消息，不等回复。

**选号为什么每个请求都问主节点**：并发槽、粘性会话、账号限流状态都是全局的。同地域部署时这次往返只有几毫秒。
以后如果要跨地域部署从节点，可以改成"把一批账号划给从节点、本地选号"，那是另一套设计，本次不做。

### 3.2 现有代码里每一步挪到哪里

网关中间件链（`internal/server/routes/gateway.go`，`/v1`、不带前缀的别名、`/v1beta`、`/backend-api/codex`、`/antigravity` 用的是同一串）：

| 现有中间件 | 做什么 | 新位置 |

| `bodyLimit`、`clientRequestID`、`endpointNorm` | 请求体上限、请求 ID、入口归一 | 从节点本地 |

| `blacklistIP`（`GlobalBlacklistIP`） | 全局 IP 黑名单，读不到时拒绝 | 从节点本地，黑名单作为配置下发（6 第二类）；没拿到配置不接请求 |
| `apiKeyAuth` | Key 鉴权、用户状态、Key 到期、IP 白名单、余额/额度预检 | 从节点本地（Key 缓存 + 本地额度）；缓存未命中问主节点 |
| `blacklistAccount`（`GlobalBlacklistAccount`） | 全局用户黑名单 | 主节点，选号时 |
| `autoGroupModelRouting` | 自动分组 Key 按模型现选分组，要查订阅 | 主节点，选号时 |
| `groupModelAllowlist` | 分组模型白名单 | 主节点，选号时 |
| `compositeTarget` | 组合平台分组按模型选目标平台 | 主节点，选号时，结果随选号返回 |
| `requireGroupAnthropic` | 未分配分组拒绝 | 主节点，选号时 |

小白端转发接口（`routes/paw.go`）的 `jwtAuth` 换成中转票据验证（从节点本地）；`BackendModeUserGuard` 在主节点选号时执行；每个请求的内部 Key 解析（`ResolvePawGroupKey`）在主节点（8.1）。

处理函数内部，以 OpenAI Responses 为例（`internal/handler/openai_gateway_handler.go`），其他平台的处理函数结构相同：

| `:515` | `previous_response_id` 归属 | 主节点，选号时 |
| `:610` | 会话哈希 | 从节点，随选号请求上送 |

### 3.3 联网搜索模拟

现有的联网搜索模拟（`service/gateway_websearch_emulation.go`，经 `websearch.Manager` 调外部搜索服务）需要搜索服务的 API Key，这些 Key 存在系统设置里（`service/websearch_config.go`）。

- 主从模式下搜索在主节点执行：从节点在需要搜索时把查询转给主节点（控制连接上的同步调用），主节点调搜索服务，返回结果；从节点继续组装响应。
- 搜索服务密钥不下发给从节点。搜索请求和结果都很小（KB 级），不影响分流效果；只在用到联网搜索的请求上多一次往返。
- 主节点不可达时，这次请求按搜索失败处理（和现有搜索服务出错时的行为一致）。

## 4. 额度

### 4.1 按维度分别锁定

现有的扣费资格检查有两种模式（`service/billing_cache_service.go:735`）：余额模式（`:879`）和订阅模式（`:900`）。订阅用户在订阅分组里用的是订阅窗口额度，余额可能是 0。
决定"能不能再花钱"的维度也各有归属：

| 维度 | 字段 | 归属 |
|---|---|---|
| 余额 | `users.balance` | 用户 |
| 订阅日/周/月窗口 | `user_subscriptions.daily/weekly/monthly_usage_usd` | 用户 × 订阅分组 |
| 分组日/周/月上限 | `groups.daily/weekly/monthly_limit_usd` | 用户 × 分组 |
| 平台日/周/月配额 | `user_platform_quotas.*_limit_usd` | 用户 × 平台 |
| Key 总额度、5 小时/1 天/7 天限额 | `api_keys.quota`、`rate_limit_5h/1d/7d` | 单个 API Key（小白端记在它的内部 Key 上，8.1） |

所以从节点上一个用户的额度是**一组子额度**，每项各自申请、收回，都遵守 4.2 的规则。一个请求放行前，它会用到的每一项子额度都要够。

订阅和 API Key 都有到期时间（`user_subscriptions.expires_at`、`api_keys.expires_at`）。对应子额度的有效期不能超过到期时间。

用户 RPM、并发数（`users.rpm_limit`、`users.concurrency`）不锁给从节点，在主节点选号时执行。

### 4.2 锁定规则

以下数值都按系统内部的余额数值计（费用按美元单价算，充值时按后台充值倍率 `BalanceRechargeMultiplier` 换算进来），不做货币换算，均可在后台调整。

- **每次给一半**：从节点申请时，主节点给出"未锁定额度的一半"。未锁定额度 = 该项的剩余 − 已锁在所有从节点上的部分。
- **最小锁定单位 0.05**：未锁定额度小于 0.1 时，全部给出。
- **每台上限 5**：一台从节点为同一用户持有的、还没用掉的锁定金额，任何时候不超过 5。
  每次给出的金额 = min（未锁定额度的一半，5 − 这台上还没用掉的部分）。
- **提前补充**：本机剩余低于 30% 时，下一次选号顺带补充，不另发消息。
- **申请不到就拒绝**：先收回这个用户在其他从节点上 5 分钟没用的额度，再计算。
  仍然不够、且该项的剩余低于 1 时，直接收回其他从节点上这个用户未使用的部分（不等闲置），再计算。
  只在剩余低于 1 时这样做，是为了避免两台同时活跃的节点反复互相收回。
  仍然不够这次请求的最低预估，就拒绝，返回余额不足（OpenAI / Anthropic 格式）。
- **租约 10 分钟**，节点在线时自动续期；节点失联时，到期后主节点单方面收回。从节点在"到期时间 − 30 秒 − 测得的时钟偏差"时就停止使用这份额度，保证主节点收回时它已经不再用。
- **重启核对**：从节点重启后内存里的额度没了，重连时上报"没有这些租约"，主节点立即释放；主节点重启后（纪元变化，7.4），从节点上报手里的租约，由主节点按库里的记录核对，以主节点为准。

例：用户可用 100，只在一台上用。这台每次最多持有 5，用掉约 3.5 时补回到 5。余额低于 10 后，一半小于 5，就按一半给；最后不足 0.1 时全部给出。

### 4.3 冻结怎么记

- `balance` 始终是用户的真实余额，**只在真正扣费时减少**。
- 新增一列 `relay_reserved_balance`，记录锁在所有从节点上的总额；明细和其他维度的预留记在租约表。
  不和批量图片已有的 `frozen_balance` 共用。
- 锁定：`relay_reserved_balance` 加。扣费：`balance` 减实际费用，`relay_reserved_balance` 同步减。收回：只减 `relay_reserved_balance`。
- 参照批量图片已有的冻结做法（`repository/usage_billing_repo.go:437-524`）：冻结要有记录，释放前核对确实冻结过，结算幂等。

**只有"能不能花钱"的判断改成看 `balance - relay_reserved_balance`**，统一调用同一个"可花余额"函数：

| 位置 | 做什么 |
|---|---|
| `service/billing_cache_service.go:870` | 网关请求前的余额预检（含主节点自己转发时） |
| `server/middleware/api_key_auth.go:434` | API Key 鉴权时余额耗尽拒绝 |
| `repository/usage_billing_repo.go:447` | 批量图片冻结时的余额条件 |
| `service/payment_refund.go:166`、`:279` | 退款时余额是否足够 |

余额显示、低余额提醒、用户接口、管理后台的代码不用改。主节点入账时同步更新余额缓存。

### 4.4 收回

| 事件 | 处理 |
|---|---|
| 某台上这个用户 5 分钟没有请求 | 收回这台上未使用的额度 |
| 节点失联 | 租约到期后主节点单方面收回 |
| 管理员减余额、退款 | 未锁定部分够就直接执行；不够时先从从节点收回 |
| 主节点上要花这个用户的钱（主节点转发、批量图片等） | 先用未锁定部分，不够再收回 |
| 封禁、停用、改密码、强制下线 | 立即全部收回，所有从节点停止放行该用户 |
| 修改用户所属分组、配额，删除或停用 Key | 立即全部收回，下次请求重新申请 |
| 修改倍率、价格 | 不收回：额度与倍率无关，新倍率从下一个请求的报价生效 |
| 用量窗口重置 | 不处理，下次申请按新窗口计算 |

收回是一次同步调用：从节点从未使用的部分里扣出来还给主节点，进行中请求需要的部分保留，结束后再退。

**锁在离线节点上的额度**收不回来，**默认等租约到期**（最长 10 分钟）由主节点自动收回。
- 管理员减余额、退款、删除用户时如果需要这部分：页面提示"有多少锁在离线节点上、最晚什么时候可以收回"，等租约到期后自动继续执行。
- **管理员主动回收**：在从节点管理页（按节点，回收这台所有用户的额度）或用户管理页（按用户，回收这个用户在所有离线节点上的额度）点"立即回收"，二次验证、记审计。被回收的租约当场作废，视为已收回，等待中的管理员操作随即继续。
- 那台节点恢复后：被作废的租约不能再用，它上报的剩余额度按作废处理；如果补报了离线期间已经发生的用量，照常扣（5.4），余额可能变成负数，每个用户每台不超过 5。

### 4.5 超支的上限

- 请求开始前预扣最低预估（按请求体大小估输入）。
- 进行中的请求不中途切断（上游已经在计费，切断也省不了钱），超出预估的部分从 `balance` 扣并记录。
- 所以超支上限是"每个进行中的请求超出它自己预估的部分"。超出后必须补充额度成功，才放行下一个请求。

## 5. 扣费

### 5.1 从节点本地队列

- 本地持久化队列（分段追加文件，每条带校验，批量落盘，细节见开发计划 3.1）。每条记录：扣费凭证、租约 ID、实际模型、全部计费维度的原始用量、临时费用、状态码、耗时、上游关键响应头、响应 ID。
- 不存凭据，不存请求内容。
- 每 1~2 秒或攒够 100 条发一批，主节点确认后才删除，断线、重启后接着发。批次带连续序号，主节点能发现漏掉或重复的批次。
- 一条记录处理失败（比如格式错误）时单独隔离并报警，不堵后面的记录。
- 本地写不进去（磁盘满、损坏），或长时间收不到确认、积压超过上限时，从节点停止接收新请求。

### 5.2 主节点入账：必须走现有扣费函数

现有扣费函数（`service/gateway_usage_billing.go` 的 `postUsageBilling` / `applyUsageBilling`）除了写 `usage_log`、扣余额，还会：

| 行 | 做什么 |
|---|---|
| `:145` | 订阅用户累加订阅用量，不扣余额 |
| `:151` | 余额用户扣余额 |
| `:175` | 累加上游账号的已用额度 |
| `:191` | 累加平台配额，处理窗口重置 |
| `:277`、`:586`、`:593` | 用别人贡献的账号时给贡献者返利；用自己贡献的账号时收自用费 |
| `:375`、`:410` | 更新账号最近使用时间 |
| `:400`、`:407` | 更新订阅用量缓存、API Key 限额用量缓存 |
| `:462`、`:472` | 同步余额缓存 |
| `:503` | 低余额邮件提醒 |
| `:544` | 账号额度提醒 |

主节点处理扣费批次时**逐条调用这套函数**，只把"用量从哪里来"换成从节点上报的记录。不能另写一个简化版，否则返利、账号额度、订阅用量会悄悄不再发生。
验证方式：同一批请求分别在单机和主从模式下跑，比较所有受影响的表，逐字段相同才算通过。

其他要求：
- 验证扣费凭证的签名，**每张凭证只入账一次**。扣费请求 ID 沿用现有规则（`:206` `resolveUsageBillingRequestID`、`:238`、`:251` 的 Grok 音频和实时会话固定 ID、`:262` 请求内容指纹），不用从节点自己生成的 ID。
- **按凭证里的报价计价**，不按批次到达时的价格。主节点重新计算，不信从节点算出的金额；不一致时按主节点的扣，并在确认里告诉从节点修正剩余额度。`usage_log` 的 `rate_multiplier`、`account_rate_multiplier` 也从报价里取。
- 用量窗口按凭证里的请求时间计入，不按入账时间。
- 每条记录在一个事务里完成（凭证去重和扣费同事务）；一批里的记录全部处理完（成功入账或已隔离）才回确认。

### 5.3 扣费凭证

主节点在每次选号时签发一张带签名的凭证：选号 ID、用户、Key、账号、分组、计费模式、请求模型、**允许的计费模型范围**、报价、签发时间。

- 从节点上报的每条记录必须带凭证，验签通过才入账，凭空编造的记录验不过。
- 报价在凭证里，从节点离线很久后补报也能正确计价。
- 现有代码会按上游实际返回的模型计费（`:727` `responseModelBillingAdoptable`）。从节点上报的实际模型必须在凭证允许的范围内，否则按请求模型计费并报警。
- 签发过的凭证不逐条落库（每请求一条太重），主节点按节点、按分钟统计"签发数 / 入账数"；进行中的选号 ID 由心跳上报核对。选号成功但一直没有扣费记录的比例异常就报警（发现少报的手段之一）。

### 5.4 迟到、丢失和吊销

| 情况 | 处理 |
|---|---|
| 迟到的记录（从节点离线后恢复补报） | 签发 60 天内照常扣，余额可能变成负数，用户充值前不能继续使用。迟到记录只可能来自当时锁给这台的额度，所以负数每个用户每台节点不超过 5 左右 |
| 丢失的记录（整机损毁、本地队列没了） | 不扣，服务端承担。心跳里的"各用户累计已用"只用来估算丢失金额，不用来扣费。按节点记审计，同一台反复丢数据要报警 |
| 正常下线 | 必须先排空、队列清空、额度全部退回，才能删除 |
| 强制删除（机器已不在） | 队列里没报上来的按丢失处理 |
| 因怀疑被攻破而吊销 | 吊销前签发的凭证照常入账，但全部标记"待复核"，后台列出，管理员可按用户整笔退回；吊销后签发不出新凭证 |

凭证的"已入账"记录保留 90 天。**签发超过 60 天的凭证不再入账**，按丢失处理（不扣，记节点审计），保证去重记录一定比可入账的凭证保留得久，不会重复扣费。所以"迟到照常扣"的期限是 60 天。

## 6. 倍率、价格、配置的实时同步

**一、影响计价的倍率和价格：每个请求自带报价**

包括：账号倍率（`accounts.rate_multiplier`）、分组倍率和峰时倍率（`groups.rate_multiplier`、`peak_rate_multiplier`）、图片/视频倍率、分组模型价格（`groups.model_pricing`）、按次计费项（网络搜索等）、用户专属分组倍率、贡献房间倍率（`contribution_rooms.consumer_rate_multiplier`）、全局模型价格表。

- 主节点在选号时按当时的配置算出报价，写进扣费凭证。正式入账用同一份报价。
- 后台改了倍率，下一个开始的请求就按新倍率；已经在进行的请求按它开始时的价格。这和现有规则一致（`service/openai_profit_control.go:164` 在请求开始时冻结计价时间 `pricingAt`）。
- 峰谷倍率按主节点的时间算。失败换号时报价随新选号重新计算。
- 从节点不保存价格表和倍率。

**二、转发用的配置：推送 + 版本栅栏**

包括：快速模式策略、首字超时模式、TLS 指纹、错误透传规则、Codex 指令模板、模型映射、全局 IP 黑名单、API Key 节点规则等。

- 后台一改，主节点立即推送给所有在线从节点。
- 选号返回里带当前配置版本号，从节点版本落后时先同步拉取再转发。所以改动提交后，不会有任何新请求按旧配置转发。
- 全局 IP 黑名单在选号之前检查，靠推送生效；从节点失联时不接请求（下面第三类），所以不会用过期的黑名单放行。
- 从节点没拿到配置之前不接请求。只推数据，不推可执行内容。
- **按白名单下发**：从节点用的系统设置是主节点按白名单挑出来的，只含转发需要的项。系统设置表里存着管理员 API Key（`SettingKeyAdminAPIKey`）、SMTP 密码、各家 OAuth 和验证码的密钥、联网搜索服务密钥等，这些一律不下发。白名单之外的设置项在从节点上读到的是空值；新增设置项默认不下发，要下发必须显式加进白名单，并在代码评审时确认不是密钥。

**三、从节点缓存的用户状态：改动即作废**

包括：API Key 的哈希缓存（对应的用户、分组、限额、IP 白名单、分配节点）、票据、额度、小白端内部 Key 的解析结果。

- 用户、Key、分组、订阅、配额、Key 分配节点的任何修改，主节点立即推送作废通知，并按 4.4 收回额度。
- 新建 Key 时，主节点推送这个 Key 的哈希，从节点清掉对应的"查不到"缓存（8.2）。
- 从节点失联期间收不到通知，但也拿不到选号，不会转发请求；重连后先比对配置版本，再恢复服务。

## 7. 主从通信

从节点主动连主节点，保持几条长连接，同一条连接上并发多个请求（gRPC 双向流或 WebSocket 加请求 ID）。

### 7.1 加密

1. **所有主从通信都走 TLS 1.3**，包括注册、待激活期间的心跳、证书续签、证书过期后的恢复。主节点这个端口只提供 TLS，不开明文端口，没有降级成明文的退路。
2. **加密必须在主节点程序本身终止**。不能在前面放负责解密的反向代理、负载均衡或 CDN，内网也不行；需要转发端口时只能用不解密的 TCP 转发。这也是双向认证成立的前提。
3. 只允许强加密套件，关闭旧版本 TLS 和弱算法；证书密钥用 ECDSA P-256 或 Ed25519。
4. **上游凭据再加一层加密**：选号返回里的上游凭据，再用这台从节点的**加密公钥**单独加密（X25519 密钥交换 + AEAD）。签名用的证书密钥（Ed25519 / ECDSA）不能直接用来加密，所以从节点另有一对加密密钥，每次续签证书时一起更换，公钥随续签请求上报。即使中间被人放了会解密的代理，凭据也不会以明文出现。
5. 日志不记录主从消息原文，只记类型、大小、耗时。

其他链路：

| 链路 | 要求 |
|---|---|
| 客户端 → 从节点 | 只接受 HTTPS。从节点不开 HTTP 端口，也不做 HTTP 跳转 HTTPS（跳转前第一个请求已经把 API Key 明文发出去了） |
| 从节点 → 上游 | HTTPS（现有行为） |
| 从节点 ↔ 对象存储 | HTTPS，临时地址只签发 `https` 的 |
| 主节点 → 飞书 | HTTPS |
| 小白端：Codex → 本机 LocalPawRelay | 只监听 127.0.0.1，不出本机 |

### 7.2 认证

- **双向 TLS**：主节点也要向从节点证明身份，否则伪造的主节点能给所有从节点下指令。
- 从节点核对主节点身份用的是**主从通信专用根证书**的指纹，不是主节点网站证书的指纹（网站证书每两三个月续期一次，会让所有从节点连不上）。
- 主节点对所有从节点接口都要求：证书有效、未吊销，且节点处于"已激活"（第 11 节）。
- 没有正式证书的连接（注册）按来源 IP 限流。

**证书被偷的防护**：
1. **短期证书，续签换密钥**：证书 24 小时有效，在线时自动续签；每次续签从节点生成新密钥，用旧证书证明身份；旧证书立即不能再建新连接，已有的连接最多保留 60 秒，由主节点关闭，从节点换到新证书的连接上。偷到的密钥最多用到这台节点下一次续签。
2. **同一身份出现两份 → 立即断开这台节点的所有连接，退回"待激活"**，发严重告警。包括：同一张证书同时从两个不同 IP 连接；同一把旧密钥被续签两次。
3. **节点换 IP**（前后不同时）只告警，不阻断，兼容动态 IP 和换服务器。
4. **证书过期后的恢复**：主节点长时间不可用导致证书过期时，从节点用注册时的长期密钥重新证明身份，节点仍是已激活就直接续签，记审计并通知。长期密钥只用于这种恢复。

从节点连接主节点时固定只用一个出口（比如只走 IPv4），否则多出口会被第 2 条误判。确实需要多出口的节点，后台可以对这台单独关闭"同时两个 IP"的判断；"同一把旧密钥被续签两次"的判断始终保留。

### 7.3 消息

| 方向 | 消息 | 频率 |
|---|---|---|
| 从 → 主 | 注册、证书续签、证书过期后的恢复 | 一次 / 每天 / 很少 |
| 从 → 主 | 拉取配置（启动、重连、版本落后时） | 按需 |
| 从 → 主 | 申请额度（小白端首次申请时顺带解析内部 Key）、续期、退回闲置额度 | 每用户每几分钟；补充可随选号 |
| 从 → 主 | 选号（返回账号、凭据版本、扣费凭证、配置版本号；凭据按需另取） | 每请求；WebSocket、实时会话每一轮 |
| 从 → 主 | 上游错误决策（同步，返回重试 / 换号 / 透传 / 失败） | 只在上游出错时 |
| 从 → 主 | 联网搜索（同步，主节点调搜索服务，3.3） | 只在用到联网搜索时 |
| 从 → 主 | 账号事件（会话窗口、账号附加信息、设置写入等）；Grok 视频计费认领（同步） | 按需 |
| 从 → 主 | 查询 API Key（缓存未命中时；返回用户、分组、限额、IP 白名单、分配节点） | 按需，有负缓存和限流（8.2） |
| 从 → 主 | 查询接口转交（`/v1/usage`、`/v1/models` 等，8.4） | 按需，每台有速率上限 |
| 从 → 主 | 并发槽释放；长请求和实时会话的占用续期 | 每请求，不等回复；心跳里带进行中的选号 ID |
| 从 → 主 | 扣费批次 | 每 1~2 秒 |
| 从 → 主 | 异步图片任务：登记、进度、完成；申请临时上传/下载地址；查询任务状态 | 按需（第 14 节） |
| 从 → 主 | 心跳（内容见 11.4） | 每 5 秒 |
| 从 → 主 | 日志摘要（警告及以上的程序日志、请求错误日志，只含主要字段）和日志计数（单独队列，优先级最低） | 批量，每台有速率上限 |
| 主 → 从 | 获取单条错误详情、获取最近日志（管理员点击时） | 按需，有大小上限 |
| 主 → 从 | 收回额度、吊销票据/Key、新建 Key 的哈希、配置变更通知、公钥轮换、排空、恢复、停用、下线、临时调日志级别 | 按需 |

### 7.4 其他要求

- **主节点按节点限流**：每台的额度申请、选号、上游错误决策、联网搜索、账号事件、扣费批次、Key 查询、查询接口转交、日志都有速率上限，一台出问题不能拖垮主节点。
- **协议版本**：消息格式带版本号，主节点拒绝过旧版本；升级时先升主节点（新旧格式都支持），再逐台升级从节点。
- **时钟同步**：所有节点开时间同步，票据和凭证的有效期检查允许少量偏差。心跳测量从节点与主节点的时钟偏差，超过 30 秒时从节点拒绝服务并告警。
- **主节点纪元**：主节点每次启动生成一个纪元 ID，握手时下发。从节点发现纪元变化时，清空 Key 缓存、凭据缓存、票据吊销表，重新拉配置，上报租约供核对（4.2）。
- **幂等**：所有会改状态的调用（选号、额度申请、收回确认、扣费批次、账号事件、释放）都带幂等键，从节点超时或重连后重发不会重复生效。幂等键绑定纪元，主节点重启后从节点不重发旧键，重新发起。
- **主节点过载**：主节点对某个调用回"稍后重试"时，从节点给客户端返回 503（OpenAI / Anthropic 格式，带 `Retry-After`），不在从节点排队。
- **主节点的关键私钥**：主从通信根证书、签中转票据、签扣费凭证三把私钥。
  - 加密保存，解密密钥放在主节点环境变量或单独文件里，**不进数据库**。现有备份功能会把数据库备份到对象存储，私钥在库里就会跟着进备份。
  - 私钥单独离线备份。主节点重装时丢了根证书私钥，所有从节点都要重新注册、激活。
  - 轮换时新旧公钥并存一段时间，从节点都拿到新公钥后再停用旧的。

## 8. 用户凭据与从节点开放的接口

### 8.1 中转票据（只给小白端）

- 主节点用私钥签名（比如 Ed25519），从节点只有公钥，能验证但造不出票据。
- 内容：用户 ID、分配的从节点 ID、有效期（默认 10 分钟）。随分配结果一起下发，换节点时重新签发，跟随约 60 秒的定期询问续签。
  吊销（封禁、改密码、强制下线）靠推送给从节点的吊销表，表里的条目保留到票据最长有效期后自动删除。
  拿到票据不能去主节点改密码、支付，也不能在别的节点上用。
- 只在请求开始时检查有效期，进行中的长回复不因票据到期中断。
- **内部 Key**：小白端现在带 JWT 访问 `/api/v1/paw/*`，服务端每个请求用 `ResolvePawGroupKey`（`service/paw_chat_service.go:60`）找到用户的内部 Key 和分组，找不到时 `EnsurePlaygroundAPIKeys` 当场创建（写数据库）。
  主从模式下这一步在主节点做：从节点首次为这个用户（和分组）申请额度时，主节点解析，必要时创建，把内部 Key ID 随额度返回；从节点按（用户, 分组）缓存。
  内部 Key 被删除、重建时主节点推送作废。4.1 的 Key 维度额度记在内部 Key 上。
- 内部 Key 不导出，不走 10.2 的节点分配和规则；它只能通过票据在分配给这个用户的从节点上使用。

### 8.2 API Key

- **认证**：从节点第一次见到某个 Key 时，经加密长连接把 Key 原文发给主节点查询（现有 `api_keys.key` 存的是原文，按原文唯一索引查找）。
  主节点返回用户、分组、限额、IP 白名单、到期时间、**分配的从节点**（10.2）；从节点只在内存里缓存"Key 的哈希 → 以上信息"，不存原文、不写盘。
- **节点规则**（从节点通用配置，10.2）：为"仅分配的从节点"时，其他从节点拒绝这个 Key，返回 403（OpenAI / Anthropic 格式），提示"此 Key 只能通过分配给它的地址使用"。为"全部从节点"时，任何已激活的从节点都接受。主节点是否接受取决于主节点分配比例（10.5）。
- Key 被删除、停用或改分配节点时主节点推送作废。
- **防止随机 Key 攻击压垮主节点**：先检查 Key 格式；查不到的 Key 缓存 30 秒；同一来源 IP 鉴权失败过多时暂时拒绝。
  新建 Key 时主节点推送这个 Key 的哈希，从节点清掉对应的"查不到"缓存，避免用户刚建的 Key 马上用却被拒。
- 客户端 IP 由从节点按 TCP 连接确定（从节点前面没有代理，不信任转发头），API Key 的 IP 白名单在从节点本地执行。桌面客户端已豁免会话绑定（`service/client_source.go:87`）。

### 8.3 从节点开放哪些接口

从节点按凭据类型只开放下面这些接口，其余一律 404：

| 凭据 | 开放的接口 |
|---|---|
| 中转票据 | 小白端转发接口：`/api/v1/paw/responses`、`/messages`、`/messages/count_tokens`、`/chat/completions`、`/images/generations`、`/images/edits`、`/files` |
| API Key | 网关接口：`/v1/*`、不带 `/v1` 前缀的别名（`/responses`、`/chat/completions`、`/models` 等）、`/v1beta/*`、`/backend-api/codex/*`、`/antigravity/*`，其中非转发接口按 8.4 处理 |

**只在主节点**：`/api/v1/paw/config`、`/api/v1/paw/auto-group`、`/api/v1/playground/*`，以及所有登录态（JWT）接口、管理后台、支付、内嵌前端、安装向导。
网页上的 playground 和聊天因此一直走主节点，流量计入主节点（不变量 1）。

### 8.4 不是转发的 API Key 接口

| 接口 | 处理 |
|---|---|
| `/v1/usage`、`/v1/sub2api/billing` | 从节点转交主节点执行（查余额、用量），不缓存 |
| `/v1/relay/assignment` | 查询这个 Key 分配的地址（10.9），从节点转交主节点执行 |
| `/v1/models`、`/v1/models/:model`、`/v1beta/models`、Codex 的模型清单 | 转交主节点，结果按分组在从节点缓存 60 秒 |
| `/v1/messages/count_tokens` | 需要上游时正常选号，但不签扣费凭证、不扣额度；本地估算的（Grok）直接在从节点算 |
| `/v1/images/tasks/:task_id` | 第 14 节 |
| `/v1/videos/*` 的状态和内容查询、`/v1/live/:call_id`、`/backend-api/codex/:call_id` | 与第 14 节同样处理：从节点带任务或会话 ID 选号，主节点找回创建时的账号。Grok 视频的计费认领（现有 `SetGrokVideoPendingBilling`、`ClaimGrokVideoBilled`，在 Redis）改成调用主节点执行。实现前核对现有代码是否依赖进程内状态 |
| `/v1/images/batches*` | **只在主节点提供**：依赖 `frozen_balance` 和 Vertex 对象存储。从节点转交主节点执行（请求和结果下载流量都经过主节点，不变量 1） |

## 9. 上游账号

| 账号类型 | 从节点拿到什么 |
|---|---|
| OAuth 账号 | 只给短期 access token；refresh token 不离开主节点，刷新在主节点（`token_refresh_service`） |
| 静态 API Key 账号 | Key 本身，长期有效 |
| 服务账号（如 Vertex） | 主节点生成短期 token 下发，不下发服务账号文件 |

- 上游返回 401 时，从节点回报，主节点刷新，下次选号带新凭据。
- 凭据只在内存，不写盘，不打日志，收到吊销立即清除。
- **"仅主节点使用"开关**：每个上游账号可单独设置，后台可按账号类型批量设置（比如所有静态 API Key 账号）。从节点来选号时跳过这些账号。
  分组里的账号全部是"仅主节点"时，该分组的小白端用户只能分配到主节点，API Key 分配主节点地址（10.2），流量占主节点带宽；后台要能看到有多少用户和 Key 因此落在主节点上。
  主节点分配比例为 0 时，"仅主节点"账号不会被任何请求用到，这些分组的用户无法使用（10.8）。
- 同一个账号可能同时被多台从节点使用。没有绑定代理的账号会从多个 IP 发出请求，可能触发上游风控，建议账号都绑定代理。

## 10. 分配与路由

### 10.1 小白端

- 登录时、定期询问时（约 60 秒一次）、当前节点连不上时，客户端调分配查询接口（10.9），主节点返回分配的地址（从节点或主节点）和中转票据。一般地址不变，只有负载调整、节点下线或管理员手动调整时才换。
- 同一用户多台设备登录，都分到同一台。
- 客户端分**控制地址**（主节点现有域名：登录、刷新、仪表盘、切组、问分配）和**转发地址**（分到从节点时是从节点域名，带中转票据；分到主节点时是主节点域名，沿用现有登录态）。
- 只改本机 LocalPawRelay 的上游地址，不动 Codex 的 `config.toml`（"运行中的 Codex 会不会重读配置"未验证，端口固定可以绕开；也不影响会话与 provider 的绑定）。
- 新地址只对下一个请求生效，正在输出的回复在原节点跑完。换节点不用转移额度：新节点自己申请，旧节点的额度闲置后收回。

**负载指标用带宽**：心跳上报网卡实测收发速率（包括 API Key 用户的流量）；带宽上限由管理员填写；负载 = 近 1 分钟速率 / 上限，上下行取较大值。超过 85% 不再分配新用户。新用户先按主从分配比例决定是否分到主节点（10.8），分到从节点的按剩余容量加权随机分配（不是每次挑最空的，避免心跳延迟期间大家挤到同一台），并把最近几秒刚分到的人数计入预估。

### 10.2 API Key 用户

API Key 用户直接访问从节点，由从节点向主节点认证（8.2）。没有公共轮询域名。

**生成时分配**：
- 每个 Key 生成时，后台为它分配一台节点，Key 上记的是**节点 ID**（主节点也是一个节点），不是域名。先按主从分配比例决定是否分给主节点（10.8）；分给从节点时，只从"已激活"且未排空、未停用、负载未超 85% 的节点里选。
- 生成时还不知道这个 Key 会有多少流量，所以按带宽上限加权随机，并把每台已分配且近 7 天有请求的 Key 数计入。
- Key 能用的分组里全部是"仅主节点"账号时（第 9 节），分配主节点；主节点分配比例为 0 时照样分配主节点，但这个 Key 用不了，Key 页面提示"当前分组暂不可用"。

**导出和推荐**：Key 页面的"使用 Key"、端点提示、CC Switch 等导出配置，给出的地址是按 Key 的分配节点现取的**这台在管理页填写的域名**，不再用全局的 `api_base_url`；分配主节点的 Key 给出主节点现有域名。
管理员修改某台的域名时，分到它的 Key 导出地址随之变化，已配置好的客户端要改地址，所以修改前提示影响的 Key 数；一般不改域名，换机器时由管理员把域名解析改到新机器（11.6）。

**节点规则**：从节点管理页的**通用配置**里的一项，对所有从节点生效，只有管理员能改，用户看不到也改不了：
- **仅分配的从节点**（默认）：只有分配的那台接受，其他从节点拒绝（8.2）。
- **全部从节点**：任何已激活的从节点都接受；导出仍给分配的地址。
- 两种规则下，主节点域名是否接受只看主节点分配比例（10.5）。
- 规则随配置推送、按版本栅栏生效（第 6 节第二类）。从"全部"改成"仅分配"后，Key 在其他节点上的额度闲置后按 4.4 收回。

**重新分配**：
- 管理员可以逐个或按节点批量把 Key 移到另一台（比如某台长期压力过高）。
- 重新分配会改变导出给出的地址，已经配置好的客户端不会自动变，用户要重新导出或手动改地址。规则为"仅分配的从节点"时，旧地址在用户改过来之前会被拒绝，所以批量移动前要提示影响的 Key 数。
- Key 页面标出"地址已变更"，提醒用户更新。
- 删除从节点时，分到它的 Key 自动重新分配并同样提示；也可以保留这个域名，由管理员把解析改到新机器（11.6）。

**节点故障时**：系统告警并列出受影响的活跃 Key，不自动改解析。管理员可以手动把这台的域名解析改到主节点（10.3），用户不用改地址；主节点分配比例为 0 时不能这样做，这台的 API Key 用户在节点恢复或管理员重新分配前不可用。

每台从节点用自己域名的 HTTPS 证书，由从节点自己申请（11.1、15.2）。

### 10.3 健康判断

心跳只能证明"从节点到主节点"是通的。从节点对外端口被挡、HTTPS 证书过期、域名解析错、连不上上游时，心跳照样正常。所以还要：

1. **外部探测**：主节点每分钟从公网探测每台从节点的对外地址，连续失败就标为"对外不可达"，停止分配（小白端用户、新 Key）并告警。
   探测直接连这台机器的 IP、按它的域名做 TLS 握手（SNI），不走域名解析，所以域名被改到主节点时仍然探测的是这台机器本身。
2. **客户端失败报告**：小白端连不上分配的节点、向主节点要新分配时，报告连不上哪台。同一台短时间内被很多用户报告，停止分配并告警。
3. **错误率降级**：某台错误率明显高于其他节点（比如连不上上游），自动停止分配并告警，恢复后自动恢复。
4. **证书到期**：从节点对外 HTTPS 证书剩 7 天到期时告警。

以上状态影响小白端的分配和新 Key 的分配；已分配到这台的 API Key 不移走。

**域名由管理员手动管理**（暂不接域名服务商接口，系统不改解析）：
- 管理员在域名服务商处给每台从节点的域名加解析，指向这台的 IP，再在管理页填写域名。建议解析 TTL 设 60 秒，手动切换时生效更快。
- 主节点每分钟解析一次各从节点域名，管理页显示"当前解析到：这台 / 主节点 / 其他地址"；和预期不符（比如解析错了、被人改了）时告警。
- **故障时**：告警里带受影响的活跃 Key 数。管理员可以选择：
  - 等节点恢复；
  - 在域名服务商处把这台的域名解析改到主节点的 IP（主节点分配比例须大于 0），恢复后再改回；
  - 把这台的 Key 批量重新分配到别的节点（用户要改地址，10.2）。
- **主节点接从节点域名**：解析改到主节点后，主节点前面的 Caddy 按需为这个域名申请证书（on_demand TLS）。申请前 Caddy 先问主节点"这是不是已登记的从节点域名"（这个查询接口只监听本机，不对外），不是就拒绝，防止被人拿任意域名刷证书。
  用从节点域名打到主节点的请求，按 Host 只开放 API Key 网关接口（8.3 的 API Key 一行），走 10.5 的主节点转发，计入转发上限，不受节点规则限制；主节点分配比例为 0 时拒绝；票据接口、网页、后台一律 404。
- 小白端不需要这套：它连不上时向主节点要新分配（10.1）。

### 10.4 排空与手动调整

- **排空**：不再分配新用户和新 Key，小白端下次询问时换走 → 进行中的请求结束、本地扣费队列清空、额度全部退回 → 停机。
  WebSocket 和实时会话可能一直不结束，排空最长等 30 分钟，到时主动断开剩余连接。
- **排空不会自动改解析**，停机期间分到这台的 API Key 用户不可用。管理页排空前提示受影响的活跃 Key 数。需要不中断时，管理员先在域名服务商处把解析改到主节点（主节点分配比例须大于 0），等 TTL 过去（建议 5 分钟，有些客户端缓存解析更久）再排空，升级完改回。
- **手动移动或固定用户**：管理员可以把某个小白端用户移到指定节点，或暂时固定在某台上（固定必须设到期时间，到期恢复自动分配）。移动只对下一个请求生效。
  固定的节点离线或对外不可达时，自动解除固定并通知管理员。操作要二次验证并记审计。

### 10.5 主节点转发

**主节点分配比例为 0 时，主节点不转发任何请求**，下面几种情况都不发生：API Key 请求打到主节点返回 403（OpenAI / Anthropic 格式），提示"请改用 <这个 Key 分配的地址>"；小白端不会分到主节点；从节点域名即使被改到主节点也会被拒绝。

分配比例大于 0 时，主节点在这些情况下转发请求：

- **按比例分到主节点的小白端用户和 Key**（10.8）。
- **API Key 请求打到主节点**：照常处理，不管节点规则。包括主节点现有域名（旧地址 10.7、分组只有"仅主节点"账号的 Key、用户手动改用），以及管理员手动改到主节点的从节点域名（10.3）。
- **从节点全部不可用时的小白端**：由主节点判断。客户端连不上自己的从节点时，向主节点要新分配。还有可用的从节点就分到别的从节点；一台可用的都没有（全部离线、对外不可达、排空或停用）时，主节点才把自己分出去。
  分配比例为 0 时不分给主节点，分配查询接口返回"暂无可用中转"（10.9），服务中断，发紧急通知。
  "可用但压力都很高"不算不可用，仍分配到从节点。

规则：
- 主节点上的转发走本机完整流程，直接读写数据库扣费，不走额度锁定。余额检查看可花余额；用户额度锁在从节点上不够用时，按 4.4 先从从节点收回。
- **主节点转发设上限**（带宽、并发请求数，后台可调），超过上限返回"服务繁忙"（OpenAI / Anthropic 格式）。登录、计费、从节点通信优先，不受这个上限影响。否则控制功能被挤垮，从节点恢复后也连不上主节点；也防止有人打挂从节点把流量逼到主节点。
- **恢复**：有从节点重新可用后，小白端下次定期询问时分回从节点；管理员把手动改到主节点的从节点域名改回（10.3），API Key 用户不用操作。

### 10.6 主节点不可用时

选号要问主节点，所以主节点挂了，新请求全部停止，返回 OpenAI / Anthropic 格式的错误。
主节点自己的规则：Postgres 或 Redis 任一不可用时，不锁新额度、不选号。

### 10.7 上线迁移

现有域名继续给主节点用；现有 API Key 用户要改地址。

1. 上线时为所有现有 Key 批量分配从节点（按 10.2 的分配方式）。
2. Key 页面和导出配置改成给出分配的地址，页面提示老用户更新地址。
3. 旧地址（主节点域名）继续可用，照常处理，但流量走主节点带宽，计入主节点转发上限。**迁移期间主节点分配比例必须大于 0**，否则旧地址的请求会被拒绝（10.5）；比例本身可以很小，它只影响新分配。
   迁移期间主节点转发上限要按实际旧地址流量设置，否则老用户会被"服务繁忙"拒绝；随着用户迁走逐步下调。
4. 后台列出"仍在用主节点地址的 Key 和用户"，按流量排序，方便逐个提醒。基本迁完后再把比例调到 0（如果想让主节点完全不做中转）。
5. 小白端：控制地址就是现有域名，升级客户端后自动按 10.1 分配，不用用户操作。

### 10.8 主从分配比例

从节点管理页通用配置里设置**主节点分配比例**（0~100%，只有管理员能改，二次验证、记审计）：

- **含义**：新分配（小白端用户、新生成的 Key）中分给主节点的比例；其余分给从节点，从节点之间按 10.1 的剩余容量加权。
  比如 10%：大约每 10 个新用户或新 Key 有 1 个分到主节点。
- 主节点也受 85% 负载阈值约束，负载按主节点转发量 / 主节点转发上限计算；超过阈值时这次分配改给从节点。
- 所有从节点都不可用时，比例大于 0 就全部分给主节点（10.5），不再按比例。
- **调整比例只影响新的分配**，已分配的不动。要让现有小白端用户按新比例分布，管理员在管理页执行"重新平衡"，小白端下一次询问时生效。Key 不自动重新平衡，因为要用户改地址。

**比例为 0：主节点不做任何中转。**

| 影响 | 处理 |
|---|---|
| 新分配 | 全部分给从节点 |
| 已分到主节点的小白端用户 | 下一次询问时移到从节点 |
| 已分到主节点的 Key | 保存时提示受影响的 Key 数，管理员确认后批量重新分配到从节点；用户要改地址（10.2 重新分配） |
| API Key 打到主节点域名 | 返回 403，提示这个 Key 分配的地址（10.5） |
| 从节点故障、排空 | 不能把域名改到主节点（改了也会被拒绝）；这台的 API Key 用户不可用（10.3、10.4） |
| 从节点全部不可用 | 服务中断，发紧急通知（10.5） |
| "仅主节点"账号和只有这类账号的分组 | 不会被用到，这些分组的用户无法使用（第 9 节）；保存时提示受影响的分组、用户和 Key 数 |
| 迁移期间用旧地址的用户 | 被拒绝，所以迁移完成前不要设为 0（10.7） |
| 网页 playground、网页聊天、只在主节点提供的接口（批量图片等） | **不受影响**：它们是主节点自己的功能，不属于分配（不变量 1）。需要关闭时用这些功能各自现有的开关 |

改成 0 之前，管理页先列出上面各项的受影响数量，确认后才保存。

### 10.9 分配查询接口

客户端向主节点查询自己分到的中转地址。只在主节点提供，不经过从节点（API Key 版本除外）。

**小白端**（登录态，主节点现有域名，归入 8.3 的"只在主节点"）：

```
GET  /api/v1/paw/relay/assignment
POST /api/v1/paw/relay/assignment        body: {"unreachable_node_id": 12}
```

- GET：返回当前分配。登录后、每隔 `refresh_after` 秒、以及切组后调用。
- POST：连不上分配的节点时调用，带上连不上的节点 ID（10.3 的客户端失败报告），返回新的分配。
- 两个接口按用户限流。

返回：

| 字段 | 说明 |
|---|---|
| `role` | `relay`（从节点）或 `master`（主节点） |
| `node_id` | 分配的节点 ID；主节点为 0 |
| `base_url` | 转发地址，`https://<域名>`。`relay` 时是从节点域名；`master` 时是主节点现有域名 |
| `ticket`、`ticket_expires_at` | 中转票据（8.1），只在 `role=relay` 时有；`master` 时沿用现有登录态访问 `/api/v1/paw/*` |
| `refresh_after` | 建议多少秒后再查，默认 60 |

- 没有可用中转时（从节点全部不可用且主节点分配比例为 0）返回 503，错误码 `RELAY_UNAVAILABLE`。客户端显示"服务暂不可用"，按 `refresh_after` 继续查询。
- 不返回其他节点的地址、负载等信息。
- 客户端只把 `base_url` 设成本机 LocalPawRelay 的上游地址（10.1），切换只对下一个请求生效。

**API Key**（给第三方工具自动获取地址用）：

```
GET /v1/relay/assignment        Authorization: Bearer <API Key>
```

- 返回这个 Key 的 `role`、`node_id`、`base_url`（主节点时为主节点现有域名），不返回票据。
- 主节点域名和所有从节点都可以访问；从节点转交主节点执行（8.4）。这是查询不是转发，主节点分配比例为 0 时也可用。
- Key 被重新分配后，工具可以用它发现新地址。

## 11. 从节点注册、激活与管理

### 11.1 注册

从节点本机只需要两样东西：**主节点地址、主从通信根证书指纹**（可选再填一个显示名称）。这两样在后台从节点管理页上提供。其余配置全部由主节点下发，本地不能改。

1. 从节点第一次启动时在本机生成长期密钥（私钥不离开本机），在控制台和日志里打印公钥指纹。
2. 连接主节点，先核对根证书指纹，对不上就拒绝连接。
3. 发送注册信息：公钥、主机名、程序版本、系统信息、显示名称。
4. 主节点记录下来，节点出现在管理页的"待激活"里，同时记录注册来源 IP。
5. 管理员核对后激活，填写或确认名称、**对外域名**（必填，API Key 导出地址就取它，10.2）、带宽上限、地域标签。
   激活前主节点检查这个域名当前解析到这台的注册 IP（不一致时提示，管理员可确认继续）。
   主节点这时才签发主从通信证书、下发完整配置。
   从节点收到域名后，自己用 ACME（TLS-ALPN-01，走 443 端口，不需要域名服务商密钥）向 Let's Encrypt 申请这个域名的 HTTPS 证书并自动续期；证书私钥只在这台从节点上，主节点不持有。申请不到时，管理员可以在从节点本机放置证书文件。
   外部探测握手成功后才开始分配用户和新 Key。
6. 之后重启时用同一把长期密钥连接，被认作同一台，不用重新激活。

任何人都能向主节点注册（没激活什么都做不了），所以要防刷：
- 注册接口按来源 IP 限流；
- 待激活节点最多 20 台，满了拒绝新注册；
- 待激活 24 小时未激活自动清除；
- 注册信息限制大小，主节点不对它做耗时处理；
- 管理页可以一键拒绝所有待激活节点。

### 11.2 激活

**待激活的节点**：只能发心跳；不分配用户和 Key；不能申请额度、选号、上报扣费、查询 Key；只拿到心跳所需的最少参数；收到任何客户端请求一律拒绝。

**激活页面显示**：注册时间、注册来源 IP、主机名、程序版本、系统信息、**公钥指纹**。

**管理员必须把从节点本机控制台上的指纹和页面上的指纹对一下，一致才激活。** 名称、主机名、IP 都能被模仿，指纹是区分"自己部署的机器"和"别人注册上来的机器"的唯一可靠依据。

- 激活要二次验证，记审计（谁、什么时候、核对的指纹）。
- **拒绝**：这把公钥被拉黑，同一台机器要换密钥重新注册。
- **需要重新激活的情况**：从节点重装、长期密钥变了（重新注册）；同一身份出现两份（7.2）自动退回待激活；管理员停用后再启用。
  重新注册的是一台新节点，原节点的域名和分到它的 Key 由管理员转给新节点（11.6）。

### 11.3 主节点下发的配置

| 类别 | 内容 |
|---|---|
| 节点身份 | 节点 ID、名称、地域标签、证书 |
| 对外服务 | 对外域名、监听端口（HTTPS 证书由从节点自己申请，11.1） |
| 容量 | 带宽上限、最大连接数、最大并发请求数、分配权重 |
| 行为参数 | 心跳间隔、额度规则、本地队列上限、日志级别和采样、Key 负缓存时间 |
| 转发配置 | 第 6 节第二类配置 |
| 公钥 | 验中转票据、验扣费凭证用的公钥（含轮换） |
| 状态 | 待激活、已激活、排空、停用 |

**通用配置**（管理页上的一组全局设置，对所有从节点生效）：主节点分配比例（10.8）、API Key 节点规则（10.2）、额度规则默认值、心跳和离线判定、排空等待时间等（第 19 节的参数）。单台的配置未单独设置的项沿用通用配置。

- 除"状态"和心跳所需参数外，其余只在激活后下发。
- 配置带版本号，修改后立即推送（第 6 节）。
- 配置里不含数据库、Redis、对象存储凭据，也不含主节点的任何私钥。

### 11.4 心跳

每 5 秒一次，连续 15 秒收不到就标为**离线**：不再分配新用户和新 Key，额度等租约到期后收回，发离线通知。

心跳内容：版本号、配置版本号、启动时间；网卡实时收发速率；客户端连接数（包括流式响应、WebSocket）；进行中的请求数和选号 ID；活跃人数和活跃 Key 数；本机锁定额度总额、各用户累计已用；本地扣费队列积压条数、最早一条的时间；日志发送积压和丢弃条数；近 1 分钟请求数、错误数；CPU、内存、磁盘剩余。

### 11.5 管理页

**列表**，每台一行：

| 列 | 说明 |
|---|---|
| 名称、地域、对外域名 | 域名当前解析到：这台 / 主节点 / 其他地址（不符合预期时标红） |
| 状态 | 在线 / 对外不可达 / 降级 / 离线 / 排空中 / 已停用 / 待激活（醒目显示并排在最前） |
| 最后心跳 | 距现在几秒 |
| 当前压力 | 上行、下行实时带宽及占上限的百分比，超过阈值标红 |
| 服务人数 | 分配人数（分到这台的小白端用户数）；分配 Key 数（其中近 7 天活跃的）；活跃人数（最近 5 分钟有请求的不同用户数，含 API Key 用户） |
| 连接数 | 客户端连接数、进行中的请求数 |
| 版本 | 程序版本、配置版本；落后或协议即将不兼容时标出 |
| IP | 当前连接的来源 IP；最近一次变化的时间 |

主节点也作为一行显示：主节点分配比例、转发带宽、占转发上限的百分比、分到主节点的用户和 Key 数、在主节点上转发的用户和 Key 数（按原因：按比例分配、旧地址、仅主节点分组、从节点域名被改到主节点、小白端回退）。

**详情页**：
- 最近 24 小时的带宽、连接数、服务人数、请求数、错误率曲线；
- 本机锁定额度总额、扣费队列积压、迟到扣费、丢失用量、待复核扣费；
- 这台上的小白端用户列表、分配的 Key 列表；
- 异常检测记录：额度申请频率异常、选号后未上报扣费的比例；
- 日志（第 12 节，默认筛这台；可获取单条详情和最近日志）；
- 审计记录。

**用户管理页**也显示这个用户当前分在哪台、他的 Key 各分配到哪台、最近在哪几台（含主节点）上有请求、锁在各节点上的额度；锁在离线节点上的额度可以"立即回收"（4.4）。

**操作**：激活、拒绝、一键拒绝所有待激活、修改配置、排空、恢复、停用、一键收回该节点所有额度（节点在线时同步收回；离线时即"立即回收"，租约当场作废，4.4）、吊销证书、删除、手动移动或固定用户、批量移动该节点的 Key、修改对外域名、修改通用配置（含主节点分配比例，改成 0 前先看影响清单，10.8）、按新比例重新平衡小白端用户、关闭"同时两个 IP"判断、复核吊销节点的扣费、临时调日志级别、获取最近日志、诊断（连通性、对外探测、上游连通、配置版本、时钟偏差，只返回状态，不返回请求内容）。
所有操作只允许最高权限的管理员，要求二次验证（现有 `stepUpAuth`）并记审计。

实时数字来自最近一次心跳；曲线由主节点把心跳按分钟汇总后存储。分配人数和分配 Key 数由主节点统计，活跃人数由从节点上报。

### 11.6 部署与升级

- **长期密钥和 HTTPS 证书缓存要持久保存**。用容器部署时，这两个目录挂到持久存储：长期密钥丢了会变成一台新节点，要重新激活；证书缓存丢了每次重建都要重新申请证书，容易撞上 Let's Encrypt 的签发次数限制。
- **换机器、重装**：管理员在域名服务商处把域名解析改到新机器；新机器按新节点注册、激活后，在管理页把旧节点的域名和分到它的 Key 转给新节点（一步操作），域名不变，用户不用改地址。
- 从节点关闭自动更新和 `AUTO_SETUP`（`deploy/docker-compose.yml:44` 默认开着，首次启动会跑安装流程、写配置文件）。
- **升级**：后台排空 → 升级 → 恢复，一台一台来。主节点先升，再升从节点。不想让这台的 API Key 用户中断时，按 10.4 先手动把解析改到主节点。
- **主节点换服务器**：只要根证书不变，从节点改一下主节点地址就能重新连上，不用重新激活。

## 12. 从节点日志

**原则**：从节点只把几个主要字段的摘要发回主节点，完整内容留在从节点本机，需要时按条获取。回传的日志量要比转发流量小几个数量级，否则分流就没有意义。

### 12.1 现有日志

| 种类 | 现在怎么存 | 后台怎么看 |
|---|---|---|
| 程序日志 | 控制台和本机文件（`data/logs/sub2api.log`，`pkg/logger/options.go`）；同时经 `service/ops_system_log_sink.go` 脱敏（`util/logredact`）后批量写数据库 | "系统日志"页（`/admin/ops/system-logs`），可按时间、主机、级别、组件、请求 ID、用户、Key、账号、平台、模型、关键字筛选；级别、采样、保留天数可实时调整（`service/ops_log_runtime.go`） |
| 请求错误日志 | 数据库，含错误信息、错误响应体、上游错误详情、逐次上游错误（`service/ops_port.go:64` `OpsInsertErrorLogInput`） | 错误日志列表和详情 |

### 12.2 回传什么

| 种类 | 回传到主节点（写进现有表） | 只留在从节点本机 |
|---|---|---|
| 请求错误日志 | 时间、请求 ID、客户端请求 ID、用户 / Key / 账号 / 分组 ID、客户端 IP、平台、请求模型、上游模型、入口路径、是否流式、错误阶段、错误类型、严重程度、状态码、上游状态码、错误信息（截到 256 字符）、各段耗时（鉴权、选号、上游、首字） | 错误响应体（`ErrorBody`）、上游错误详情（`UpstreamErrorDetail`）、逐次上游错误（`UpstreamErrors`）、User-Agent |
| 程序日志 | 只回传**警告及以上**：时间、级别、组件、消息（截到 256 字符）、请求 ID、用户 / Key / 账号 ID | 信息和调试级别、堆栈、其他附加字段 |
| 逐请求访问日志 | 不回传 | 全部（本来默认关闭） |
| 日志计数 | 每分钟按（级别, 组件）和（错误类型, 状态码）汇总的条数 | — |

- 每条摘要截断后不超过 1KB；每台每秒最多回传 50 条，超出的只计数不回传，计数照常回传。
  按上限算，一台最多约 50KB/秒，相对 MB 级的转发流量可以忽略。
- 请求成功时不产生日志回传（用量走扣费记录，第 5 节）。

### 12.3 要看完整内容时

- **单条错误详情**：错误日志详情页上，来源是从节点的记录显示"完整内容在从节点"。点"获取详情"时，主节点按请求 ID 向那台要这一条的完整内容（已脱敏，单条上限 64KB），只在页面显示，不入库。
  从节点离线、或本机日志已滚动删除时取不到，页面说明原因。
- **最近日志**：从节点详情页"获取最近日志"，最多 200 行、256KB，只显示不入库。
- 从节点本机按请求 ID 给错误详情建简单索引，取单条时不用扫整个文件。

### 12.4 来源显示

- 系统日志、错误日志的列表**新增"来源"列**：显示"主节点"或从节点名称，悬停显示节点 ID 和 IP；可以按来源筛选（主节点也是一个选项）。从节点详情页的"日志"标签默认筛这台。
- 后台使用记录列表也新增"来源"列（取 `usage_log.node_id`，16.6）。
- 来源由主节点按连接证书填写（日志表加 `node_id` 列，主节点自己写的为空），不信从节点自己报的。
- 同一个请求 ID 下，主节点（选号、入账、上游错误决策）和从节点（转发）的记录都能搜到，用"来源"列区分。

### 12.5 发送与断线

- 日志摘要走独立的日志连接，优先级最低，扣费优先。内存队列满了丢最旧的并计数；详情页显示积压和丢弃条数。
- 断线时内存里保留最近约 1000 条摘要，重连后补发。
- 本机文件日志保留完整内容（单个 20MB、保留 5 个）。本机文件和回传摘要用同一套脱敏，都不写请求内容、响应内容、密钥和凭据。

### 12.6 按节点调级别

- 日志级别、采样随节点配置下发，默认跟主节点一致。级别只影响从节点本机记多少，回传始终只有警告及以上的摘要。
- 可以只把某一台临时调成详细级别，必须设到期时间（比如 30 分钟），到期自动恢复；详细内容用"获取最近日志"查看。

### 12.7 安全

- 从节点发来的摘要和按需取回的详情都是不可信输入：主节点再脱敏一次；限制每条长度和字段数；后台一律按纯文本显示，不当 HTML 渲染。
- 查看权限和保留天数沿用现有系统日志的设置。

## 13. 通知

**现有能力**：运维告警（`service/ops_alert_evaluator_service.go`）支持按规则产生告警事件、按严重程度过滤、每小时限量，但只能发邮件（`:678` `maybeSendAlertEmail`）。

**做法**：
- 从节点相关事件接入现有运维告警，在后台查看、确认、恢复。
- 新增**飞书机器人**渠道（后台填 Webhook 地址和签名密钥），与邮件并列，每类事件可选渠道。飞书发送失败时重试，仍失败就改发邮件。
- 飞书 Webhook 地址和签名密钥只存在主节点，加密保存，修改要二次验证；使用飞书自带的签名校验。

| 事件 | 默认 | 严重程度 |
|---|---|---|
| 从节点离线 | 开 | 严重 |
| 从节点恢复在线 | 开 | 提示 |
| 从节点对外不可达、降级（10.3） | 开 | 严重 |
| 从节点域名的解析和预期不符（解析到别处、解析失败） | 开 | 严重 |
| 从节点 HTTPS 证书自动申请或续期失败 | 开 | 严重 |
| 从节点 HTTPS 证书即将到期 | 开 | 警告 |
| 所有从节点不可用，小白端已回退到主节点 | 开 | 紧急 |
| 所有从节点不可用且主节点分配比例为 0，服务中断 | 开 | 紧急 |
| 主节点分配比例被修改 | 开 | 提示 |
| 回退结束，小白端已切回从节点 | 开 | 提示 |
| 主节点转发达到上限，开始拒绝请求 | 开 | 严重 |
| 同一身份出现两份，节点已退回待激活（7.2） | 开 | 严重 |
| 证书过期后用长期密钥恢复 | 开 | 警告 |
| 有从节点注册，等待激活 | 开 | 提示 |
| 待激活超时自动清除 | 开 | 提示 |
| 固定的用户因节点故障被自动解除固定 | 开 | 提示 |
| 本地扣费队列积压过多 | 开 | 警告 |
| 从节点停止接收新请求（磁盘满、扣费队列损坏、时钟偏差超限） | 开 | 严重 |
| 额度申请频率异常、选号后未上报扣费比例异常 | 开 | 严重 |
| 从节点连接 IP 变化 | 开 | 提示 |
| 从节点压力持续超过阈值（比如 85% 持续 5 分钟） | 关 | 警告 |
| 从节点版本或配置版本落后 | 关 | 提示 |

**避免刷屏**：同一台一次离线只发一条，恢复时再发一条；短时间反复上下线合并成一条"不稳定"；多台同时出事合并成一条；大量注册合并成一条。

**内容**：节点名称、IP、事件时间、最后一次心跳时间、受影响的分配人数、分配的活跃 Key 数和进行中的请求数、系统已采取的动作、后台管理页链接。不包含用户信息、密钥、凭据。

**主节点自己挂了发不出通知**，从节点也不能代发（不持有飞书密钥）。上线前要在另一台机器上准备独立的外部监控，定时探测主节点，失败时发飞书。

## 14. 异步图片任务

现有做法（`docs/ASYNC_IMAGE_TASKS.md`）：提交后返回任务 ID，后台生成，结果存对象存储，客户端用 `GET /v1/images/tasks/{task_id}` 轮询；任务状态在 Redis，任务完成时扣费。功能默认关闭。

主从模式下：**任务提交落在哪台从节点，就由那台执行。**

- **任务状态放主节点**：从节点接到提交后向主节点登记，执行中上报进度和结果位置。
- **轮询可以落在任何节点**（包括域名在任务执行中被改到主节点、或用户改用主节点地址）：那台向主节点查状态；要返回图片内容时，用主节点签发的临时下载地址从对象存储取，流量走这台从节点。
- **从节点不持有对象存储凭据**：上传用主节点签发的临时上传地址，只能上传这个任务的这一个文件，几分钟后失效。
- **扣费**：提交时选号、拿扣费凭证、本地预扣；任务完成时按凭证入账。凭证和预扣在任务执行期间持续续期。
- **执行中的从节点挂了**：主节点超时后把任务标为失败，不扣费。

批量图片任务只在主节点（8.4），用 `frozen_balance`，与从节点额度的 `relay_reserved_balance` 互不影响。

## 15. 安全汇总

### 15.1 从节点被攻破时

| 攻击 | 上限 | 防护 |
|---|---|---|
| 拿走正在用的上游凭据 | OAuth 短期 token 到期为止；静态 Key 长期有效 | 短期 token；静态 Key 账号可设"仅主节点"（第 9 节） |
| 收集经过它的用户 API Key | 分到这台的 Key；节点规则为"全部从节点"时还包括被用户改到这台的 Key | 无法避免（Key 本身就发给它）；吊销这台后，后台一键列出分到它的 Key，提示用户重置 |
| 虚报用量，多扣用户的钱 | 同一时刻每个用户最多 5；但可以反复申请 | 见下 |
| 少报用量，白用上游账号 | 不受额度限制（它有账号凭据） | 主节点用自己的凭据定期独立查询上游账号用量，与各从节点回报的总量对账；选号后未上报扣费的比例异常报警（5.3）；反复丢数据报警（5.4） |
| 伪造票据、扣费凭证 | 做不到：只有公钥 | 非对称签名 |
| 编造扣费记录 | 做不到 | 每条记录必须带有效凭证，每张只入账一次 |
| 谎报计费模型 | 做不到 | 必须在凭证允许的范围内 |
| 伪造主节点下指令 | 做不到 | 双向 TLS，固定根证书指纹 |
| 偷走证书和密钥，在别的机器上冒充这台节点 | 到这台节点下一次续签为止（最长约 24 小时），或被发现、吊销为止 | 续签换密钥；同一身份出现两份立即断开并退回待激活；换 IP 告警 |
| 偷走长期密钥 | 证书过期需要恢复时可以冒用 | 长期密钥只用于恢复；恢复时同样检查同一身份出现两份；恢复记审计并通知 |
| 用 Key 查询试探主节点 | 受限流约束 | Key 查询有负缓存和每台速率上限（8.2、7.4） |
| 重放或篡改扣费批次 | 做不到 | TLS + 批次序号 + 凭证只入账一次 |
| 在日志里写入恶意内容 | 做不到有效攻击 | 主节点再脱敏、纯文本显示（第 12 节） |
| 读本地磁盘 | 扣费队列（凭证和用量数字）、长期密钥、HTTPS 证书私钥、本机完整错误日志（已脱敏，可能含上游错误信息的片段） | 队列不存凭据和请求内容；Key 缓存和上游凭据只在内存；系统设置里的密钥不下发（6）；被攻破后吊销这台并换掉它的域名证书 |
| 读用户对话 | 流经它的内容 | 无法避免，只能部署在自己能控制的服务器上 |

**关于虚报用量**：每台上限 5 限制的是一次能锁住多少，不是一台节点总共能扣走多少。被攻破的节点可以虚报用完后再申请。上限的作用是拖慢速度、给检测留时间，真正拦住它的是：
- **申请频率检查**：同一用户在同一台上的补充频率、消耗速度明显高于该用户历史水平或其他节点时，暂停给这台发额度并报警；
- **记录必须对应选号**：没有有效凭证的记录不入账；token 数要和请求体大小对得上；
- **一键收回**：收回某台所有额度、吊销证书，吊销前的扣费标记待复核。

### 15.2 部署要求

| 要求 | 原因 |
|---|---|
| 从节点只开放 8.3 列出的接口，不挂管理后台、登录、内嵌前端（`router.go:74-75`）、安装向导 | 缩小公网攻击面 |
| 从节点关闭 `AUTO_SETUP` 和自动更新 | 见 11.6 |
| 从节点只开 HTTPS，不开 HTTP | 见 7.1 |
| 主节点接从节点的端口直连，不经过会解密的代理或 CDN | 见 7.1 |
| 每台从节点自己申请自己域名的 HTTPS 证书，私钥只在本机，不共用通配符证书；主节点不持有从节点证书，接从节点域名时由 Caddy 按需申请，且只给已登记的从节点域名申请 | 共用一张通配符证书时，一台被攻破就泄露整个域名的私钥 |
| 域名服务商账号由管理员自己保管，系统不保存 | 暂不接域名服务商接口，系统里没有能改解析的密钥 |
| 主节点对外端口上，用从节点域名访问时只开放 API Key 网关接口 | 不让从节点域名成为访问后台、登录的入口 |
| 健康检查、监控只走长连接 | 不对外暴露内部状态 |

## 16. 其他细节

1. **附件**：`/paw/files` 上传的附件存在进程内存里（`NewPawAttachmentMemoryRepository()`），之后按 ID 引用。小白端同一用户所有请求走同一台，可以直接在从节点上运行；上传后、使用前换了节点时会找不到，本次接受。
2. **并发槽**：现有并发槽 15 分钟自动过期（`repository/concurrency_cache.go:47`），有流量时刷新。释放消息丢了最多占用 15 分钟。超过 15 分钟的长请求靠心跳里的选号 ID 续期。
3. **WebSocket 和实时会话**：现有代码每一轮重新定价（`service/openai_profit_control.go:182`），在线占用 60 秒过期需持续刷新（`concurrency_cache.go:39-40`）。所以每一轮都要选号拿报价，占用通过长连接刷新；实时音频的时长由从节点上报。
4. **进程内的上限要按节点数调整**：图片生成并发、WebSocket 连接数等按进程计算（`deploy/config.example.yaml:501`）。
5. **余额很少的用户**：余额不足 0.1 时会被全部锁到一台。小白端和只用分配地址的 API Key 用户只在一台上用，不受影响。
   同一用户同时在多个地址使用时（多个 Key 分到不同节点、节点规则为"全部从节点"时换了地址、同时用主节点地址），别处的请求可能看到"余额不足"，直到按 4.2 从持有的那台收回（剩余低于 1 时立即收回）。这是预期行为，客服要知道。
6. **可观测性**：`usage_log` 加 `node_id`（主节点转发也记），后台按节点看流量、错误率、延迟、丢失用量、额度申请频率。
