# 主从节点架构设计（v0.27，2026-10-06）

> 状态：开发中（分支 `feat/master-relay-nodes`，进度见开发计划）。本文只记录当前结论；历史版本不再保留在正文里。开发计划见 `docs/MASTER_RELAY_NODES_PLAN.md`。
> 代码引用按 2026-09-25 的 main（`c652d850`）核对；行号会漂移，引用处同时写了函数名，以函数名为准。

## 1. 目标与已定决策

**目标**：单台服务器的公网带宽不够，把中转的大流量分到多台从节点上。
主节点负责登录、鉴权、选号、计费、节点管理和分配；从节点只负责转发，不连数据库。

**分工原则（2026-09-29 定）**：几乎所有转发逻辑都在从节点完成，**主从之间只有授权和计费**；日志和记录留在从节点，由从节点提供查询（后续加）。
判断一件事放哪边：它是授权（能不能用、用哪个账号、封不封号）或计费，就在主节点；否则在从节点本地做，主节点只接收影响授权的结果（如违规次数）和扣费记录。转发功能要用的密钥（审核接口、提示词审计、联网搜索）加密下发给从节点（6 第二类），而不是让从节点每次去问主节点。

| 项 | 决定 |
|---|---|
| 瓶颈 | 服务器公网带宽 |
| 从节点数据访问 | 不连 Postgres，不连 Redis，只连主节点 |
| 选号 | 每个请求向主节点要一个上游账号（第 3 节） |
| 额度 | 从节点每次向主节点申请用户未锁定额度的一半，每台为同一用户最多持有 5，最小锁定单位 0.05；不够再申请，申请不到就拒绝（第 4 节） |
| 扣费 | 从节点本地记账，异步批量回报；主节点逐条走现有扣费函数入账（第 5 节） |
| 从节点丢失的用量 | 不扣用户的钱，服务端承担 |
| 迟到的扣费记录 | 签发 60 天内照常扣，余额可能变成负数；超过 60 天按丢失处理（5.4） |
| 用户看到的余额 | 冻结是服务端内部的事，用户不感知；扣费回报后客户端刷新可见，略慢可接受 |
| 倍率、价格、配置修改 | 实时生效（第 6 节） |
| 主从通信 | 从节点主动建立的长连接，TLS 1.3 双向认证，不允许任何明文（第 7 节） |
| 从节点接入 | 从节点直接注册，管理员在从节点管理页核对指纹后激活才能用（第 11 节） |
| 从节点鉴权 | 从节点按凭据类型开放不同接口：中转票据只能用小白端转发接口，API Key 只能用网关接口（8.3） |
| 按账号分配节点 | 只有小白端：登录后由主节点分配一台从节点，同一用户所有请求走这台（10.1） |
| 从节点域名 | 管理员在域名服务商处自己配解析，在从节点管理页给每台填写对外域名；暂不接域名服务商接口，系统不改解析（10.3） |
| API Key 用户 | 直接访问从节点，从节点向主节点认证。每个 Key 生成时由后台分配一台从节点，导出和推荐配置时取这台的域名（10.2） |
| API Key 节点规则 | 从节点通用配置项，只有管理员能改：API Key 仅能在分配的从节点使用，或可在全部从节点使用（10.2） |
| 主从分配比例 | 从节点管理页通用配置：主节点承担多少比例的新分配（0~100%），其余按带宽分给从节点。**为 0 时主节点不做任何中转**（10.8） |
| 分配查询接口 | 客户端向主节点查询自己分到的中转地址，返回从节点或主节点（10.9） |
| 从节点故障 | 告警并列出受影响的 Key；管理员可以手动把这台的域名解析改到主节点（主节点分配比例须大于 0），用户不用改地址（10.3） |
| 主节点域名 | 保持现有域名不变，用于网页、后台、登录、小白端控制。API Key 请求打到主节点时：分配比例大于 0 照常处理，计入主节点转发上限；为 0 时拒绝，并提示这个 Key 分配的地址（10.5） |
| 现有 API Key 用户 | 上线时为现有 Key 批量分配从节点，用户需要改成新地址；迁移期间主节点分配比例保持大于 0，旧地址继续可用（10.7） |
| 从节点全部不可用 | 主节点分配比例大于 0 时，小白端转到主节点，从节点域名可由管理员手动改到主节点，主节点转发设上限；为 0 时服务中断（10.5） |
| 静态 API Key 类型的上游账号 | 后台开关，可设为"仅主节点使用"（第 9 节） |
| 异步图片任务 | 谁接到谁处理（第 14 节） |
| 下发给从节点的配置 | 按白名单下发，只含转发需要的项；管理员 API Key、SMTP 密码、OAuth / 验证码密钥等与转发无关的密钥一律不下发。转发功能要用的密钥（审核接口 Key、提示词审计凭据、联网搜索 Key，以及这些配置引用的代理）按节点加密下发、只在内存（6 第二类） |
| 联网搜索模拟 | 在从节点执行，搜索服务密钥加密下发（3.3） |
| 内容审核与 cyber 策略 | 安全审计（内容审核 + 提示词审计）在从节点判定；审核记录、风控记录留在从节点；违规次数报给主节点，由主节点累计、封号；"命中过的输入"名单同步到每台从节点；cyber 会话屏蔽随选号在主节点查（3.4） |
| 上游账号凭据 | 按账号缓存在从节点内存里，这台上所有用户共用，同一账号不重复下发；但每次使用前必须有主节点为这个用户、这个请求选中该账号的选号结果（9.1） |
| 主节点转发时的可花余额 | 鉴权层不动；请求前的余额预检减去单独缓存的冻结额（4.3） |
| 主节点转发上限 | 覆盖网页聊天和游客试用；手机同步会话不算（10.5） |
| 从节点日志 | 程序日志、请求错误日志、审核记录、风控记录都留在从节点本机，由从节点提供查询，后台按节点查（后续加）；主节点只收心跳里的计数用于告警（第 12 节） |
| 通知 | 从节点离线等事件发飞书或后台已设定的渠道（第 13 节） |
| 本次范围 | 所有转发路径和 API Key 用户都做（一次交付，不分期） |
| 本次部署 | 从节点与主节点同一地域 |

## 2. 总体结构

```
                           ┌──────────────── 主节点（控制流）────────────────┐
 小白端 ─登录/刷新/仪表盘/分配─▶│ 鉴权 · 额度锁定 · 选号 · 计价 · 记账 · 节点管理 │── Postgres / Redis
 网页、后台 ──────────────────▶│ 网页 playground/聊天、批量图片等只在这里         │   （只有主节点能访问）
   │                       └──────────────▲─────────────────────────────────┘
   │ 小白端：中转票据                       │ 加密长连接：认证 / 额度 / 选号 / 扣费 / 配置 / 日志 / 指令
   │ API Key 用户：分配的从节点域名          │
   │ 请求体、流式响应（MB 级）              │
   ▼                                      │
 从节点 1..N ─────────────────────────────┘
   │  本地：验票据 / 查 Key 缓存 · 查额度 · 本地记账 · 异步回报
   │  用上游凭据直连上游（经账号绑定的代理）
   ▼
 上游（OpenAI / Anthropic / ...）
```

**不变量**：
1. 请求体和响应体不经过主节点。例外只有这些，都计入主节点转发上限（10.5）：
   - 按主从分配比例分到主节点的小白端用户和 Key（10.8）；
   - 从节点全部不可用时小白端回退到主节点（10.5）；
   - 管理员把故障从节点的域名手动改到主节点期间，这台的 API Key 流量（10.3）；
   - 分组里只有"仅主节点使用"账号的用户（第 9 节）；
   - API Key 请求直接打到主节点域名（旧地址、手动改用）（10.2、10.7）；
   - 网页上的 playground 和聊天（登录态，不走从节点）；
   - 游客试用（`/api/v1/trial/*`，未登录访客的网页文字聊天，不走从节点）；
   - 手机同步会话（`/api/v1/remote/*`，桌面助手和手机各一条长连接，连接状态在主节点进程内）；
   - 只在主节点提供的接口，如批量图片（8.4）。

   主节点分配比例为 0 时，前五种都不会发生（10.8），只剩网页功能和只在主节点提供的接口。
2. 从节点没有数据库、Redis、对象存储凭据，也没有能签发用户票据、扣费凭证的私钥，也没有 JWT 密钥。系统设置里的密钥只拿得到转发功能要用的那几项（审核接口、提示词审计、联网搜索及其代理，加密下发、只在内存），其余一律拿不到（6 第二类）。
3. 任何时刻，所有从节点为同一用户锁住的额度加起来都不超过用户的可用额度。
4. 主节点保留完整的单机能力，现有单机部署不受影响。
5. 一套代码、一个程序，`NODE_ROLE=relay` 时换一套内部接线。现有的 `RUN_MODE`（standard/simple）是计费简化模式，与此无关。

## 3. 一次请求

### 3.1 流程

1. **客户端 → 从节点**：小白端带中转票据访问小白端转发接口；API Key 用户带 Key 访问网关接口（8.3）。
2. **本地鉴权**：验票据签名；或查本地 Key 缓存（未命中时问主节点），检查 Key 状态、到期、IP 白名单，以及节点规则是否允许这个 Key 在这台使用（8.2）。全局 IP 黑名单在这一步之前检查。
3. **粗查额度**：这个用户在本机有没有可用额度。没有就申请（第 4 节），申请不到就拒绝。
   小白端第一次申请时，主节点替它解析内部 Key（8.1），结果随额度返回并缓存。
4. **本地预处理**：从请求体提取模型、是否流式、会话哈希、`previous_response_id`、是否生成图片。
5. **选号（→ 主节点）**：发送凭据类型、用户、Key（小白端为内部 Key）、请求的分组（小白端按请求头；自动分组 Key 为候选池）、入口路径、模型、会话哈希、`previous_response_id`、cyber 会话屏蔽要查的键（已哈希）（安全审计在这之前已在从节点本地做完，3.4），以及记运维日志用的 UA、请求 ID、客户端请求 ID。
   主节点先做只有它能做的检查和决定：分组模型白名单、TypeSafe 分组的接口限制、全局用户黑名单、cyber 会话屏蔽、后台模式下只允许管理员（3.2）。
   自动分组 Key 的分组、组合平台分组的目标平台在这之前已经定下（从节点读出模型后问主节点 `ResolveRoute`，与本地这两个中间件在同一位置，3.2）：选号带着定下的分组，主节点只核对它是这把 Key 的候选；组合平台按同一个公开模型再选一次目标。
   然后选号（含分组兜底池，`fallback_pool.go`）、占并发槽，返回：
   - 账号和分组快照（含决定上游访问限制的字段：账号的贡献者、代理的归属用户，见第 9 节）、上游地址、代理（地址和凭据）、TLS 指纹配置、Anthropic OAuth 的身份指纹（`identityService.GetOrCreateFingerprint` 在主节点执行）、模型映射；
   - 上游凭据的版本号。凭据按账号缓存在从节点上、所有用户共用（9.1）：内存里已有这个账号的这个版本就直接用，没有时单独取一次（额外加密，见 7.1）；
   - 本次使用的分组和计费模式（余额或订阅）；
   - **扣费凭证**（5.3），里面包含入账要用的选号上下文；不计费的请求（如 `count_tokens`）不签发凭证；
   - 这次请求的换号上限（工作台本地回退 Key 更高，8.2）；
   - 当前配置版本号（6.2）；
   - 需要时顺带补充额度。
6. **精查额度并预扣**：按返回的分组和计费模式，检查用到的每一项子额度都够，并在本地**预扣这次请求的最低预估费用**。
   同一用户的并发请求（默认可同时 30 个）因此不会重复使用同一笔额度。
7. **转发**：本地配置版本落后时先同步拉取；改写请求体，直连上游，流式回传。
8. **本地记账**：从响应解析用量，写入本地扣费队列。从节点不知道价格；主节点入账后在确认里告诉它各项额度实际消耗了多少，从节点据此结算预扣、修正本地额度。
9. **异步回报**：扣费队列批量发给主节点，主节点正式入账（第 5 节）。
10. **失败重试**：上游返回错误或超时时，从节点**同步**发"上游错误决策"给主节点，带原始事实（状态码、关键响应头、错误分类、耗时、已输出字节数）。
    主节点用现有 `RateLimitService`（`CheckErrorPolicy`、`HandleUpstreamError`、`HandleStreamTimeout`）判定并落库（标限流、临时不可调度、记错误），返回"重试 / 换号 / 透传 / 失败"。
    要换号时重新选号（带已试过的账号）再重试。自动分组 Key 在分组内没号可换（选不出账号、换号用完）或遇到终止性上游错误时会换到下一个候选分组（本地 `openai_auto_group_failover.go` 的 `tryOpenAIAutoGroupFailover` → `ResolveAutoGroupForModelExcluding`），分组、计费模式、订阅随之变化。
    从节点照本地的换组分支走，选组这一步经主节点（`SwitchAutoGroup`，选组状态在主节点）：主节点在这类选号拒绝上标"可换组"，从节点先问换组，换成了就带新分组接着选号，没换成再按原来的拒绝写。本地"换号用完后换组"时的计费资格复查由主节点在换组时顺带做。主节点发现同一请求换了分组时，已排除的账号和选号状态从头来，计价上下文按新分组（与本地一致）。
    每次选号各有一张凭证，每次尝试各自结算；前一次已经产生的部分输出照现有规则计费。
    这一步不能做成异步事件：它决定这次请求接下来怎么走，从节点手里只有过期的账号状态，不能自己判定。只在出错时发生，不影响正常请求的延迟。
    主节点不可达时：不重试、不换号，按配置快照里的错误透传规则把错误返回客户端；原始事实作为账号事件排队，重连后主节点照常判定、标记账号。

并发槽的释放不等扣费批次：请求一结束就单独发一条释放消息，不等回复。

**选号为什么每个请求都问主节点**：并发槽、粘性会话、账号限流状态都是全局的。同地域部署时这次往返只有几毫秒。
以后如果要跨地域部署从节点，可以改成"把一批账号划给从节点、本地选号"，那是另一套设计，本次不做。

### 3.2 现有代码里每一步挪到哪里

网关中间件链（`internal/server/routes/gateway.go`，`/v1`、不带前缀的别名、`/v1beta`、`/backend-api/codex`、`/antigravity` 用的是同一串）：

| 现有中间件 | 做什么 | 新位置 |
|---|---|---|
| `bodyLimit`、`clientRequestID`、`endpointNorm` | 请求体上限、请求 ID、入口归一 | 从节点本地 |
| `opsErrorLogger` | 请求错误日志 | 从节点本地记完整内容，由从节点提供查询（第 12 节） |
| `blacklistIP`（`GlobalBlacklistIP`） | 全局 IP 黑名单，读不到时拒绝 | 从节点本地，黑名单作为配置下发（6 第二类）；没拿到配置不接请求 |
| `apiKeyAuth` | Key 鉴权、用户状态、Key 到期、IP 白名单、余额/额度预检 | 从节点本地（Key 缓存 + 本地额度）；缓存未命中问主节点 |
| `blacklistAccount`（`GlobalBlacklistAccount`） | 全局用户黑名单 | 主节点，选号时 |
| `autoGroupModelRouting` | 自动分组 Key 按模型现选分组，要查订阅；请求结束时把结果（状态码、首字耗时）交给选组器 | 主节点选：从节点在准入之后按模型问 `ResolveRoute`，主节点用本地同一个选组器选定分组，回 Key 快照和订阅；之后选号带着这个分组，主节点只核对。请求结束时从节点按本地同一段算法把结果报给主节点（`ReportAutoGroupResult`，后台发、不重试；交给主节点转发的不报） |
| `groupModelAllowlist` | 分组模型白名单 | 主节点，选号时 |
| `compositeTarget` | 组合平台分组按模型选目标平台 | 主节点选：从节点按模型问 `ResolveRoute`，拿到目标平台和上游模型后在本地改写请求体；选号时主节点按同一个公开模型再选一次。目标不是从节点已接入的平台时交给主节点转发 |
| `requireGroupAnthropic` | 未分配分组拒绝 | 主节点，选号时 |
| `typeSafeProtocolGuard` | TypeSafe 分组的 Key 只能用 `/v1/systemone`、`/v1/usage`、`/v1/models`，其余 404 | 主节点，选号时（看的是自动分组、组合平台解析之后的分组平台，从节点在选号前不知道） |

小白端转发接口（`routes/paw.go`）的 `jwtAuth` 换成中转票据验证（从节点本地）；`BackendModeUserGuard` 在主节点选号时执行；每个请求的内部 Key 解析（`ResolvePawGroupKey`）在主节点（8.1）。
`/paw/systemone` 单独挂的 `GroupModelAllowlist`、聊天 / Responses / Messages 里的 `pawRejectTypeSafeGroup`（TypeSafe 分组只能走 `/paw/systemone`）同样在主节点选号时执行。

处理函数内部，以 OpenAI Responses 为例（`internal/handler/openai_gateway_handler.go` 的 `Responses`），其他平台的处理函数结构相同：

| 现有位置 | 做什么 | 新位置 |
|---|---|---|
| 余额、订阅、配额检查 | 能否扣费 | 从节点本地（额度） |
| 内容审核（`runContentModeration`，`handler/content_moderation_helper.go`） | 转发前按配置审核请求文字，命中时拦截、记录、累计封号 | 见 3.4 |

Anthropic Messages（`internal/handler/gateway_handler.go` 的 `Messages`，Anthropic 分组）与 OpenAI 的分法相同，只有换号循环的位置不同：

- 主节点：中间件复查、渠道映射、用户并发槽、计费资格、计价时间、粘性会话预取（请求开始时一次），然后一轮"选号 → 预热拦截检查 → 抢槽或排队 → 利润终检 → 准入后粘性绑定"（`handler.AnthropicAccountAdmitter`，本地同一段代码）。
- 从节点：换号状态（已失败的账号、同账号重试、利润否决次数、选号耗尽后的退避、强制按缓存计费）留在处理函数的 `FailoverState` 里，与单机同一段代码。主节点把"利润否决""选号耗尽""预热拦截"作为拒绝回来，从节点转成本地的结果照原来的循环走；这几种拒绝之后主节点留着请求记录（用户槽、计价时间、粘性会话起点只算一次），请求结束时手里没有选号的由从节点按请求 ID 结束。
- 转发成功时释放消息带"转发成功"，主节点按本地同一条件刷新粘性会话绑定；转发路径上直接写账号仓储的临时不可调度作为账号事件由主节点照写（时长不超过本地用的最长时长）。
- 账号类型：OAuth / setup-token（指纹、access token 由主节点给，TLS 指纹模板走快照分段）、服务账号（Vertex，主节点换好的 token 随凭据下发）、Bedrock、混合调度进 Anthropic 分组的 Antigravity 账号（Google token 由主节点给；转发路径上写账号状态的几处——模型级 / 账号级限流、积分耗尽标记——作为账号事件交主节点照写，INTERNAL 500 渐进惩罚的计数和惩罚在主节点）。用户消息串行队列的锁和计数每一步经 `UserMsgQueue` 在主节点的 Redis 上执行，从节点照本地同一段排队代码（含排队期间的 SSE 保活）。
- Gemini 原生入口（`/v1beta` 的 POST，SDK / CLI 直连）、Antigravity 专用入口（`/antigravity/v1/messages`、`/antigravity/v1beta`）、Gemini / Antigravity 平台分组的 Messages 同样经从节点：换号状态留在从节点，会话（CLI / 通用会话哈希、粘性绑定、内容摘要会话匹配与保存）整段在主节点，从节点只带哈希和摘要链；Gemini OAuth / 服务账号的 token 由主节点换好下发；429 的账号级限流（含按档位的冷却）和清粘性绑定作为账号事件交主节点；强制 Antigravity 平台由主节点按路径定。Gemini 的准入、拒绝按 Google 格式（与本地 Google 鉴权链逐字节一致）。
- OpenAI 网关的其余文本入口同样经从节点：Embeddings、同步图片、`/v1/responses/input_tokens` 与 `/v1/messages/count_tokens`（不占槽、不计费）、Codex alpha search 与 Codex 直连路径；Anthropic / Gemini / Antigravity 平台分组的 `/v1/responses`、`/v1/chat/completions` 走 Messages 的选号与准入；Grok 与国产兼容平台分组的 Responses / Chat / Messages 按选定平台调度（只接 API Key 账号）。凭证允许的计费模型包含渠道映射后的模型。
- Antigravity 回 prompt 过长时本地换到分组配置的兜底分组重试：从节点经 `SwitchFallbackGroup` 让主节点解析兜底分组、做计费资格复查，之后的选号带兜底分组，主节点核对后按它选号和计费（渠道映射、渠道功能配置、粘性会话起点仍按原来的分组）。组合平台选到 Anthropic 目标、没有分组的 Key 也走这个入口。
- 强制按缓存计费（换号时有绑定的会话、或上游明确要求）是从节点得出的、影响价格的事实，与 token 数一样随扣费记录上报、照用。
- 选号结果带上分组所属渠道的功能配置（`FeaturesConfig`），转发路径上按分组查渠道的地方（联网搜索模拟"跟随渠道"、Bedrock CC 兼容、OpenAI 的 Codex 生图桥接）读它；JSON 往返后数字是 float64，现在读的都是布尔值。

### 3.3 联网搜索模拟

现有的联网搜索模拟（`service/gateway_websearch_emulation.go`，经 `websearch.Manager` 调外部搜索服务）需要搜索服务的 API Key，这些 Key 存在系统设置里（`service/websearch_config.go`）；各搜索服务的用量配额在 Redis 里计数（`websearch.Manager.tryReserveQuota`）。

- 主从模式下**搜索在从节点执行**（分工原则，第 1 节）：搜索配置（含服务 Key 和引用的代理）随配置快照加密下发（6 第二类），从节点用单机同一段代码调搜索服务，不经过主节点。
- **配额计数**是全局的，不能各节点各算各的：从节点在份额内本机计数，每 10 秒把新用的次数报给主节点（`ReportWebSearchUsage`，带幂等键），主节点加进单机同一个 Redis 计数（保留按订阅日重置），在回复里给每个有上限的服务的已用和这台的份额（剩余按在线节点分摊，还有剩余时至少 1）。份额用完就换下一个服务，与单机配额用完一样。节点之间报得不及时时可能略超配额，本次接受。还没拿到过份额时放行（与单机 Redis 不可用时一样）；报完之后搜索失败退回的，下次报成负数。
- "代理暂不可用"标记（单机在 Redis 里共享 5 分钟）在从节点上只记本机：各节点的网络各自不同。
- 主节点不可达时照常搜索（配置和密钥在本机），用量留着，重连后补报。
- 联网搜索模拟只在 Anthropic 网关服务上用（`GatewayService.Forward`）；账号设为"跟随渠道"时要看渠道配置，渠道在主节点，接 Anthropic 入口时随选号带下来（开发计划总账）。

### 3.4 内容审核与 cyber 策略

现有的安全审计在转发前执行（各网关处理函数经 `checkSecurityAudit` → `securityaudit.Coordinator`）：内容审核（`service/content_moderation.go` 的 `ContentModerationService.Check`，风控中心开关 `risk_control_enabled` 打开时生效）和提示词审计（`securityaudit.PromptService`，异步或阻断模式）。

**主从模式下判定在从节点做**（分工原则，第 1 节）：从节点装配单机同一个审计协调器，只把依赖换成从节点的实现，判定代码和单机同一份，请求延迟也和单机相同（关键词、只记录不拦截的模式不多等；`pre_block`、阻断模式只等外部审核接口，和单机一样）。

| 步骤 | 单机用到什么 | 主从模式下 |
|---|---|---|
| 审核配置（`content_moderation_config`，含审核接口 Key）、提示词审计配置（含接口凭据）、审核接口用的代理 | 数据库、`proxyRepo` | 随配置快照**加密下发**（6 第二类），只在从节点内存 |
| 关键词拦截 | 配置里的关键词表 | 从节点本地 |
| 命中过的输入哈希拦截 | Redis（`hashCache`） | 从节点查本机副本：主节点的 Redis 名单是权威，每台从节点连上时整份拉取、之后增量推送；从节点新命中的输入报给主节点写入，再推给其他节点；后台删除、清空同样推送到所有节点。副本还没拉到时按单机"哈希检查出错"处理（记警告、继续往下审） |
| 调外部审核接口（`pre_block` 同步、`observe` 异步） | 审核接口 Key | 从节点直接调 |
| 提示词审计（异步、阻断） | 提示词审计服务；配置里的接口凭据用主节点的密钥加密存；异步任务队列在 PG、待审内容在 Redis | 从节点直接调：主节点把解密后的生效配置和降级状态放进加密下发的部分（加密凭据的密钥不下发），配置变了当场推送；该开阻断却没有可用配置时与主节点一样拒绝放行（503）。异步任务队列和待审内容在从节点内存（容量同配置，重启时还没审完的丢掉；单机的队列在库里，重启后接着审），审计事件写本机 |
| 审核记录、提示词审计记录 | 数据库 | **留在从节点本机**（数据目录，重启不丢），按单机的保留期定时清理；后台按节点查询（后续加，第 12 节） |
| 累计违规次数、自动封号、命中通知邮件 | `repo.CountFlaggedByUserSince`、`userRepo.Update`、邮件服务 | **主节点**（授权）：从节点写一条计入封号的记录之前，同步报一次违规（`ModerationViolation`，控制连接，在审核的后台任务里、不在请求路径上；只带计数、封号、通知要用的字段，不含输入内容）。主节点记成一条最小的违规记录（带 `node_id`），用单机同一段代码累计窗口内次数、到阈值封号（触发 4.4 的"封禁即全部收回"），把次数和封号结果回给从节点写进本机记录；通知邮件另一次调用由主节点发（SMTP 不下发）。上报调不通时按单机"次数查不到"记第 1 次、不封号，后台用同一个幂等键重试 20 分钟（从节点重启会丢掉还没补上的） |

- **身份**：从节点用准入拿到的 Key 快照（用户、Key、分组），与单机用鉴权结果一样。违规事件会导致封号，主节点只认这台节点最近准入过的用户（按节点记最近 30 分钟准入过的用户），防止被攻破的节点随意封别人。
- **与单机的差异**：
  - 命中过的输入名单在节点间同步有秒级延迟（刚在别处命中的输入，这台可能晚一点才直接拦截，期间照常走外部审核）。
  - 违规计数在审核的后台任务里同步问主节点，时序与单机后台写记录、再判封号相近；上报失败时这一次按第 1 次记，后台补报。主节点重启后（准入记录和纪元都重置）还没补上的会丢掉。
  - `previous_response_id` 不属于这个用户的请求，单机在审计之前就拒，从节点要到选号时才拒（归属在主节点），所以会先审计一次。
  - 审计之后主节点回"暂不支持"而交给主节点转发的少数请求（准入之后 Key 所在分组变了等），主节点会再审计一次（多一次外部审核调用和记录）。


cyber 策略：
- **cyber 会话屏蔽**（`openai_cyber_session_block.go`，屏蔽表在 Redis，属于授权）：每个请求要查"这个会话是否已被屏蔽"。从节点把要查的键（已哈希）随选号请求上送，主节点选号时查，命中就拒绝选号。上游判定 cyber 后要写进屏蔽表的键由主节点从这次选号上送的查询键推导（单机也改用同一个推导），不信从节点另报的键。
- **cyber 命中**（`recordCyberPolicyIfMarked`）：屏蔽标记由从节点同步调 `CyberPolicyHit` 让主节点写（只等 500ms，与单机同步写屏蔽标记的上限一致；没发完的在后台发完，这次选号的释放等它）；风控记录、运维日志写在从节点本机；计入封号的命中同样发违规事件。转发失败时要写的 0 token 用量行走扣费队列（第 5 节），用这次选号的凭证，入账口径与单机 `RecordCyberPolicyUsageLog` 相同。

## 4. 额度

### 4.1 按维度分别锁定

现有的扣费资格检查有两种模式（`service/billing_cache_service.go:735`）：余额模式（`:879`）和订阅模式（`:900`）。订阅用户在订阅分组里用的是订阅窗口额度，余额可能是 0。
决定"能不能再花钱"的维度也各有归属：

| 维度 | 字段 | 归属 |
|---|---|---|
| 余额 | `users.balance` | 用户 |
| 订阅日/周/月窗口 | 用量 `user_subscriptions.daily/weekly/monthly_usage_usd`，上限 `groups.daily/weekly/monthly_limit_usd` | 用户 × 订阅分组（租约的 `scope_id` 记分组 ID，与订阅缓存、订阅作废同一个键） |
| 平台日/周/月配额 | `user_platform_quotas.*_limit_usd` | 用户 × 平台 |
| Key 总额度、5 小时/1 天/7 天限额 | `api_keys.quota`、`rate_limit_5h/1d/7d` | 单个 API Key（小白端记在它的内部 Key 上，8.1） |

分组的日/周/月上限只在订阅模式下、拿订阅用量来比（`checkSubscriptionEligibility`），余额模式不用，所以和订阅窗口是同一个维度；租约表里的 `group_*` 维度不使用。
上限没配置（为空）的窗口不限，不锁、不申请。余额这一项的剩余要先减去最低保留额（`billing.minimum_balance_reserve`），和单机的余额预检一致。
各项的"剩余"与单机的资格检查读同一份数据（余额缓存、订阅缓存、平台配额缓存、Key 限额缓存）、用同样的窗口重置规则。单机的 Key 限额检查在数据库出错时放行；锁定额度在主节点 PG / Redis 出错时一律不给（开发计划第 4 节）。

所以从节点上一个用户的额度是**一组子额度**，每项各自申请、收回，都遵守 4.2 的规则。一个请求放行前，它会用到的每一项子额度都要够。

订阅和 API Key 都有到期时间（`user_subscriptions.expires_at`、`api_keys.expires_at`）。对应子额度的有效期不能超过到期时间。

用户 RPM、并发数（`users.rpm_limit`、`users.concurrency`）不锁给从节点，在主节点选号时执行。

### 4.2 锁定规则

以下数值都按系统内部的余额数值计（费用按美元单价算，充值时按后台充值倍率 `BalanceRechargeMultiplier` 换算进来），不做货币换算，均可在后台调整。

- **每次给一半**：从节点申请时，主节点给出"未锁定额度的一半"。未锁定额度 = 该项的剩余 − 已锁在所有从节点上的部分。
- **最小锁定单位 0.05**：未锁定额度小于 0.1 时，全部给出。
- **每台上限 5**：一台从节点为同一用户持有的、还没用掉的锁定金额，任何时候不超过 5。
  每次给出的金额 = min（未锁定额度的一半，5 − 这台上还没用掉的部分）。
  "这台上还没用掉的部分"由从节点在申请时上报（主节点只知道租约里还锁着、未入账的总额，其中含已用未回报的部分）；虚报会在异常检测里发现（12、13 节）。
- **至少够这次请求**：一半不够这次请求的最低预估时，给到够为止（仍不超过未锁定额度和每台上限），否则未锁定额度明明够也会被拒。单个请求的预估超过每台上限 5 时申请不到。
- **一次申请全有或全无**：一个请求用到的各项子额度都够才一起给，有一项不够就一项都不给，不为要被拒绝的请求锁钱。
- **提前补充**：本机剩余低于 30% 时，下一次选号顺带补充，不另发消息。
- **申请不到就拒绝**：先收回这个用户在其他从节点上 5 分钟没用的额度，再计算。
  仍然不够、且该项的剩余低于 1 时，直接收回其他从节点上这个用户未使用的部分（不等闲置），再计算。
  只在剩余低于 1 时这样做，是为了避免两台同时活跃的节点反复互相收回。
  仍然不够这次请求的最低预估，就拒绝，返回余额不足（OpenAI / Anthropic 格式）。
- **租约 10 分钟**，节点在线时自动续期；节点失联时，到期后主节点单方面收回。从节点在"到期时间 − 30 秒 − 测得的时钟偏差"时就停止使用这份额度，保证主节点收回时它已经不再用。
- **重启核对**：从节点重启后内存里的额度没了，重连时上报"没有这些租约"，主节点立即释放；主节点重启后（纪元变化，7.4），从节点上报手里的租约，由主节点按库里的记录核对，以主节点为准。

例：用户可用 100，只在一台上用。这台每次最多持有 5，用掉约 3.5 时补回到 5。余额低于 10 后，一半小于 5，就按一半给；最后不足 0.1 时全部给出。

### 4.3 冻结怎么记

- `balance` 始终是用户的真实余额，**只在真正扣费时减少**。
- 新增一列 `relay_reserved_balance`，记录锁在所有从节点上的总额；明细和其他维度的预留记在租约表。
  不和批量图片已有的 `frozen_balance` 共用。
- 锁定：`relay_reserved_balance` 加。扣费：`balance` 减实际费用，`relay_reserved_balance` 同步减。收回：只减 `relay_reserved_balance`。
- 参照批量图片已有的冻结做法（`repository/usage_billing_repo.go:437-524`）：冻结要有记录，释放前核对确实冻结过，结算幂等。

**只有"能不能花钱"的判断改成看 `balance - relay_reserved_balance`**，统一调用同一个"可花余额"函数：

| 位置 | 做什么 |
|---|---|
| `service/billing_cache_service.go:883` `checkBalanceEligibility`（阈值判断在 `:874` `balanceBelowEligibilityThreshold`） | 网关请求前的余额预检（含主节点自己转发时）；余额从 `GetUserBalance` 读，走余额缓存 |
| `server/middleware/api_key_auth.go:182`、`:267`，`api_key_auth_google.go:203`（都调 `apiKeyBalanceBelowAuthThreshold`，`api_key_auth.go:434`） | API Key 鉴权时余额耗尽拒绝；余额取自 Key 鉴权缓存里的 `apiKey.User.Balance` |
| `service/gateway_usage_billing.go:461` | 扣费后按新余额判断是否作废余额缓存 |
| `repository/usage_billing_repo.go:447`（`reserveUsageBillingBatchImageBalance`） | 批量图片冻结时的余额条件 |
| `service/payment_refund.go:166`、`:279` | 退款时余额是否足够 |

前两处读的是缓存里的余额，做法：
- **鉴权层不动**：`apiKeyBalanceBelowAuthThreshold` 只拦余额 ≤ 0，继续看 `balance`，Key 鉴权缓存不变。余额为正、但全被锁在从节点上的用户能过鉴权层，由下一步预检拦下。
- **预检减去冻结额**：余额缓存（`GetUserBalance`，现在只有预检在读，扣费时 `QueueDeductBalance` 直接减它）保持存真实余额；冻结额由主节点的额度服务放在内存里（主节点只有一个进程，锁定、收回、入账都经过它），挂到 `BillingCacheService` 上；`checkBalanceEligibility` 用"余额 − 冻结额"判断。主从分流关闭时不挂，预检不做任何额外读取。
  不把余额缓存直接改成可花余额：从节点的记录入账时余额和冻结额同时减、可花余额不变，现有的"扣费即减缓存"就错了。
- **扣费后的缓存处理不改**（`gateway_usage_billing.go` 的 `syncBalanceCacheAfterDeduction`）：它按新余额决定作废余额缓存还是直接减缓存，缓存里存的是真实余额，看真实余额是对的；冻结额在预检时才减。
- 退款的余额判断和"可用余额扣减"（`DeductAvailableBalance`）、批量图片冻结的余额条件都改成看"余额 − 冻结额"，锁在从节点上的钱不能退、不能挪去冻结。
余额显示、低余额提醒、用户接口、管理后台的代码不用改。主节点入账时同步更新余额缓存。

### 4.4 收回

| 事件 | 处理 |
|---|---|
| 某台上这个用户 5 分钟没有请求 | 收回这台上未使用的额度 |
| 节点失联 | 租约到期后主节点单方面收回 |
| 管理员减余额、退款 | 未锁定部分够就直接执行；不够时先从从节点收回 |
| 主节点上要花这个用户的钱（主节点转发、批量图片等） | 先用未锁定部分，不够再收回 |
| 封禁、停用、改密码、强制下线 | 立即全部收回，所有从节点停止放行该用户 |
| 修改用户所属分组、配额，删除或停用 Key | 立即全部收回，下次请求重新申请 |
| 修改倍率、价格 | 不收回：额度与倍率无关，入账时按当时的倍率计价（第 6 节） |
| 用量窗口重置 | 不处理，下次申请按新窗口计算 |

收回是一次同步调用：从节点从未使用的部分里扣出来还给主节点，进行中请求需要的部分保留，结束后再退。
选号时的收回（申请不到时）等回复，两轮共用 1.5 秒；事件触发的收回（上表）只发不等，回复到了就入账。只发给在线节点，离线节点上的等租约到期。
事件来源：订阅改动收回这个用户这个分组的订阅额度；分组改动收回所有用户这个分组的订阅额度；平台配额改动收回这个用户的平台配额额度；用户被停用、删除时收回全部；充值、兑换等普通用户改动不收回。
改密码、强制下线没有业务层事件：选号复查会拒绝改密码后的票据，这些租约闲置 5 分钟后被收回。Key 删除、停用的收回随 WP11（需要 Key ID）。

**锁在离线节点上的额度**收不回来，**默认等租约到期**（最长 10 分钟）由主节点自动收回。
- 管理员减余额、设余额、退款时如果需要这部分：先从在线节点同步收回（最多等 3 秒），仍不够就返回 409（`RELAY_BALANCE_LOCKED`，带锁着的金额 `locked_amount` 和最晚放回时间 `release_by`），不排队自动续做；管理员可以等到那个时间再操作，或者"立即回收"（2026-09-26 定）。
- **管理员主动回收**：在从节点管理页（按节点，回收这台所有用户的额度）或用户管理页（按用户，回收这个用户在所有离线节点上的额度）点"立即回收"，二次验证、记审计。被回收的租约当场作废，视为已收回，等待中的管理员操作随即继续。
- 那台节点恢复后：被作废的租约不能再用，它上报的剩余额度按作废处理；如果补报了离线期间已经发生的用量，照常扣（5.4），余额可能变成负数，每个用户每台不超过 5。

### 4.5 超支的上限

- 请求开始前预扣最低预估（按请求体大小估输入）。
- 进行中的请求不中途切断（上游已经在计费，切断也省不了钱），超出预估的部分从 `balance` 扣并记录。
- 所以超支上限是"每个进行中的请求超出它自己预估的部分"。超出后必须补充额度成功，才放行下一个请求。

## 5. 扣费

### 5.1 从节点本地队列

- 本地持久化队列（分段追加文件，每条带校验，批量落盘，细节见开发计划 3.1）。每条记录：扣费凭证、转发结果（实际模型、全部计费维度的原始用量、耗时、上游关键响应头、响应 ID 等），以及**入账输入里由转发节点得出的字段**（清单由字段守卫维护，见开发计划 2.2）。
  现有处理函数构造 `RecordUsageInput` / `OpenAIRecordUsageInput` 等入账输入时，有一批字段是在接请求的那台机器上算出来的：入站端点、上游端点、User-Agent、客户端 IP、客户端会话 ID、请求体哈希（`RequestPayloadHash`，参与扣费去重，5.2）、强制缓存计费、请求的推理强度等。
  它们要随记录上报，否则主节点入账写出的 `usage_log` 和去重结果会和单机不同。完整清单由开发计划 2.2 的脚本扫描所有入账输入的构造点生成，不在这里手写。
- 不存凭据，不存请求内容（请求体哈希不算请求内容）。
- 每 1~2 秒或攒够 100 条发一批，主节点确认后才删除，断线、重启后接着发。批次带连续序号，主节点能发现漏掉或重复的批次。
- 一条记录处理失败（比如格式错误）时单独隔离并报警，不堵后面的记录。
- 本地写不进去（磁盘满、损坏），或长时间收不到确认、积压超过上限时，从节点停止接收新请求。

### 5.2 主节点入账：必须走现有扣费函数

现有扣费函数（`service/gateway_usage_billing.go` 的 `postUsageBilling` / `applyUsageBilling`）除了写 `usage_log`、扣余额，还会：

| 行 | 做什么 |
|---|---|
| `:145` | 订阅用户累加订阅用量，不扣余额 |
| `:151` | 余额用户扣余额 |
| `:175` | 累加上游账号的已用额度 |
| `:191` | 累加平台配额，处理窗口重置 |
| `:277`、`:586`、`:593` | 用别人贡献的账号时给贡献者返利；用自己贡献的账号时收自用费 |
| `:375`、`:410` | 更新账号最近使用时间 |
| `:400`、`:407` | 更新订阅用量缓存、API Key 限额用量缓存 |
| `:462`、`:472` | 同步余额缓存 |
| `:503` | 低余额邮件提醒 |
| `:544` | 账号额度提醒 |

主节点处理扣费批次时**逐条调用这套函数**，只把"用量从哪里来"换成从节点上报的记录。不能另写一个简化版，否则返利、账号额度、订阅用量会悄悄不再发生。
这套函数除了入参，还从请求上下文里读选号时定下的值（见 5.3 的选号上下文）。主节点入账前先把凭证里的选号上下文恢复进上下文，再调用。
`usage_log.account_source`（号池 / 自有账号 / 贡献房间，`UsageLogAccountSourceFor`）由账号和用户现算，不用额外上报。
验证方式：同一批请求分别在单机和主从模式下跑，比较所有受影响的表，逐字段相同才算通过。

其他要求：
- 验证扣费凭证的签名，**每张凭证只入账一次**。扣费请求 ID 沿用现有规则（`:206` `resolveUsageBillingRequestID`、`:238`、`:251` 的 Grok 音频和实时会话固定 ID、`:262` 请求内容指纹），不用从节点自己生成的 ID。
- **按主节点入账时的配置计价，与单机一致**：单机本来就是请求结束后异步入账、读当时的倍率和价格，只有计价时间 `pricingAt`（峰谷因子按它算）在请求开始时定下，它随选号上下文带到入账。金额全由主节点计算，从节点不算价；确认里带着各项额度实际消耗了多少，从节点据此修正剩余额度。
- 用量窗口（订阅日 / 周 / 月、平台配额、Key 限额）按入账时间计入，与单机一致。从节点离线很久后补报的记录按补报时的价格和窗口。
- 入账在现有扣费事务里同时认领凭证、按实扣金额消耗这台节点为这个用户锁的额度租约，并同步减 `relay_reserved_balance`（4.3）；已入账过的凭证原样返回当时的消耗。
- 每条记录在一个事务里完成（凭证去重和扣费同事务）；一批里的记录全部处理完（成功入账或已隔离）才回确认。

### 5.3 扣费凭证

主节点在每次选号时签发一张带签名的凭证：选号 ID、用户、Key、账号、分组、计费模式、请求模型、**允许的计费模型范围**、签发时间、**选号上下文**。不带报价：入账按主节点当时的配置计价（5.2）。

**选号上下文**：现有扣费函数从请求上下文里读、在选号时由主节点定下的值，入账时必须原样恢复：
- 计价时间 `pricingAt`（`openai_profit_control.go` 的 `WithOpenAIRequestPricingContext`、`gateway_request_pricing.go`）和计费分组；
- 组合平台的目标平台、上游模型、对外公开模型、路由来源（`composite_platform.go` 的 `Resolved*FromContext`），以及 `ForcePlatform`；
- 分组兜底池的使用记录（源分组、目标分组，`fallback_pool.go` 的 `applyFallbackPoolUsageTrace`，写进 `usage_log` 的 `fallback_*` 列）；
- 贡献房间路由选出的贡献者（`contribution_room_routing.go`）；
- 渠道映射结果（`ChannelUsageFields`）、配额计量平台（`QuotaPlatform`）。

清单同样以开发计划 2.2 的脚本为准：凡是扣费函数、`usage_log` 构造从上下文读、且由选号决定的值，都进选号上下文。

- 从节点上报的每条记录必须带凭证，验签通过才入账，凭空编造的记录验不过。
- 现有代码会按上游实际返回的模型计费（`:727` `responseModelBillingAdoptable`）。凭证允许的范围是请求模型、渠道映射后的模型和账号映射后的上游模型；转发里还有 compact 映射、Codex 归一、上游拒绝后的回退模型等合法情况，所以上报的模型不在范围内时**照上报的计费**（改价会让正常请求和单机算得不一样），报警并把这张凭证记为待复核。
- 签发过的凭证不逐条落库（每请求一条太重），主节点按节点、按分钟统计"签发数 / 入账数"；进行中的选号 ID 由心跳上报核对。选号成功但一直没有扣费记录的比例异常就报警（发现少报的手段之一）。

### 5.4 迟到、丢失和吊销

| 情况 | 处理 |
|---|---|
| 迟到的记录（从节点离线后恢复补报） | 签发 60 天内照常扣，余额可能变成负数，用户充值前不能继续使用。迟到记录只可能来自当时锁给这台的额度，所以负数每个用户每台节点不超过 5 左右 |
| 丢失的记录（整机损毁、本地队列没了） | 不扣，服务端承担。心跳里的"各用户累计已用"只用来估算丢失金额，不用来扣费。按节点记审计，同一台反复丢数据要报警 |
| 正常下线 | 必须先排空、队列清空、额度全部退回，才能删除 |
| 强制删除（机器已不在） | 队列里没报上来的按丢失处理 |
| 因怀疑被攻破而吊销 | 吊销前签发的凭证照常入账，但全部标记"待复核"，后台列出，管理员可按用户整笔退回；吊销后签发不出新凭证 |

凭证的"已入账"记录保留 90 天。**签发超过 60 天的凭证不再入账**，按丢失处理（不扣，记节点审计），保证去重记录一定比可入账的凭证保留得久，不会重复扣费。所以"迟到照常扣"的期限是 60 天。

## 6. 倍率、价格、配置的实时同步

**一、影响计价的倍率和价格：入账时按主节点的配置计算**

包括：账号倍率（`accounts.rate_multiplier`）、分组倍率和峰时倍率（`groups.rate_multiplier`、`peak_rate_multiplier`）、图片/视频倍率、分组模型价格（`groups.model_pricing`）、按次计费项（网络搜索等）、用户专属分组倍率、贡献房间倍率（`contribution_rooms.consumer_rate_multiplier`）、全局模型价格表。

- 与单机一致：入账时按主节点当时的倍率和价格计算。单机也是请求结束后异步入账，读的是入账那一刻的配置；只有计价时间 `pricingAt`（`service/openai_profit_control.go:164`，峰谷因子按它算）在请求开始时冻结，它随扣费凭证的选号上下文带到入账。
- 峰谷倍率按主节点的时间算。失败换号时计价时间沿用这次请求开始时的（与单机相同）。
- 从节点不保存价格表和倍率，也不计算金额。
- 从节点离线很久后才补报的记录按补报时的配置计价。

**二、转发用的配置：推送 + 版本栅栏**

包括：快速模式策略、首字超时模式、TLS 指纹、错误透传规则、Codex 指令模板、模型映射、全局 IP 黑名单、内容审核与提示词审计配置（3.4）、联网搜索配置（3.3）、API Key 节点规则等。

- 后台一改，主节点立即推送给所有在线从节点。
- 选号返回里带当前配置版本号，从节点版本落后时先同步拉取再转发。所以改动提交后，不会有任何新请求按旧配置转发。
- 全局 IP 黑名单在选号之前检查，靠推送生效；从节点失联时不接请求（下面第三类），所以不会用过期的黑名单放行。
- 从节点没拿到配置之前不接请求。只推数据，不推可执行内容。
- **按白名单下发**：从节点用的系统设置是主节点按白名单挑出来的，只含转发需要的项。系统设置表里存着管理员 API Key（`SettingKeyAdminAPIKey`）、SMTP 密码、各家 OAuth 和验证码的密钥等与转发无关的密钥，这些一律不下发。白名单之外的设置项在从节点上读到的是空值；新增设置项默认不下发，要下发必须显式加进白名单，并在代码评审时确认不是密钥。普通白名单里的值照旧检查：设置名和 JSON 值里的字段名像密钥的，不下发并报错。
- **转发功能要用的密钥加密下发**（2026-09-29 定，分工原则）：审核配置（`content_moderation_config`，里面有审核接口的 `api_key` / `api_keys`）、提示词审计配置（含接口凭据）、联网搜索配置（含服务 Key），以及这些配置引用的代理（含代理密码），单独列成一张"加密下发"清单。快照里这部分按节点用它的加密公钥封好（与上游凭据同一套，7.1 第 4 条），从节点解开后只放在内存，不写盘、不打日志。清单同样显式维护，新增项要在代码评审时确认确实是转发要用的。从节点被吊销或怀疑被攻破时，要到主节点更换这些 Key（管理页提示）。
- **从节点换快照时清掉设置缓存**：`SettingService` 自己带进程内缓存，包括 `setting_value_cache.go`（每个请求都要读的设置，5 秒过期）和各功能的原子缓存（如 `cyberSessionBlockRuntimeCache`）。从节点收到新快照后要先清掉这些缓存再放行请求，否则版本栅栏形同虚设，最多 5 秒按旧配置转发。
  主节点上，配置推送挂在现有"写入时作废缓存"的同一批位置上；绕开服务直接改库（备份恢复、手工 SQL）的，靠主节点定时比对快照指纹补推。

**三、从节点缓存的用户状态：改动即作废**

包括：API Key 的哈希缓存（对应的用户、分组、限额、IP 白名单、分配节点）、票据、额度、小白端内部 Key 的解析结果。

- 用户、Key、分组、订阅、配额、Key 分配节点的任何修改，主节点立即推送作废通知，并按 4.4 收回额度。
- 新建 Key 时，主节点推送这个 Key 的哈希，从节点清掉对应的"查不到"缓存（8.2）。
- 从节点失联期间收不到通知，但也拿不到选号，不会转发请求；重连后先比对配置版本，再恢复服务。

## 7. 主从通信

从节点主动连主节点，保持几条长连接，同一条连接上并发多个请求（gRPC 双向流或 WebSocket 加请求 ID）。

### 7.1 加密

1. **所有主从通信都走 TLS 1.3**，包括注册、待激活期间的心跳、证书续签、证书过期后的恢复。主节点这个端口只提供 TLS，不开明文端口，没有降级成明文的退路。
2. **加密必须在主节点程序本身终止**。不能在前面放负责解密的反向代理、负载均衡或 CDN，内网也不行；需要转发端口时只能用不解密的 TCP 转发。这也是双向认证成立的前提。
3. 只允许强加密套件，关闭旧版本 TLS 和弱算法；证书密钥用 ECDSA P-256 或 Ed25519。
4. **上游凭据和下发的密钥再加一层加密**：选号返回里的上游凭据、配置快照里加密下发的那部分密钥（第 6 节），再用这台从节点的**加密公钥**单独加密（X25519 密钥交换 + AEAD）。签名用的证书密钥（Ed25519 / ECDSA）不能直接用来加密，所以从节点另有一对加密密钥，每次续签证书时一起更换，公钥随续签请求上报（换了之后快照按新公钥重新封）。即使中间被人放了会解密的代理，凭据和密钥也不会以明文出现。
5. 日志不记录主从消息原文，只记类型、大小、耗时。

其他链路：

| 链路 | 要求 |
|---|---|
| 客户端 → 从节点 | 只接受 HTTPS。从节点不开 HTTP 端口，也不做 HTTP 跳转 HTTPS（跳转前第一个请求已经把 API Key 明文发出去了） |
| 从节点 → 上游 | HTTPS（现有行为） |
| 从节点 ↔ 对象存储 | HTTPS，临时地址只签发 `https` 的 |
| 主节点 → 飞书 | HTTPS |
| 小白端：Codex → 本机 LocalPawRelay | 只监听 127.0.0.1，不出本机 |

### 7.2 认证

- **双向 TLS**：主节点也要向从节点证明身份，否则伪造的主节点能给所有从节点下指令。
- 从节点核对主节点身份用的是**主从通信专用根证书**的指纹，不是主节点网站证书的指纹（网站证书每两三个月续期一次，会让所有从节点连不上）。
- 主节点对所有从节点接口都要求：证书有效、未吊销，且节点处于"已激活"（第 11 节）。
- 没有正式证书的连接（注册）按来源 IP 限流。

**证书被偷的防护**：
1. **短期证书，续签换密钥**：证书 24 小时有效，在线时自动续签；每次续签从节点生成新密钥，用旧证书证明身份。新证书第一次被使用时（最晚续签后 60 秒），旧证书就不能再建新连接，已有的连接最多再保留 60 秒，由主节点关闭，从节点换到新证书的连接上。偷到的密钥最多用到这台节点下一次续签。
   - **续签回复丢失**：从节点在发出请求前把新密钥落盘，重试、甚至重启后都用同一把新密钥重发；主节点见到同一张旧证书带着同一把新公钥，原样返回上次签发的证书，不当作异常。
   - 续签一直失败（或旧证书已失效）时，从节点改用长期密钥重新领证（第 4 条）。
2. **同一身份出现两份 → 立即断开这台节点的所有连接，吊销证书，退回"待激活"**，发严重告警。包括：
   - 同一张证书同时从两个不同 IP 连着（见第 3 条的判定）；
   - 同一张旧证书带着**两把不同的新公钥**续签。
3. **节点换 IP**（前后不同时）只告警，不阻断，兼容动态 IP 和换服务器。
   换出口时主节点上可能还挂着旧地址的半开连接（要等保活超时才断），所以新地址连进来、旧地址的连接还在时，主节点按"换了出口"处理：断开旧地址的连接、告警、放行。
   之后 10 分钟内，旧地址在新地址还连着的时候又用同一张证书连回来，才判定为两份身份（第 2 条）。证书被偷到别处使用时，原节点被挤掉后马上重连，正好触发这一条。
   出口来回频繁切换的节点，用下面的"关闭同时两个 IP 判断"。
4. **证书过期后的恢复**：主节点长时间不可用导致证书过期时，从节点用注册时的长期密钥重新证明身份，节点仍是已激活就直接续签，记审计并通知。长期密钥只用于这种恢复。

从节点连接主节点时固定只用一个出口（比如只走 IPv4），否则多出口会被第 2 条误判。确实需要多出口的节点，后台可以对这台单独关闭"同时两个 IP"的判断；"同一张旧证书带两把不同的新公钥续签"的判断始终保留。
注册、心跳、领证这些不带签发证书的调用按来源 IP 限流（不按密钥指纹：换一把密钥不能换来一份新额度）。

### 7.4 其他要求

- **主节点按节点限流**：每台的额度申请、选号、上游错误决策、账号事件、违规事件、扣费批次、Key 查询、查询接口转交都有速率上限，一台出问题不能拖垮主节点。
- **协议版本**：消息格式带版本号，主节点拒绝过旧版本；升级时先升主节点（新旧格式都支持），再逐台升级从节点。
- **时钟同步**：所有节点开时间同步，票据和凭证的有效期检查允许少量偏差。心跳测量从节点与主节点的时钟偏差，超过 30 秒时从节点拒绝服务并告警。
- **主节点纪元**：主节点每次启动生成一个纪元 ID，握手时下发。从节点发现纪元变化时，清空 Key 缓存、凭据缓存、票据吊销表，重新拉配置，上报租约供核对（4.2）。
- **幂等**：所有会改状态的调用（选号、额度申请、收回确认、扣费批次、账号事件、释放）都带幂等键，从节点超时或重连后重发不会重复生效。幂等键绑定纪元，主节点重启后从节点不重发旧键，重新发起。
- **主节点过载**：主节点对某个调用回"稍后重试"时，从节点给客户端返回 503（OpenAI / Anthropic 格式，带 `Retry-After`），不在从节点排队。
- **主节点的关键私钥**：主从通信根证书、签中转票据、签扣费凭证三把私钥。
  - 加密保存，解密密钥放在主节点环境变量或单独文件里，**不进数据库**。现有备份功能会把数据库备份到对象存储，私钥在库里就会跟着进备份。
  - 私钥单独离线备份。主节点重装时丢了根证书私钥，所有从节点都要重新注册、激活。
  - 轮换时新旧公钥并存一段时间，从节点都拿到新公钥后再停用旧的。
  - 主从通信根证书分三步轮换（管理页操作，二次验证、记审计）：
    1. **预备**：生成新根证书，它的指纹随配置快照下发给所有从节点，还不用于签发；同时只能有一个预备版本，预备版本随时可以放弃。
    2. **启用**：所有在服务（已激活、排空中）的节点都拉到过含新指纹的配置后才允许，否则拒绝并列出还没拿到的节点（离线的在服务节点也算，它回来时要认得新根签的主节点证书）。启用后主节点证书和之后的节点证书改由新根签发。
    3. **停用旧根**：新根签发满 25 小时才允许（节点证书 24 小时有效，这时旧根签的节点证书都已过期）。
  - 签中转票据、签扣费凭证的私钥也按同样三步轮换（管理页按用途操作）：票据公钥和根指纹一样随配置快照下发，启用新版本前要求所有在服务节点都已拿到，新版本签满"票据有效期 + 时钟偏差"（约 11 分钟）后可停用旧版本；凭证公钥不下发，启用不等送达，旧版本要等新版本签满 61 天（旧凭证都已超过 60 天入账期限）才能停用。
  - 主节点把全部未停用的根证书指纹（含预备中的）放进配置快照，以及注册、状态查询、领证和续签的回复里。从节点收到后用它**整份替换**本机存下的指纹列表并落盘（停用的旧根随之去掉），实际信任的是"本机配置的指纹 ∪ 存下来的指纹"，所以管理员在本机手改配置始终有效。
    待激活、已停用的节点一直按心跳查询状态，预备期间在线就能拿到新指纹；预备期间关机的，新根启用后要在本机改填新指纹才能再连上。

## 8. 用户凭据与从节点开放的接口

### 8.1 中转票据（只给小白端）

- 主节点用私钥签名（比如 Ed25519），从节点只有公钥，能验证但造不出票据。
- 内容：用户 ID、分配的从节点 ID、签发时用户的 `token_version`（由邮箱和密码哈希推导，与登录态同一个值）、签发时间、有效期（默认 10 分钟）。随分配结果一起下发，换节点时重新签发，跟随约 60 秒的定期询问续签。
- **以主节点选号时的复查为准**：票据替代的是小白端现在的登录态（`jwtAuth`），所以登录态在哪些情况下被拒，票据也要被拒。主节点每次选号按登录态中间件的同一套规则复查：用户存在、状态为启用、`token_version` 与当前一致。封禁、删除、改密码、改邮箱后，旧票据在下一个请求就被拒；主节点重启也不会让它们复活，不需要持久化的吊销表。
  "强制下线"现在只撤销 refresh token、不影响已签发的登录态，票据与之一致（最长 10 分钟）。
- **从节点的吊销表只用来提前拒绝**（不用选号的请求、省一次往返）：用户在某时刻及之前签发的票据作废，条目保留到"吊销时刻 + 票据有效期 + 时钟偏差"。来源两个：主节点得知用户被停用或删除时推送（事件流连上时整份发一次）；选号被主节点以"票据已吊销"拒绝时，从节点自己记下。只在内存，纪元变化时清空。
  拿到票据不能去主节点改密码、支付，也不能在别的节点上用。
- 只在请求开始时检查有效期，进行中的长回复不因票据到期中断。
- **内部 Key**：小白端现在带 JWT 访问 `/api/v1/paw/*`，服务端每个请求用 `ResolvePawGroupKey`（`service/paw_chat_service.go:60`）找到用户的内部 Key 和分组，找不到时 `EnsurePlaygroundAPIKeys` 当场创建（写数据库）。
  主从模式下这一步在主节点做：从节点首次为这个用户（和分组）申请额度时，主节点解析，必要时创建，把内部 Key ID 随额度返回；从节点按（用户, 分组）缓存。
  内部 Key 被删除、重建时主节点推送作废。4.1 的 Key 维度额度记在内部 Key 上。
- 内部 Key 不导出，不走 10.2 的节点分配和规则；它只能通过票据在分配给这个用户的从节点上使用。

**实现状态（v0.23）**：`/api/v1/paw/{files,chat/completions,responses,messages,messages/count_tokens,images/generations,images/edits,systemone}` 已在从节点上提供。
- 票据在从节点本地验（签名、有效期、签给本节点、吊销表，错误码与 `jwtAuth` 一致）；之后每个请求发 `PawResolve`：主节点用同一个票据验证器再验一次，复查用户（存在、启用、`token_version`——与 `GetByIDForAuth` 同一个值）和后台模式（管理员放行），再跑本地 /paw 同一段服务代码（`PawChatService.PrepareSelection / PrepareResponses / PrepareMessages`、`PawImageService.ValidateGeneration`，聊天的"校验"和"拼请求体"拆开了：校验在主节点，请求体带附件内容在从节点用本机附件服务拼）、TypeSafe 分组拒绝和组合平台选目标，回**会话句柄**。错误体用本地同样的两种写法（`{"error":{"code","message"}}`；`/paw/messages` 是 Anthropic 形状）。
- **内部 key 的原文不离开主节点**：从节点拿到的是 key 快照（不含原文）和一个不透明的句柄，选号、换组（`SwitchAutoGroup`、`SwitchFallbackGroup`）等调用都用句柄代替 API Key 原文放进凭据字段；主节点在 `admitAPIKey` 里认句柄：句柄存在且签给调用的这台节点、没过期（30 分钟，只为覆盖一次请求里的重试），**每次使用都复查用户**（启用、`token_version`）——所以改密码后哪怕从节点还没收到吊销，下一次选号也被拒。句柄只存在主节点内存里（重启作废，进行中的请求最多在下一次选号时失败）。
- 不跑 API Key 的鉴权链（IP 白名单、全局黑名单、自动分组、分组模型白名单）：本地 /paw 本来就不过那条链（只有 `/paw/systemone` 单独挂分组白名单，从节点同样挂）。
- 面板限流（`panelRateLimiter`，记在 Redis）不在从节点做：转发请求的并发由主节点选号时的用户并发槽限制。`/paw/files` 只在从节点本地（附件在内存，不查主节点，所以改密码后到票据过期前仍能上传——不影响用上游额度）。`/paw/config`、`/paw/auto-group`、`PUT /paw/config/defaults` 仍只在主节点（登录态）。

### 8.2 API Key

- **认证**：从节点第一次见到某个 Key 时，经加密长连接把 Key 原文发给主节点查询（现有 `api_keys.key` 存的是原文，按原文唯一索引查找）。
  主节点返回用户、分组、限额、IP 白名单、到期时间、**分配的从节点**（10.2），以及现有鉴权中间件按 Key 算出、后面要用的标记（如工作台本地回退 Key：名字形如 `共飞工作台-*-客户端`，`api_key_auth.go:424` 起，换号上限提到 64，`handler/workspace_fallback.go`）；从节点只在内存里缓存"Key 的哈希 → 以上信息"，不存原文、不写盘。
- **节点规则**（从节点通用配置，10.2）：为"仅分配的从节点"时，其他从节点拒绝这个 Key，返回 403（OpenAI / Anthropic 格式），提示"此 Key 只能通过分配给它的地址使用"。为"全部从节点"时，任何已激活的从节点都接受。主节点是否接受取决于主节点分配比例（10.5）。
- Key 被删除、停用或改分配节点时主节点推送作废。
- **防止随机 Key 攻击压垮主节点**：先检查 Key 格式；查不到的 Key 缓存 30 秒；同一来源 IP 鉴权失败过多时暂时拒绝。
  新建 Key 时主节点推送这个 Key 的哈希，从节点清掉对应的"查不到"缓存，避免用户刚建的 Key 马上用却被拒。
**实现状态（v0.24）**：
- **节点规则**在主节点准入时执行（`api_key_node_rule`：assigned / any；Key 的 `relay_node_id`：0=主节点、空=没分配），因为准入本来就在主节点，用调用的节点 ID 比对；认证快照带 `relay_node_id`，缓存命中时规则同样生效。
- **负缓存**（`nodegw/keycache.go`）：主节点回"查不到这个 Key"（401，`invalid_api_key`）时，从节点按（Key 的 SHA-256，是否 Google 入口）记 30 秒，期间本地原样写同一个拒绝；新建 Key 的作废推送清掉对应条目；事件流重连、主节点纪元变化时整个清空；上限 5 万条。
- **没有做"查到了"的正缓存**（与上面"缓存哈希 → 信息"的写法不同）：这里的准入是主节点上整条鉴权链的一次评估（IP 黑名单、Key 状态、余额与订阅额度、自动分组解析、节点规则），这些随时在变，选号时主节点还会再查一遍；缓存快照只会让从节点多放行一些马上被选号拒绝的请求，省下的只是一次往返。需要时再按"短 TTL + 用户/分组/Key 作废推送"加。
- **无效鉴权防刷**：从节点内存里用与单机同一个限流器（`api_key_auth_cache.invalid_abuse`：每个来源 IP 窗口内失败次数、封禁时长）；取不到 Key、负缓存命中、主节点回"查不到"都算一次失败；超限时本地回 429 `INVALID_AUTH_RATE_LIMITED`（Google 入口写 Google 格式）并带 `Retry-After`，不再调用主节点。
- 客户端 IP 由从节点按 TCP 连接确定（从节点前面没有代理，不信任转发头），API Key 的 IP 白名单在从节点本地执行。桌面客户端已豁免会话绑定（`service/client_source.go:87`）。

## 9. 上游账号

| 账号类型 | 从节点拿到什么 |
|---|---|
| OAuth 账号 | 只给短期 access token；refresh token 不离开主节点，刷新在主节点（`token_refresh_service`） |
| 静态 API Key 账号 | Key 本身，长期有效 |
| 服务账号（如 Vertex） | 主节点生成短期 token 下发，不下发服务账号文件 |

### 9.1 凭据在从节点上的缓存与授权

**凭据是账号级的，对整台从节点通用**：从节点按（账号, 凭据版本）在内存里缓存上游凭据，这台上的所有用户共用同一份。同一个账号只在第一次用到、或主节点换了版本时下发一次，不按用户、不按请求重复下发和解密。

**但缓存里有凭据不等于能用**，授权每个请求单独做：
- 从节点只在拿到**这个请求**的选号结果、且结果里指定了这个账号时，才从缓存取这个账号的凭据。从节点不自己挑账号，不因为"缓存里正好有"就用某个账号。
- 用户能不能用这个账号，由主节点选号时按现有调度规则判断：分组、平台、账号状态、"仅主节点"开关，以及贡献账号的归属规则（自己贡献的账号、所在贡献房间的账号、号池）。选号结果和扣费凭证都写明（用户, Key, 账号, 选号 ID），入账时主节点再核对凭证里的账号与记录一致。
- 用户失去某个账号的使用权（离开贡献房间、账号被移出分组、账号被停用）后，主节点下一次选号就不会再给他这个账号；缓存里的凭据还在，但没有选号结果就用不上，不需要为此清缓存。账号被删除、停用或凭据被吊销时，主节点推送作废，从节点清掉这个账号的凭据。
- 换号重试时同样要先拿到新的选号结果，才能用新账号的凭据。

其他：
- 上游返回 401 时，从节点回报，主节点刷新，下次选号带新凭据版本。
- 凭据只在内存，不写盘，不打日志，收到吊销立即清除。
- **"仅主节点使用"开关**：每个上游账号可单独设置，后台可按账号类型批量设置（比如所有静态 API Key 账号）。从节点来选号时跳过这些账号。
  分组里的账号全部是"仅主节点"时，该分组的小白端用户只能分配到主节点，API Key 分配主节点地址（10.2），流量占主节点带宽；后台要能看到有多少用户和 Key 因此落在主节点上。
  主节点分配比例为 0 时，"仅主节点"账号不会被任何请求用到，这些分组的用户无法使用（10.8）。
- 同一个账号可能同时被多台从节点使用。没有绑定代理的账号会从多个 IP 发出请求，可能触发上游风控，建议账号都绑定代理。
- **用户贡献的账号和代理只能连公网**：现有转发对贡献账号限制上游只能是公网地址，对用户自有代理限制只能用公网代理（`http_upstream_profile.go` 的 `WithHTTPUpstreamPublicHostsOnlyForAccount`，拨号检查在 `repository/http_upstream_public.go`），防止用户借账号地址访问服务器内网。
  从节点一般在云上，内网里有云厂商的元数据接口等敏感地址，这条限制在从节点上必须照样生效：选号返回的账号快照要带账号的贡献者、代理的归属用户，从节点的上游客户端沿用同一套公网检查。

## 10. 分配与路由

### 10.1 小白端

- 登录时、定期询问时（约 60 秒一次）、当前节点连不上时，客户端调分配查询接口（10.9），主节点返回分配的地址（从节点或主节点）和中转票据。一般地址不变，只有负载调整、节点下线或管理员手动调整时才换。
- 同一用户多台设备登录，都分到同一台。
- 客户端分**控制地址**（主节点现有域名：登录、刷新、仪表盘、切组、问分配、手机同步会话的长连接）和**转发地址**（分到从节点时是从节点域名，带中转票据；分到主节点时是主节点域名，沿用现有登录态）。
- 只改本机 LocalPawRelay 的上游地址，不动 Codex 的 `config.toml`（"运行中的 Codex 会不会重读配置"未验证，端口固定可以绕开；也不影响会话与 provider 的绑定）。
- 新地址只对下一个请求生效，正在输出的回复在原节点跑完。换节点不用转移额度：新节点自己申请，旧节点的额度闲置后收回。

**负载指标用带宽**：心跳上报网卡实测收发速率（包括 API Key 用户的流量）；带宽上限由管理员填写；负载 = 近 1 分钟速率 / 上限，上下行取较大值。超过 85% 不再分配新用户。新用户先按主从分配比例决定是否分到主节点（10.8），分到从节点的按剩余容量加权随机分配（不是每次挑最空的，避免心跳延迟期间大家挤到同一台），并把最近几秒刚分到的人数计入预估。

### 10.2 API Key 用户

API Key 用户直接访问从节点，由从节点向主节点认证（8.2）。没有公共轮询域名。

**生成时分配**：
- 每个 Key 生成时，后台为它分配一台节点，Key 上记的是**节点 ID**（主节点也是一个节点），不是域名。先按主从分配比例决定是否分给主节点（10.8）；分给从节点时，只从"已激活"且未排空、未停用、负载未超 85% 的节点里选。
- 生成时还不知道这个 Key 会有多少流量，所以按带宽上限加权随机，并把每台已分配且近 7 天有请求的 Key 数计入。
- Key 能用的分组里全部是"仅主节点"账号时（第 9 节），分配主节点；主节点分配比例为 0 时照样分配主节点，但这个 Key 用不了，Key 页面提示"当前分组暂不可用"。

**导出和推荐**：Key 页面的"使用 Key"、端点提示、CC Switch 等导出配置，给出的地址是按 Key 的分配节点现取的**这台在管理页填写的域名**，不再用全局的 `api_base_url`；分配主节点的 Key 给出主节点现有域名。
管理员修改某台的域名时，分到它的 Key 导出地址随之变化，已配置好的客户端要改地址，所以修改前提示影响的 Key 数；一般不改域名，换机器时由管理员把域名解析改到新机器（11.6）。

**节点规则**：从节点管理页的**通用配置**里的一项，对所有从节点生效，只有管理员能改，用户看不到也改不了：
- **仅分配的从节点**（默认）：只有分配的那台接受，其他从节点拒绝（8.2）。
- **全部从节点**：任何已激活的从节点都接受；导出仍给分配的地址。
- 两种规则下，主节点域名是否接受只看主节点分配比例（10.5）。
- 规则随配置推送、按版本栅栏生效（第 6 节第二类）。从"全部"改成"仅分配"后，Key 在其他节点上的额度闲置后按 4.4 收回。

**重新分配**：
- 管理员可以逐个或按节点批量把 Key 移到另一台（比如某台长期压力过高）。
- 重新分配会改变导出给出的地址，已经配置好的客户端不会自动变，用户要重新导出或手动改地址。规则为"仅分配的从节点"时，旧地址在用户改过来之前会被拒绝，所以批量移动前要提示影响的 Key 数。
- Key 页面标出"地址已变更"，提醒用户更新。
- 删除从节点时，分到它的 Key 自动重新分配并同样提示；也可以保留这个域名，由管理员把解析改到新机器（11.6）。

**节点故障时**：系统告警并列出受影响的活跃 Key，不自动改解析。管理员可以手动把这台的域名解析改到主节点（10.3），用户不用改地址；主节点分配比例为 0 时不能这样做，这台的 API Key 用户在节点恢复或管理员重新分配前不可用。

每台从节点用自己域名的 HTTPS 证书，由从节点自己申请（11.1、15.2）。

**实现状态（v0.25，WP11）**，对应上面各条的测试在括号里：
- **生成时分配**（`master/key_assign.go`，`service/api_key_relay.go`）：`APIKeyService.Create` 在写库前问分配器要节点，写进 `relay_node_id`；分配失败不影响建 Key（保持未分配，哪台都接）；开关关闭时没有分配器；Playground 内部 Key（`SkipRelayAssignment`）不分配（8.1）。先按比例掷骰子决定给不给主节点；给从节点时，候选是"已激活、有域名、事件流在线、负载没超阈值"的节点（排空、停用、待激活、没填域名、不在线的都不分），按权重**带宽上限 ÷ (1 + 这台上近 7 天用过的 Key 数)** 加权随机（带宽没填按 100；Key 数统计缓存 30 秒，期间新分配的即时计入）。没有负载合格的从节点时：比例大于 0 给主节点，否则给负载最低的从节点；一台都没有且比例为 0 时不分配。负载由心跳上报，那部分属于 WP13/WP14，现在按 0。（`TestKeyAssignerPicksByRatioAndEligibility`、`…NeverPicksMasterAtRatioZero`、`…WeightsByBandwidthAndActiveKeys`、`…RespectsLoadThreshold`、`TestAPIKeyCreateAssignsRelayNode`）
- **重新分配**：管理接口 `POST /admin/relay/api-keys/move`（指定 Key）、`POST /admin/relay/nodes/:id/move-keys`（按节点批量；不指定目标时每把按分配规则重选、不选原节点，选不出的留在原节点并计数）、`GET /admin/relay/api-keys/assignment`（各节点上的 Key 数，改比例、停用节点前看影响）。目标必须能接收（节点已激活有域名；主节点比例为 0 时不能给主节点）；记"分配改变时间"；**每把 Key 的鉴权缓存作废并推给从节点**，所以节点规则马上换边，不用等缓存过期。（`TestRuntimeMovesKeysBetweenNodes`、`…RefusesMasterTargetAtRatioZero`、`…MovesAllKeysOfANode`、`TestReassignedKeyMovesBetweenNodesImmediately`）
- **上线时给存量 Key 分配**（10.7 第 1 步）：`POST /admin/relay/api-keys/assign-unassigned`，按同一规则；第一次分配不记"分配改变时间"。（`TestRuntimeAssignsUnassignedKeysWithoutMarkingChange`）
- **导出地址**：Key 列表带 `relay_node_id`、`relay_base_url`（从节点是 `https://<域名>`，主节点是 `api_base_url`，没配置时为空，前端用当前站点地址）、`relay_address_changed_at`（Key 页面据此提示"地址已变更"）；地址按节点现取（10 秒缓存，节点操作时清）。（`TestRuntimeResolvesNodeAddresses`）节点规则的 403 提示里带分配的地址。（`TestNodeRuleRejectionNamesTheAssignedAddress`）
- **换机器**（11.6）：`POST /admin/relay/nodes/:id/replace`（新节点 ID + 它的指纹）：先核对（指纹、新节点待激活、旧节点有域名——在停用旧节点之前），在用的旧节点先停用（额度作废放回），再在一个事务里清掉旧节点的域名、激活新节点（域名、名称、带宽、区域沿用），最后把分到旧节点的 Key 全转给新节点（域名不变，不记地址已变更）。内存和 SQL 存储跑同一套契约用例。（`TestRuntimeReplacesANodeKeepingDomainAndKeys`、契约用例 `replace node moves the domain to the new machine`）
- **"删除从节点"**：系统里没有删除节点的操作，只有拒绝、停用、吊销（退回待激活），这几个都不自动移走 Key（可能只是维护）。要下线一台时管理员先用 `move-keys` 把它的 Key 移走（接口先给出影响数量）。
- **有意推迟**：①"Key 能用的分组里全是'仅主节点'账号时分配主节点"——要在建 Key 时查分组和账号，自动分组 Key 的候选分组还会变，先不做（这样的 Key 会按普通规则分到从节点，用不了仅主节点账号时由请求时的选号决定）；②改比例到 0 时"保存前列出影响、确认后批量重新分配"只提供了数量接口，保存本身不拦（前端 WP16 做确认）。

### 10.3 健康判断

心跳只能证明"从节点到主节点"是通的。从节点对外端口被挡、HTTPS 证书过期、域名解析错、连不上上游时，心跳照样正常。所以还要：

1. **外部探测**：主节点每分钟从公网探测每台从节点的对外地址，连续失败就标为"对外不可达"，停止分配（小白端用户、新 Key）并告警。
   探测直接连这台机器的 IP、按它的域名做 TLS 握手（SNI），不走域名解析，所以域名被改到主节点时仍然探测的是这台机器本身。
2. **客户端失败报告**：小白端连不上分配的节点、向主节点要新分配时，报告连不上哪台。同一台短时间内被很多用户报告，停止分配并告警。
3. **错误率降级**：某台错误率明显高于其他节点（比如连不上上游），自动停止分配并告警，恢复后自动恢复。
4. **证书到期**：从节点对外 HTTPS 证书剩 7 天到期时告警。

以上状态影响小白端的分配和新 Key 的分配；已分配到这台的 API Key 不移走。

**域名由管理员手动管理**（暂不接域名服务商接口，系统不改解析）：
- 管理员在域名服务商处给每台从节点的域名加解析，指向这台的 IP，再在管理页填写域名。建议解析 TTL 设 60 秒，手动切换时生效更快。
- 主节点每分钟解析一次各从节点域名，管理页显示"当前解析到：这台 / 主节点 / 其他地址"；和预期不符（比如解析错了、被人改了）时告警。
- **故障时**：告警里带受影响的活跃 Key 数。管理员可以选择：
  - 等节点恢复；
  - 在域名服务商处把这台的域名解析改到主节点的 IP（主节点分配比例须大于 0），恢复后再改回；
  - 把这台的 Key 批量重新分配到别的节点（用户要改地址，10.2）。
- **主节点接从节点域名**：解析改到主节点后，主节点前面的 Caddy 按需为这个域名申请证书（on_demand TLS）。申请前 Caddy 先问主节点"这是不是已登记的从节点域名"（这个查询接口只监听本机，不对外），不是就拒绝，防止被人拿任意域名刷证书。
  用从节点域名打到主节点的请求，按 Host 只开放 API Key 网关接口（8.3 的 API Key 一行），走 10.5 的主节点转发，计入转发上限，不受节点规则限制；主节点分配比例为 0 时拒绝；票据接口、网页、后台一律 404。
- 小白端不需要这套：它连不上时向主节点要新分配（10.1）。

### 10.4 排空与手动调整

- **排空**：不再分配新用户和新 Key，小白端下次询问时换走 → 进行中的请求结束、本地扣费队列清空、额度全部退回 → 停机。
  WebSocket 和实时会话可能一直不结束，排空最长等 30 分钟，到时主动断开剩余连接。
- **排空不会自动改解析**，停机期间分到这台的 API Key 用户不可用。管理页排空前提示受影响的活跃 Key 数。需要不中断时，管理员先在域名服务商处把解析改到主节点（主节点分配比例须大于 0），等 TTL 过去（建议 5 分钟，有些客户端缓存解析更久）再排空，升级完改回。
- **手动移动或固定用户**：管理员可以把某个小白端用户移到指定节点，或暂时固定在某台上（固定必须设到期时间，到期恢复自动分配）。移动只对下一个请求生效。
  固定的节点离线或对外不可达时，自动解除固定并通知管理员。操作要二次验证并记审计。

### 10.5 主节点转发

**主节点分配比例为 0 时，主节点不转发任何请求**，下面几种情况都不发生：API Key 请求打到主节点返回 403（OpenAI / Anthropic 格式），提示"请改用 <这个 Key 分配的地址>"；小白端不会分到主节点；从节点域名即使被改到主节点也会被拒绝。

分配比例大于 0 时，主节点在这些情况下转发请求：

- **按比例分到主节点的小白端用户和 Key**（10.8）。
- **API Key 请求打到主节点**：照常处理，不管节点规则。包括主节点现有域名（旧地址 10.7、分组只有"仅主节点"账号的 Key、用户手动改用），以及管理员手动改到主节点的从节点域名（10.3）。
- **从节点全部不可用时的小白端**：由主节点判断。客户端连不上自己的从节点时，向主节点要新分配。还有可用的从节点就分到别的从节点；一台可用的都没有（全部离线、对外不可达、排空或停用）时，主节点才把自己分出去。
  分配比例为 0 时不分给主节点，分配查询接口返回"暂无可用中转"（10.9），服务中断，发紧急通知。
  "可用但压力都很高"不算不可用，仍分配到从节点。

规则：
- 主节点上的转发走本机完整流程，直接读写数据库扣费，不走额度锁定。余额检查看可花余额；用户额度锁在从节点上不够用时，按 4.4 先从从节点收回。
- **主节点转发设上限**（带宽、并发请求数，后台可调），超过上限返回"服务繁忙"（OpenAI / Anthropic 格式）。登录、计费、从节点通信优先，不受这个上限影响。网页聊天和游客试用也算进这个上限（它们同样在转发上游流量）；手机同步会话不算（消息小、连接长，算进去超限时会把手机连接断掉）。否则控制功能被挤垮，从节点恢复后也连不上主节点；也防止有人打挂从节点把流量逼到主节点。
- **恢复**：有从节点重新可用后，小白端下次定期询问时分回从节点；管理员把手动改到主节点的从节点域名改回（10.3），API Key 用户不用操作。

**实现状态（v0.25，WP11）**：主节点分配比例为 0 时的闸门是一个挂在整个 HTTP 引擎上的中间件（`middleware.RelayMasterGateMiddleware`），只在主从分流在运行且比例为 0 时生效，只对 API Key 的**转发路由**生效——按路由模板（`c.FullPath()`）和一张**正面清单**判断（`IsRelayForwardingRoute`：messages、responses、chat/completions、图片生成与编辑、视频、语音、embeddings、alpha search、systemone、web/x search、Seedance 任务、live、Gemini 原生的 `POST /models/*`，各前缀和根路径别名），模型列表、用量、余额、批量图片、图片任务查询、分配查询等不是转发的接口（8.4）和网页、后台都不在清单里，不认识的路由一律放行。被拒时回 403（`master_relay_disabled`，OpenAI / Anthropic / Google 格式），提示这把 Key 分配的地址。**从节点交给主节点转发的请求要放行**，所以交过来的请求带从节点自己签的标记 `X-Sub2api-Relay-Handoff`：主节点进程内随机生成一把密钥，经加密下发的配置分段（`handoff`）给各从节点；标记 = HMAC(密钥, 节点 ID、时间、方法、路径)，5 分钟有效；主节点验签并确认签发的节点还在服务（激活或排空）才放行；从节点转交时先去掉客户端自己带的同名头，再带自己的。主节点重启换新密钥，节点随配置版本重新拉取。（`TestIsRelayForwardingRoute`、`TestRelayMasterGateBlocksDirectForwardingAtRatioZero`、`TestRuntimeGateBlocksMasterForwardingAtRatioZero`、`TestHandOffCarriesTheNodesOwnMarker`）

**实现状态（v0.27，WP12）**：
- **用户分配**（`master/user_assign.go`、`user_assign_store.go`，表 `relay_user_assignments`）：新用户先按主节点分配比例掷骰子（主节点负载也受阈值约束），其余按**剩余容量加权随机**——权重 = 带宽上限 × (1 − 负载)，至少留 2%；负载是心跳的近 1 分钟速率比，再加上最近 10 秒刚分到这台的人数 × 1%；超过 85% 的不再分。已分配的保持不动，直到：原节点不可用（离线、排空、停用、被客户端报告暂停、疑似少报）、客户端 POST 报告连不上它、比例改成 0（分到主节点的移走）、管理员移动或重新平衡。从节点都不可用时：比例大于 0 临时分给主节点（原因 `fallback`，从节点恢复后下次询问分回去）；比例为 0 返回 `ErrRelayUnavailable`（接口回 503 `RELAY_UNAVAILABLE`）；"可用但压力都很高"仍分给从节点（挑负载最低的），不分给主节点。
- **票据**：分到从节点时用 `Runtime.IssueTicket` 签发，`token_version` 取用户当前的 `service.ResolvedTokenVersion`（与登录态同一个值）；`refresh_after` 取通用配置（默认 60 秒）且不超过票据有效期的一半。
- **接口** `GET/POST /api/v1/paw/relay/assignment`（登录态、`/paw` 组；只在主节点，不在从节点开放）：返回 `role`、`node_id`、`base_url`（主节点没配置 `api_base_url` 时用当前请求的主机）、`ticket`、`ticket_expires_at`、`refresh_after`；POST 带 `unreachable_node_id`；主从分流没开时 404 `RELAY_NOT_ENABLED`（客户端沿用现在的地址）。限流用 `/paw` 组已有的面板限流。
- **客户端失败报告**（10.3 第 2 条）：同一台被 5 个不同用户在 2 分钟内报告连不上，暂停分配 5 分钟并发 `node_unreachable_reports`；暂停期间这台不接新用户。
- **管理操作**：`GET /admin/relay/users/assignment`（各节点的用户数）、`POST /admin/relay/users/rebalance`（删掉没固定的分配，下次询问重新分）、`POST /admin/relay/users/:id/move`、`/pin`（必须设到期时间，最长 30 天；节点必须现在能接用户）、`/unpin`；固定的节点不可用时自动解除固定并发 `user_pin_released`。都记审计、要二次验证。
- **主节点转发上限**（10.5）：通用配置 `master_max_concurrent`（同时转发的请求数）和 `master_max_bandwidth_mbps`（带宽，取主节点网卡近 1 分钟速率），0 为不限；全局中间件对"API Key 转发路由 + 小白端转发接口 + 网页聊天 + 游客试用"占名额，超限回 503 `server_busy`（OpenAI / Anthropic / Google 格式，`Retry-After: 5`），**从节点交来的请求同样计入**，手机同步会话和其他登录态接口不算；主节点负载 = 并发占比和带宽占比较大者，分配时用它判断主节点是否过载。
- 测试：`TestAssignUser*`（比例、票据、加权、失败转移与 fallback、比例 0、客户端报告）、`TestPinMoveAndRebalanceUsers`、`TestMasterForwardingCap`、`TestPawRelayAssignmentEndpoint`。**没做**：分配结果的"从节点域名当前解析到主节点"相关处理（WP13）。

### 10.6 主节点不可用时

选号要问主节点，所以主节点挂了，新请求全部停止，返回 OpenAI / Anthropic 格式的错误。
主节点自己的规则：Postgres 或 Redis 任一不可用时，不锁新额度、不选号。

### 10.7 上线迁移

现有域名继续给主节点用；现有 API Key 用户要改地址。

1. 上线时为所有现有 Key 批量分配从节点（按 10.2 的分配方式）。
2. Key 页面和导出配置改成给出分配的地址，页面提示老用户更新地址。
3. 旧地址（主节点域名）继续可用，照常处理，但流量走主节点带宽，计入主节点转发上限。**迁移期间主节点分配比例必须大于 0**，否则旧地址的请求会被拒绝（10.5）；比例本身可以很小，它只影响新分配。
   迁移期间主节点转发上限要按实际旧地址流量设置，否则老用户会被"服务繁忙"拒绝；随着用户迁走逐步下调。
4. 后台列出"仍在用主节点地址的 Key 和用户"，按流量排序，方便逐个提醒。基本迁完后再把比例调到 0（如果想让主节点完全不做中转）。
5. 小白端：控制地址就是现有域名，升级客户端后自动按 10.1 分配，不用用户操作。

### 10.8 主从分配比例

从节点管理页通用配置里设置**主节点分配比例**（0~100%，只有管理员能改，二次验证、记审计）：

- **含义**：新分配（小白端用户、新生成的 Key）中分给主节点的比例；其余分给从节点，从节点之间按 10.1 的剩余容量加权。
  比如 10%：大约每 10 个新用户或新 Key 有 1 个分到主节点。
- 主节点也受 85% 负载阈值约束，负载按主节点转发量 / 主节点转发上限计算；超过阈值时这次分配改给从节点。
- 所有从节点都不可用时，比例大于 0 就全部分给主节点（10.5），不再按比例。
- **调整比例只影响新的分配**，已分配的不动。要让现有小白端用户按新比例分布，管理员在管理页执行"重新平衡"，小白端下一次询问时生效。Key 不自动重新平衡，因为要用户改地址。

**比例为 0：主节点不做任何中转。**

| 影响 | 处理 |
|---|---|
| 新分配 | 全部分给从节点 |
| 已分到主节点的小白端用户 | 下一次询问时移到从节点 |
| 已分到主节点的 Key | 保存时提示受影响的 Key 数，管理员确认后批量重新分配到从节点；用户要改地址（10.2 重新分配） |
| API Key 打到主节点域名 | 返回 403，提示这个 Key 分配的地址（10.5） |
| 从节点故障、排空 | 不能把域名改到主节点（改了也会被拒绝）；这台的 API Key 用户不可用（10.3、10.4） |
| 从节点全部不可用 | 服务中断，发紧急通知（10.5） |
| "仅主节点"账号和只有这类账号的分组 | 不会被用到，这些分组的用户无法使用（第 9 节）；保存时提示受影响的分组、用户和 Key 数 |
| 迁移期间用旧地址的用户 | 被拒绝，所以迁移完成前不要设为 0（10.7） |
| 网页 playground、网页聊天、游客试用、手机同步会话、只在主节点提供的接口（批量图片等） | **不受影响**：它们是主节点自己的功能，不属于分配（不变量 1）。需要关闭时用这些功能各自现有的开关 |

改成 0 之前，管理页先列出上面各项的受影响数量，确认后才保存。

### 10.9 分配查询接口

客户端向主节点查询自己分到的中转地址。只在主节点提供，不经过从节点（API Key 版本除外）。

**小白端**（登录态，主节点现有域名，归入 8.3 的"只在主节点"）：

```
GET  /api/v1/paw/relay/assignment
POST /api/v1/paw/relay/assignment        body: {"unreachable_node_id": 12}
```

- GET：返回当前分配。登录后、每隔 `refresh_after` 秒、以及切组后调用。
- POST：连不上分配的节点时调用，带上连不上的节点 ID（10.3 的客户端失败报告），返回新的分配。
- 两个接口按用户限流。

返回：

| 字段 | 说明 |
|---|---|
| `role` | `relay`（从节点）或 `master`（主节点） |
| `node_id` | 分配的节点 ID；主节点为 0 |
| `base_url` | 转发地址，`https://<域名>`。`relay` 时是从节点域名；`master` 时是主节点现有域名 |
| `ticket`、`ticket_expires_at` | 中转票据（8.1），只在 `role=relay` 时有；`master` 时沿用现有登录态访问 `/api/v1/paw/*` |
| `refresh_after` | 建议多少秒后再查，默认 60 |

- 没有可用中转时（从节点全部不可用且主节点分配比例为 0）返回 503，错误码 `RELAY_UNAVAILABLE`。客户端显示"服务暂不可用"，按 `refresh_after` 继续查询。
- 不返回其他节点的地址、负载等信息。
- 客户端只把 `base_url` 设成本机 LocalPawRelay 的上游地址（10.1），切换只对下一个请求生效。

**API Key**（给第三方工具自动获取地址用）：

```
GET /v1/relay/assignment        Authorization: Bearer <API Key>
```

- 返回这个 Key 的 `role`、`node_id`、`base_url`（主节点时为主节点现有域名），不返回票据。
- 主节点域名和所有从节点都可以访问；从节点转交主节点执行（8.4）。这是查询不是转发，主节点分配比例为 0 时也可用。
- Key 被重新分配后，工具可以用它发现新地址。

**实现状态（v0.25，WP11）**：`GET /v1/relay/assignment` 已实现（API Key 版本），返回 `role`（`relay` / `master` / `unassigned`）、`node_id`、`base_url`；主节点没配置 `api_base_url` 时用当前请求的主机；分配的节点已经没有地址时回 503。注册在 `/v1` 组里 `/sub2api/billing` 旁（同一条鉴权链，不受转发闸门影响）；从节点按 8.4 交给主节点。（`TestRelayAssignmentReturnsTheAssignedAddress`、`TestNonForwardingEndpointsAreHandedOffUnchanged`）小白端版本（`/api/v1/paw/relay/assignment`）属于 WP12。

## 11. 从节点注册、激活与管理

### 11.1 注册

从节点本机只需要两样东西：**主节点地址、主从通信根证书指纹**（可选再填一个显示名称）。这两样在后台从节点管理页上提供。其余配置全部由主节点下发，本地不能改。

1. 从节点第一次启动时在本机生成长期密钥（私钥不离开本机），在控制台和日志里打印公钥指纹。
2. 连接主节点，先核对根证书指纹，对不上就拒绝连接。
3. 发送注册信息：公钥、主机名、程序版本、系统信息、显示名称。
4. 主节点记录下来，节点出现在管理页的"待激活"里，同时记录注册来源 IP。
5. 管理员核对后激活，填写或确认名称、**对外域名**（必填，API Key 导出地址就取它，10.2）、带宽上限、地域标签。
   激活前主节点检查这个域名当前解析到这台的注册 IP（不一致时提示，管理员可确认继续）。
   主节点这时才签发主从通信证书、下发完整配置。
   从节点收到域名后，自己用 ACME（TLS-ALPN-01，走 443 端口，不需要域名服务商密钥）向 Let's Encrypt 申请这个域名的 HTTPS 证书并自动续期；证书私钥只在这台从节点上，主节点不持有。申请不到时，管理员可以在从节点本机放置证书文件。
   外部探测握手成功后才开始分配用户和新 Key。
6. 之后重启时用同一把长期密钥连接，被认作同一台，不用重新激活。

任何人都能向主节点注册（没激活什么都做不了），所以要防刷：
- 注册接口按来源 IP 限流；
- 待激活节点最多 20 台，满了拒绝新注册；
- 待激活 24 小时未激活自动清除；
- 注册信息限制大小，主节点不对它做耗时处理；
- 管理页可以一键拒绝所有待激活节点。

### 11.2 激活

**待激活的节点**：只能发心跳；不分配用户和 Key；不能申请额度、选号、上报扣费、查询 Key；只拿到心跳所需的最少参数；收到任何客户端请求一律拒绝。

**激活页面显示**：注册时间、注册来源 IP、主机名、程序版本、系统信息、**公钥指纹**。

**管理员必须把从节点本机控制台上的指纹和页面上的指纹对一下，一致才激活。** 名称、主机名、IP 都能被模仿，指纹是区分"自己部署的机器"和"别人注册上来的机器"的唯一可靠依据。

- 激活要二次验证，记审计（谁、什么时候、核对的指纹）。
- **拒绝**：这把公钥被拉黑，同一台机器要换密钥重新注册。
- **需要重新激活的情况**：从节点重装、长期密钥变了（重新注册）；同一身份出现两份（7.2）自动退回待激活；管理员停用后再启用。
  重新注册的是一台新节点，原节点的域名和分到它的 Key 由管理员转给新节点（11.6）。

### 11.3 主节点下发的配置

| 类别 | 内容 |
|---|---|
| 节点身份 | 节点 ID、名称、地域标签、证书 |
| 对外服务 | 对外域名、监听端口（HTTPS 证书由从节点自己申请，11.1） |
| 容量 | 带宽上限、最大连接数、最大并发请求数、分配权重 |
| 行为参数 | 心跳间隔、额度规则、本地队列上限、日志级别和采样、Key 负缓存时间 |
| 转发配置 | 第 6 节第二类配置 |
| 公钥 | 验中转票据用的公钥（含轮换中的新版本）。扣费凭证只在主节点入账时验，公钥不下发 |
| 状态 | 待激活、已激活、排空、停用 |

**通用配置**（管理页上的一组全局设置，对所有从节点生效）：主节点分配比例（10.8）、API Key 节点规则（10.2）、额度规则默认值、心跳和离线判定、排空等待时间等（第 19 节的参数）。单台的配置未单独设置的项沿用通用配置。

- 除"状态"和心跳所需参数外，其余只在激活后下发。
- 配置带版本号，修改后立即推送（第 6 节）。
- 配置里不含数据库、Redis、对象存储凭据，也不含主节点的任何私钥。

### 11.4 心跳

每 5 秒一次，连续 15 秒收不到就标为**离线**：不再分配新用户和新 Key，额度等租约到期后收回，发离线通知。

心跳内容：版本号、配置版本号、启动时间；网卡实时收发速率；客户端连接数（包括流式响应、WebSocket）；进行中的请求数和选号 ID；活跃人数和活跃 Key 数；本机锁定额度总额、各用户累计已用；本地扣费队列积压条数、最早一条的时间；日志发送积压和丢弃条数；近 1 分钟请求数、错误数；CPU、内存、磁盘剩余。

**实现状态（v0.26，WP14）**：`RelayControl.Heartbeat`（`master/heartbeat.go`、`node/heartbeat.go`、`nodegw/stats.go`）。
- 内容按上面的清单（另带 `usage_records_enqueued_total`、按（级别, 组件）和（错误类型, 状态码）汇总的条数；"日志发送积压和丢弃"指本机写盘队列的积压和丢弃，日志本身不外发）。网卡速率取 gopsutil 的累计字节差，CPU / 内存 / 磁盘同；"客户端连接数"数 HTTP 连接（被升级成 WebSocket 的不再算）；"活跃用户 / Key"是近 5 分钟鉴权通过过的。
- **在线判定**：主节点按心跳（不是事件流）判定，15 秒（通用配置 `offline_after_seconds`）没收到标离线并发 `node_offline`，恢复发 `node_online`（事件交给 WP15 的通知器）。新 Key 分配的"在线"也看它。停用 / 吊销的节点忘掉心跳状态，不算掉线。
- **负载** = 近 1 分钟收发速率较大者 ÷ 带宽上限（没填带宽上限时为 0），新 Key 分配用它（10.2）。小白端分配（WP12）同用。
- **时钟偏差**：从节点用心跳往返的中点测（没扣单向延迟）；额度租约停用时间点按它再提前（原来按 0）；超过 30 秒从节点本机拒绝服务（503），主节点发 `node_clock_skew`。
- **分钟汇总**写进 `relay_node_minute_metrics`（同一分钟覆盖写；`vouchers_issued / vouchers_consumed` 列实际存的是"节点写进本地扣费队列的条数 / 主节点入账的条数"）。
- **长请求的占用续期**：心跳带进行中的选号 ID，主节点据此重算对应请求的占用时间（长流不会因超过 15 分钟被当成泄漏放掉）。
- **扣费记录对账**：宽限期（10 分钟）之前节点已写进本地队列的记录，到现在"主节点入账数 + 节点自己说还在队列里的"仍少于它报的写入数，差额达到 20 条就发 `node_voucher_shortfall`，并且**这台不再被选号、不再发额度**（`Control.Select` 返回 Unavailable）直到差额消失。这是丢失 / 卡死检测，不是防作弊（节点撒谎时这条查不出）。
- **异常检测**：近 1 分钟选号次数超过 12 × 节点自己报的请求数 + 300（刷选号）发 `node_select_flood`；近 10 分钟有 10 次选号到定时清理才被放掉（选号后不上报）发 `node_selections_unreleased`；每种持续期间只告警一次。
- 管理接口 `GET /admin/relay/nodes/health`：各在服务节点的最近一次心跳、在线、负载百分比、时钟偏差、对账差额。
- **没做**：独立对账（主节点按上游查用量、与节点上报的总量比对）——各平台的用量查询接口不统一，先不做，记在总账；外部探测（WP13）。

### 11.5 管理页

**列表**，每台一行：

| 列 | 说明 |
|---|---|
| 名称、地域、对外域名 | 域名当前解析到：这台 / 主节点 / 其他地址（不符合预期时标红） |
| 状态 | 在线 / 对外不可达 / 降级 / 离线 / 排空中 / 已停用 / 待激活（醒目显示并排在最前） |
| 最后心跳 | 距现在几秒 |
| 当前压力 | 上行、下行实时带宽及占上限的百分比，超过阈值标红 |
| 服务人数 | 分配人数（分到这台的小白端用户数）；分配 Key 数（其中近 7 天活跃的）；活跃人数（最近 5 分钟有请求的不同用户数，含 API Key 用户） |
| 连接数 | 客户端连接数、进行中的请求数 |
| 版本 | 程序版本、配置版本；落后或协议即将不兼容时标出 |
| IP | 当前连接的来源 IP；最近一次变化的时间 |

主节点也作为一行显示：主节点分配比例、转发带宽、占转发上限的百分比、分到主节点的用户和 Key 数、在主节点上转发的用户和 Key 数（按原因：按比例分配、旧地址、仅主节点分组、从节点域名被改到主节点、小白端回退）。

**详情页**：
- 最近 24 小时的带宽、连接数、服务人数、请求数、错误率曲线；
- 本机锁定额度总额、扣费队列积压、迟到扣费、丢失用量、待复核扣费；
- 这台上的小白端用户列表、分配的 Key 列表；
- 异常检测记录：额度申请频率异常、选号后未上报扣费的比例；
- 日志和记录（第 12 节，查询转给这台；最近日志）；
- 审计记录。

**用户管理页**也显示这个用户当前分在哪台、他的 Key 各分配到哪台、最近在哪几台（含主节点）上有请求、锁在各节点上的额度；锁在离线节点上的额度可以"立即回收"（4.4）。

**操作**：激活、拒绝、一键拒绝所有待激活、修改配置、排空、恢复、停用、一键收回该节点所有额度（节点在线时同步收回；离线时即"立即回收"，租约当场作废，4.4）、吊销证书、删除、手动移动或固定用户、批量移动该节点的 Key、修改对外域名、修改通用配置（含主节点分配比例，改成 0 前先看影响清单，10.8）、按新比例重新平衡小白端用户、关闭"同时两个 IP"判断、复核吊销节点的扣费、临时调日志级别、获取最近日志、诊断（连通性、对外探测、上游连通、配置版本、时钟偏差，只返回状态，不返回请求内容）。
所有操作只允许最高权限的管理员，要求二次验证（现有 `stepUpAuth`）并记审计。

实时数字来自最近一次心跳；曲线由主节点把心跳按分钟汇总后存储。分配人数和分配 Key 数由主节点统计，活跃人数由从节点上报。

### 11.6 部署与升级

- **长期密钥和 HTTPS 证书缓存要持久保存**。用容器部署时，这两个目录挂到持久存储：长期密钥丢了会变成一台新节点，要重新激活；证书缓存丢了每次重建都要重新申请证书，容易撞上 Let's Encrypt 的签发次数限制。
- **换机器、重装**：管理员在域名服务商处把域名解析改到新机器；新机器按新节点注册、激活后，在管理页把旧节点的域名和分到它的 Key 转给新节点（一步操作），域名不变，用户不用改地址。
- 从节点关闭自动更新和 `AUTO_SETUP`（`deploy/docker-compose.yml:45` 默认开着，首次启动会跑安装流程、写配置文件）。
- **升级**：后台排空 → 升级 → 恢复，一台一台来。主节点先升，再升从节点。不想让这台的 API Key 用户中断时，按 10.4 先手动把解析改到主节点。
- **主节点换服务器**：只要根证书不变，从节点改一下主节点地址就能重新连上，不用重新激活。

## 12. 从节点日志与记录

**原则**（分工原则，第 1 节）：日志和记录都留在从节点本机，由从节点提供查询；主节点不收日志内容。后台查看时主节点把查询转给对应节点，结果只显示、不入库。主从之间的流量只有授权和计费，日志不能把分流的意义吃掉。

### 12.1 现有日志和记录

| 种类 | 现在怎么存 | 后台怎么看 |
|---|---|---|
| 程序日志 | 控制台和本机文件（`data/logs/sub2api.log`，`pkg/logger/options.go`）；同时经 `service/ops_system_log_sink.go` 脱敏（`util/logredact`）后批量写数据库 | "系统日志"页（`/admin/ops/system-logs`），可按时间、主机、级别、组件、请求 ID、用户、Key、账号、平台、模型、关键字筛选；级别、采样、保留天数可实时调整（`service/ops_log_runtime.go`） |
| 请求错误日志 | 数据库，含错误信息、错误响应体、上游错误详情、逐次上游错误（`service/ops_port.go:64` `OpsInsertErrorLogInput`） | 错误日志列表和详情 |
| 审核记录（含 cyber 风控记录） | 数据库 `content_moderation_logs`，含命中类别、分数、输入内容摘录 | 风控中心 |
| 提示词审计记录 | 数据库（`securityaudit` 的事件表），待审内容在 Redis | 提示词审计页 |

### 12.2 放在哪

| 种类 | 从节点本机（数据目录，重启不丢） | 主节点收到的 |
|---|---|---|
| 程序日志 | 全部，按单机的级别、采样、保留天数 | 心跳里每分钟按（级别, 组件）汇总的条数（告警用） |
| 请求错误日志 | 全部内容 | 心跳里每分钟按（错误类型, 状态码）汇总的条数 |
| 审核记录、提示词审计记录、cyber 风控记录 | 全部内容，按单机的保留期（命中 / 未命中分开）清理 | 违规事件（只有用户、时间、类别，3.4） |
| 逐请求访问日志 | 全部（本来默认关闭） | — |

- 请求成功时主从之间不因日志产生任何流量（用量走扣费记录，第 5 节）。
- 本机存储用分段文件，有总大小上限，超出先删最旧的；按请求 ID、时间建简单索引，查询时不用扫全部文件。
- 脱敏规则与单机相同（`util/logredact`）。审核记录和单机一样含输入内容摘录，属于本机敏感数据（15.1）。

### 12.3 查询（后续加）

- 后台日志、错误日志、风控中心、提示词审计页按节点查：选"主节点"查本机库；选某台从节点时，主节点把查询条件（时间、级别、用户、请求 ID、关键字、分页）转给那台，结果只显示不入库，单次有条数和大小上限；选"全部"时并发问各在线节点再合并，每台有超时，离线或超时的节点在页面上标出。
- 从节点离线、或本机记录已过保留期时查不到，页面说明原因。
- 从节点详情页"最近日志"：最多 200 行、256KB。

**实现状态（v0.26，WP14）**：
- **本机存储**：`nodestore` 按"种类/日期"分段的 JSON 行文件，总大小上限（默认 2GB，超出先删最旧的）、按种类整天清理；种类 `app`（程序日志）、`error`（请求错误日志）、`moderation-*`（审核记录，已有）。**程序日志**（`nodegw.LogSink`，接 `logger.Sink`）写警告以上和审计（访问日志默认不写，`SetPersistAccessLogs` 打开）；**请求错误日志**把 `service.OpsService` 装在从节点上（只实现写入的 `NodeOpsRepository`），用同一个 `OpsErrorLoggerMiddleware` 和同样的脱敏前处理，落进 `error`。脱敏在单机的 logredact 之上再去掉 API Key 和 Bearer 令牌。成功的请求不产生任何日志流量。
- **查询**（`master/logquery.go`、`nodegw/logs.go`）：`LogQuery` / `LogQueryResult` 经事件流往返（从节点只向主节点发起连接）；条件：种类、时间范围、翻页游标 `before`、级别、组件、请求 ID、用户、Key、账号、平台、模型、关键字；单次最多 200 条、1MB；`tail=1` 是"最近日志"（200 条、256KB）。主节点按不可信输入处理：条数、每条 64KB、必须是 JSON 对象，不合格的丢掉并计数；每台超时 10 秒，离线 / 超时 / 出错的节点在结果里标出；多台按时间新到旧合并，每条带节点。管理接口 `GET /admin/relay/nodes/:id/logs`、`GET /admin/relay/logs`（可 `node_ids=` 限定）。
- **"节点"列**：后台使用记录列表带 `node_id`、支持 `node_id=master|<ID>` 筛选（列表和统计，`usage_logs.node_id`，主节点自己转发的为空）；其他日志页查的是从节点本机记录，每条结果带节点，不另有列。
- **没做**：本机索引（现在是按天读文件顺序扫，扫描量有上限 200 万行，超出回 `scan_limited`，要求缩小时间范围）；按节点临时调日志级别（12.5）；提示词审计记录和 cyber 记录的查询种类（审核记录已经能查；cyber 命中走请求错误日志的写入路径，随 `error` 种类可查）；系统日志页上 `ops_system_logs.node_id` 的"节点"列（主节点库里没有从节点的系统日志，页面按节点查走上面的接口）。

### 12.4 节点列

- 系统日志、错误日志的列表**新增"节点"列**：显示"主节点"或从节点名称，悬停显示节点 ID 和 IP；可以按节点筛选（主节点也是一个选项）。
  不叫"来源"：使用记录已有"账号来源"筛选（`usage_logs.account_source`：号池 / 自有账号 / 贡献房间），同名会混淆。从节点详情页的"日志"标签默认筛这台。
- 后台使用记录列表也新增"节点"列（取 `usage_log.node_id`，16.6），和已有的"账号来源"并列。
- 节点由主节点按连接证书认定（查询转给哪台就标哪台），不信从节点自己报的。
- 同一个请求 ID 下，主节点（选号、入账、上游错误决策）和从节点（转发）的记录都能搜到，用"节点"列区分。

### 12.5 按节点调级别

- 日志级别、采样、保留天数随节点配置下发，默认跟主节点一致。
- 可以只把某一台临时调成详细级别，必须设到期时间（比如 30 分钟），到期自动恢复；详细内容用"最近日志"查看。

### 12.6 安全

- 从节点返回的查询结果是不可信输入：主节点限制条数、每条长度和字段数；后台一律按纯文本显示，不当 HTML 渲染。
- 查看权限沿用现有日志、风控中心的设置。

## 13. 通知

**现有能力**：运维告警（`service/ops_alert_evaluator_service.go`）支持按规则产生告警事件、按严重程度过滤、每小时限量，但只能发邮件（`:678` `maybeSendAlertEmail`）。

**做法**：
- 从节点相关事件接入现有运维告警，在后台查看、确认、恢复。
- 新增**飞书机器人**渠道（后台填 Webhook 地址和签名密钥），与邮件并列，每类事件可选渠道。飞书发送失败时重试，仍失败就改发邮件。
- 飞书 Webhook 地址和签名密钥只存在主节点，加密保存，修改要二次验证；使用飞书自带的签名校验。

| 本地扣费队列积压过多 | 开 | 警告 |
| 从节点停止接收新请求（磁盘满、扣费队列损坏、时钟偏差超限） | 开 | 严重 |
| 额度申请频率异常、选号后未上报扣费比例异常 | 开 | 严重 |
| 从节点连接 IP 变化 | 开 | 提示 |
| 从节点压力持续超过阈值（比如 85% 持续 5 分钟） | 关 | 警告 |
| 从节点版本或配置版本落后 | 关 | 提示 |

**避免刷屏**：同一台一次离线只发一条，恢复时再发一条；短时间反复上下线合并成一条"不稳定"；多台同时出事合并成一条；大量注册合并成一条。

**内容**：节点名称、IP、事件时间、最后一次心跳时间、受影响的分配人数、分配的活跃 Key 数和进行中的请求数、系统已采取的动作、后台管理页链接。不包含用户信息、密钥、凭据。

**主节点自己挂了发不出通知**，从节点也不能代发（不持有飞书密钥）。上线前要在另一台机器上准备独立的外部监控，定时探测主节点，失败时发飞书。

## 14. 异步图片任务

现有做法（`docs/ASYNC_IMAGE_TASKS.md`）：提交后返回任务 ID，后台生成，结果存对象存储，客户端用 `GET /v1/images/tasks/{task_id}` 轮询；任务状态在 Redis，任务完成时扣费。功能默认关闭。

主从模式下：**任务提交落在哪台从节点，就由那台执行。**

- **任务状态放主节点**：从节点接到提交后向主节点登记，执行中上报进度和结果位置。
- **轮询可以落在任何节点**（包括域名在任务执行中被改到主节点、或用户改用主节点地址）：那台向主节点查状态；要返回图片内容时，用主节点签发的临时下载地址从对象存储取，流量走这台从节点。
- **从节点不持有对象存储凭据**：上传用主节点签发的临时上传地址，只能上传这个任务的这一个文件，几分钟后失效。
- **扣费**：提交时选号、拿扣费凭证、本地预扣；任务完成时按凭证入账。凭证和预扣在任务执行期间持续续期。
- **执行中的从节点挂了**：主节点超时后把任务标为失败，不扣费。

**实现状态（v0.22）**：
- 异步图片任务：从节点提交 → `RelayControl.ImageTask` 登记（只认这台节点最近准入过的用户）→ 本机经同步图片入口执行（选号、扣费照常）→ 结果报给主节点，由主节点用单机同一个 `ImageTaskService` 转存图片、落库；轮询落在任何节点都向主节点查。**与上面的差别**：图片数据先随结果走主从连接送到主节点转存（设计是从节点用一次性上传地址直传），所以任务另用一类连接（`RelayTasks`，单条消息上限 64MB；控制连接是 4MB），报结果失败时从节点在内存里有限次退避重发（1、2、4、8、16 秒）。执行中的从节点挂了：主节点在查询任务时发现"处理中"超过执行超时加 5 分钟，标为失败（504，不另扣费：用量在执行时已按同步图片入口入账）。
- 视频任务（Grok 视频创建 / 编辑 / 延伸 / 状态 / 内容、Seedance 创建 / 状态 / 删除）：创建成功后从节点报"任务登记"记录（任务 ID、创建时的待计费快照；不扣费），主节点绑定账号并存快照；之后的状态 / 内容轮询经主节点按绑定的账号选号（没有绑定回 404），第一次看到完成的视频时报"任务完成"记录，主节点按任务认领、合并快照后用 `RecordUsage` 入账，入账失败放掉认领。两条记录的执行逻辑与单机共用 `service.PrepareGrokVideoCompletionBilling` / `PrepareSeedanceCompletionBilling`。**已知差别**：任务登记经扣费队列异步到达主节点，创建成功后立刻查状态可能因绑定还没到而回 404（单机是同步绑定）；客户端按惯例隔几秒再轮询，不受影响。
- 实时通话 `live`：创建时占账号租约、拿 ChatGPT 的 attestation，之后主节点长期持有一个观察连接（按通话时长计费、续租、结束入账），旁路连接按 call_id 找记录。这套生命周期绑在主节点的 Redis 和后台协程上，**暂时仍由主节点处理**（从节点收到这些路径照常转交）；要迁时需要先定"观察连接和结束入账放哪台"。

批量图片任务只在主节点（8.4），用 `frozen_balance`，与从节点额度的 `relay_reserved_balance` 互不影响。

## 15. 安全汇总

### 15.1 从节点被攻破时

| 攻击 | 上限 | 防护 |
|---|---|---|
| 拿走正在用的上游凭据 | OAuth 短期 token 到期为止；静态 Key 长期有效 | 短期 token；静态 Key 账号可设"仅主节点"（第 9 节） |
| 收集经过它的用户 API Key | 分到这台的 Key；节点规则为"全部从节点"时还包括被用户改到这台的 Key | 无法避免（Key 本身就发给它）；吊销这台后，后台一键列出分到它的 Key，提示用户重置 |
| 虚报用量，多扣用户的钱 | 同一时刻每个用户最多 5；但可以反复申请 | 见下 |
| 少报用量，白用上游账号 | 不受额度限制（它有账号凭据） | 主节点用自己的凭据定期独立查询上游账号用量，与各从节点回报的总量对账；选号后未上报扣费的比例异常报警（5.3）；反复丢数据报警（5.4） |
| 伪造票据、扣费凭证 | 做不到：只有公钥 | 非对称签名 |
| 编造扣费记录 | 做不到 | 每条记录必须带有效凭证，每张只入账一次 |
| 谎报计费模型 | 做不到 | 必须在凭证允许的范围内 |
| 伪造主节点下指令 | 做不到 | 双向 TLS，固定根证书指纹 |
| 偷走证书和密钥，在别的机器上冒充这台节点 | 到这台节点下一次续签为止（最长约 24 小时），或被发现、吊销为止 | 续签换密钥；同一身份出现两份立即断开并退回待激活；换 IP 告警 |
| 偷走长期密钥 | 证书过期需要恢复时可以冒用 | 长期密钥只用于恢复；恢复时同样检查同一身份出现两份；恢复记审计并通知 |
| 用 Key 查询试探主节点 | 受限流约束 | Key 查询有负缓存和每台速率上限（8.2、7.4） |
| 重放或篡改扣费批次 | 做不到 | TLS + 批次序号 + 凭证只入账一次 |
| 在查询结果里写入恶意内容 | 做不到有效攻击 | 限制大小、纯文本显示（第 12 节） |
| 拿走下发的审核接口 Key、提示词审计凭据、联网搜索 Key | 被发现、更换为止 | 只在内存；吊销这台后到主节点更换这些 Key（管理页提示）；审核接口 Key 能调付费模型，建议用单独的、只开审核接口权限且有额度上限的 Key |
| 谎报违规，让主节点封别人 | 只能针对这台最近准入过的用户 | 主节点只认这台节点最近 30 分钟准入过的用户（3.4）；违规事件按节点限流；封号可在后台解封，吊销这台后复核它报的违规 |
| 不做审核，放过违规内容 | 流经它的请求 | 无法避免（审核在它上面做），与"读用户对话"同一前提 |
| 读本地磁盘 | 扣费队列（凭证和用量数字）、长期密钥、HTTPS 证书私钥、本机完整日志和错误日志（已脱敏）、审核记录（含输入内容摘录，与单机的记录相同）、提示词审计的待审内容 | 队列不存凭据；Key 缓存、上游凭据和下发的密钥只在内存；与转发无关的密钥不下发（6）；被攻破后吊销这台并换掉它的域名证书 |
| 读用户对话 | 流经它的内容 | 无法避免，只能部署在自己能控制的服务器上 |

**关于虚报用量**：每台上限 5 限制的是一次能锁住多少，不是一台节点总共能扣走多少。被攻破的节点可以虚报用完后再申请。上限的作用是拖慢速度、给检测留时间，真正拦住它的是：
- **申请频率检查**：同一用户在同一台上的补充频率、消耗速度明显高于该用户历史水平或其他节点时，暂停给这台发额度并报警；
- **记录必须对应选号**：没有有效凭证的记录不入账；token 数要和请求体大小对得上；
- **一键收回**：收回某台所有额度、吊销证书，吊销前的扣费标记待复核。

### 15.2 部署要求

| 要求 | 原因 |
|---|---|
| 从节点只开放 8.3 列出的接口，不挂管理后台、登录、内嵌前端（`router.go:74-75`）、安装向导 | 缩小公网攻击面 |
| 从节点关闭 `AUTO_SETUP` 和自动更新 | 见 11.6 |
| 从节点只开 HTTPS，不开 HTTP | 见 7.1 |
| 主节点接从节点的端口直连，不经过会解密的代理或 CDN | 见 7.1 |
| 每台从节点自己申请自己域名的 HTTPS 证书，私钥只在本机，不共用通配符证书；主节点不持有从节点证书，接从节点域名时由 Caddy 按需申请，且只给已登记的从节点域名申请 | 共用一张通配符证书时，一台被攻破就泄露整个域名的私钥 |
| 域名服务商账号由管理员自己保管，系统不保存 | 暂不接域名服务商接口，系统里没有能改解析的密钥 |
| 主节点对外端口上，用从节点域名访问时只开放 API Key 网关接口 | 不让从节点域名成为访问后台、登录的入口 |
| 健康检查、监控只走长连接 | 不对外暴露内部状态 |
| 从节点上"贡献账号和用户代理只能连公网"的限制照样生效（第 9 节） | 云主机内网有元数据接口等敏感地址，不能让用户借账号地址访问 |

## 16. 其他细节

1. **附件**：`/paw/files` 上传的附件存在进程内存里（`NewPawAttachmentMemoryRepository()`），之后按 ID 引用。小白端同一用户所有请求走同一台，可以直接在从节点上运行；上传后、使用前换了节点时会找不到，本次接受。
2. **并发槽**：现有并发槽 15 分钟自动过期（`repository/concurrency_cache.go:47`），有流量时刷新。释放消息丢了最多占用 15 分钟。超过 15 分钟的长请求靠心跳里的选号 ID 续期。
3. **WebSocket 和实时会话**：现有代码每一轮重新定价（`service/openai_profit_control.go:182`），在线占用 60 秒过期需持续刷新（`concurrency_cache.go:39-40`）。所以每一轮都要选号，占用通过长连接刷新；实时音频的时长由从节点上报。
4. **进程内的上限要按节点数调整**：图片生成并发等按进程计算（`deploy/config.example.yaml:502` `image_concurrency`）。WebSocket 每个 Key 的连接数不是按进程：它是 Redis 里的全局租约（`gateway.openai_ws.max_ingress_connections_per_api_key`），从节点经主节点申请（开发计划 WP10-3）。
5. **余额很少的用户**：余额不足 0.1 时会被全部锁到一台。小白端和只用分配地址的 API Key 用户只在一台上用，不受影响。
   同一用户同时在多个地址使用时（多个 Key 分到不同节点、节点规则为"全部从节点"时换了地址、同时用主节点地址），别处的请求可能看到"余额不足"，直到按 4.2 从持有的那台收回（剩余低于 1 时立即收回）。这是预期行为，客服要知道。
6. **可观测性**：`usage_log` 加 `node_id`（主节点转发也记），后台按节点看流量、错误率、延迟、丢失用量、额度申请频率。
