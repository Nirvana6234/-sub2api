# 小白客户端「本地中转服务」模式 —— 调研

> 状态：**调研，未动代码**。整理于 2026-09-01。
> 想法（用户提出）：把 ChatGPT 桌面版的 base URL 指向**小白客户端本身**，
> 由客户端完成与中转站的通讯；目的是让手机端（类似 Paseo 那样的独立 chat）
> 能操作小白端，获得 ChatGPT 桌面端的会话能力。
> 相关：[`共飞 Paw 远程操作整体架构.md`](共飞%20Paw%20远程操作整体架构.md)、
> [`Codex官方客户端注入增强设计草稿.md`](Codex官方客户端注入增强设计草稿.md)。

---

## 0. 先说三件已经查证的事，它们决定了整篇结论

### 0.1 这不是新架构，是**工作台的既有架构换一个轻实现**

`doc/中转中心单用户本机架构设计草稿.md` 写的就是："所有 AI 客户端**永远只连本机 Sub2API**
（`http://127.0.0.1:8080`），切换来源只改本机的账号/调度配置，不改客户端上游地址。"

也就是说：

| | 客户端指向 | 本机跑什么 |
|---|---|---|
| 共飞工作台（现状） | `127.0.0.1:8080` | **完整 sub2api**：Go 后端 + PostgreSQL + Redis |
| 小白版（现状） | **远端中转站** | 无 |
| **本次想法** | `127.0.0.1:<客户端端口>` | **一个薄转发**：只做转发 + 镜像 + 注入密钥，无数据库 |

所以要评估的不是"这个架构行不行"（工作台已经在跑），而是"**薄到什么程度还能成立**"。

### 0.2 手机侧的聊天通道**已经存在**

`backend/internal/server/routes/paw.go:110-111` 已经有：

```
paw.POST("/chat/completions", …)
paw.POST("/responses",        …)   // 注释原文：工作台里的 codex 走这条
```

也就是说"手机能用同一账号、同一分组聊天"这件事**不需要本地中转也能做**，
Paw 直接连服务端就行。本地中转真正新增的能力只有一件：
**让手机看到／接续桌面端那些对话**。这一点必须先说清楚，否则容易高估收益。

### 0.3 让镜像成立的关键事实：ChatGPT 账号路线**必须整段发送上下文**

`backend/internal/handler/openai_gateway_handler.go:607-627`：

> `previous_response_id` 只在 **OpenAI API-key 账号**上支持；
> OAuth / SetupToken（也就是 ChatGPT 账号）上游不支持，调度器宁可换账号也不会
> 悄悄把续话状态删掉。

共飞是**个人账号优先**的调度（见 [[sub2api-backend]] 的口径），意味着走 ChatGPT 账号时
**上游没有服务端会话状态**，客户端只能把整段对话塞进每次请求的 `input` 里。

**推论：本地转发看得到的是完整对话，而不是增量。** 镜像因此在原理上成立。
⚠️ 但这是**从服务端代码推出来的**，不是抓包抓出来的 —— 见 §5 的 V-11，**未验之前不要当结论**。

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 桌面版能不能指向本机的我们？ | 大概率可以：V-2′ 已实测 `codex exec` 在同一套 config 下把 `POST /v1/responses` 打到 `127.0.0.1:8080`（明文 HTTP、带 `authorization` 与 `chatgpt-account-id`）。**桌面版走完整交互会话**这条还没实测（V-12）。 |
| 手机能"看"桌面端的对话吗？ | ✅ 原理成立（§0.3），代价是客户端进程看得到全部明文（§4.2）。 |
| 手机能"接着"桌面端的对话聊吗？ | ⚠️ **内容层可以，UI 层不行**：能把录到的对话当作新一轮的输入继续，但**桌面版界面不会显示手机发的这几轮**，之后在桌面继续会分叉（§2.2）。 |
| 手机能"操作"桌面端本身吗？ | ❌ 转发做不到。转发是被桌面版调用的一方，无法主动往它的会话里塞消息。要这个只能走 CDP 注入（§2.3）。 |
| 和 Paseo 那条路冲突吗？ | 不冲突，是**互补**：本地转发给"看桌面对话 + 轻量聊天"，Paseo 给"手机上跑真 agent"（§6）。 |
| 最大代价 | **单点故障**：config 指向我们之后，客户端没开＝桌面版所有模型请求都失败。今天客户端关掉桌面版照样能用（§4.1）。 |
| 阻塞级验证 | V-11（请求体是否整段带上下文）、V-12（桌面版能否在明文 loopback base_url 上跑完整会话）。 |

## 2. 三种能力要分开谈（不要混成一个功能）

### 2.1 观察 / 镜像 —— 可行

转发进程看得到每一轮的请求体与流式响应体，可以据此重建可读的对话，推给手机。

- 前提是 §0.3 那条（整段上下文），待 V-11 验证；
- 只覆盖**开启转发之后**的对话。之前的历史在桌面版本地（`~/.codex/sessions` 的 rollout），
  转发看不到；要读那些得另外解析文件，是另一件事；
- 桌面版还有**不经过 base_url 的流量**（`chatgpt.com/backend-api/*`，
  注入方案里实测过的 MCP 通道就是其一），这部分转发永远看不见。

### 2.2 接续（内容层）—— 可行，但会分叉

手机发一句话时，客户端把**录到的完整对话 + 这句话**作为一次新的上游请求发出去。
从模型的角度这就是同一段对话的延续；从产品角度要认下面两条：

1. **桌面版界面不会出现这几轮**。它的本地 rollout 里没有，它也不知道发生过；
2. 用户之后在桌面继续打字时，桌面是从**它自己的**最后一轮往下接的，
   于是两条线**从这里分叉**。手机上看到的和桌面上看到的会不一样。

这不是 bug，是这个方案的固有形状。要么产品上明说"手机是另一条线"，
要么加一层"回写"（把手机那几轮塞回桌面版）—— 而回写属于 §2.3。

> 附带一个技术细节：如果走的是 **API-key 账号**，`previous_response_id` 是可用的，
> 手机那一轮可以直接挂在桌面最后一轮的 response id 上，省掉重发整段上下文。
> 但个人（ChatGPT）账号上游不支持，所以**不能把它当主路径**（§0.3）。

### 2.3 接管桌面版会话（UI 层）—— 转发做不到

转发是**被调用方**：桌面版什么时候发请求、发什么，由它自己决定。
没有任何办法从转发这一侧"制造"一轮桌面版会话。

要真的往桌面版的会话里塞消息，只有 `AiSwitch.Injection` 那条 CDP 路（往渲染进程里注入、
操作 composer）。那条路已有代码、也已实测能注入 DOM，但随官方 UI 改版会持续腐化。

## 3. 形态选择

| 形态 | 客户端要做什么 | 手机能得到什么 | 代价 |
|---|---|---|---|
| **A. 只做路由中继**（最薄） | 转发 + 注入真实密钥；不解析请求体 | 无新增（手机还是直连服务端聊） | 单点故障；换来"密钥不落 config.toml" |
| **B. 转发 + 镜像**（推荐起点） | A + 解析并留存对话，经共联推给手机 | **看**桌面对话、收通知 | A + 客户端看得到全部明文 |
| **C. B + 手机接续** | B + 代手机发起上游请求 | 看 + 在手机上接着聊（会分叉，§2.2） | B + 分叉的产品解释 |
| **D. C + 回写桌面** | C + CDP 注入把手机的轮次写回桌面版 | 真正的"同一个会话" | 依赖注入层，随官方改版腐化 |

**建议按 B 起步**：它是第一个带来新能力的形态，而且不需要对分叉做产品解释。
C 是一个开关，D 单独立项。

## 4. 风险（按严重度排）

### 4.1 🔴 单点故障：客户端没开 = 桌面版不能用

今天小白版客户端关掉，桌面版照样直连中转站工作。改成本地转发之后，
`config.toml` 指着 `127.0.0.1:<port>`，**客户端不在，桌面版每一次模型请求都失败**，
而且报错形态是网络错误，用户完全无从判断。

这是本方案**最大的行为倒退**，且专打小白用户。缓解手段（都要另花成本）：

- 客户端注册为开机自启，并在托盘常驻；
- 客户端退出前把 `config.toml` 还原成直连中转站（已有还原机制，但要覆盖这条路径）；
- 端口固定 + 健康自检，异常时弹明确提示而不是让桌面版自己超时。

### 4.2 🔴 隐私姿态改变：客户端看得到全部明文

今天客户端只是**改一个 URL**；改成转发之后，它**读到每一轮对话的全文**。
这跟整体架构文档里"relay 零知识作废"那条是同一类变化，需要一次明确的产品表态：

- 只在内存中转，还是落盘？落多久？
- 用户能不能看到"客户端正在记录这台机器上的对话"？
- 手机侧能看到的范围由谁决定？

### 4.3 🟡 官方登录会重写 `config.toml`

注入方案文档里实测过：完成一次官方 ChatGPT 登录，桌面版会**整体重写 config.toml，
丢掉它不认识的键**（`model_provider`、`[model_providers.*]` 等）。

今天丢了只是"路由回官方"；本方案下丢了是**桌面版彻底不能用**（指向的本地转发没了）。
`CodexRouteGuard` 因此更吃重，而不是更轻松。

### 4.4 🟡 身份头必须原样转发

V-2′ 实测：请求带 `authorization` **和 `chatgpt-account-id`**。
转发时漏掉后者会**静默改变中转站认到的身份**，进而影响调度与计费归属。
转发实现必须"除白名单外原样透传"，而不是"挑几个头转发"。

### 4.5 🟡 流式必须真流式

Responses 走 SSE。转发若缓冲，桌面版的打字机效果会变成一个转圈。
实现上要点对点透传字节流、不做整包解析（要镜像就旁路复制一份，别卡在主链路上）。

### 4.6 🟢 请求体形状会变

`x-codex-beta-features`、以及后端日志里的 `codex.remote_compact.detected_body_signal`
说明 codex 会带 beta 特性、也会请求服务端压缩上下文。
镜像逻辑要能容忍"这一轮的 body 不是我认识的形状"，不认识就**只转发不解析**，
绝不能因为解析失败而中断转发。

## 5. 待验清单（🔴 为阻塞级）

| 编号 | 内容 | 级别 |
|---|---|---|
| **V-11** | 让桌面版把 base_url 指向一个**真正的本地 HTTP 服务**（能收 POST、能回 SSE），抓一轮真实对话：请求体里是不是**整段 `input`**、有没有 `previous_response_id`、带了哪些头 | 🔴 阻塞。镜像与接续全压在这条上 |
| **V-12** | 桌面版在**明文 loopback base_url** 上能不能跑完整交互会话（不只是 `codex exec`） | 🔴 阻塞。V-2′ 只证到 CLI |
| V-13 | 桌面版有多少流量**不经过** base_url（已知 `chatgpt.com/backend-api/*`），这些缺口影响哪些产品承诺 | 🟡 |
| V-14 | 客户端不在时，桌面版的报错形态是什么（超时？立刻失败？重试几次？）——决定 §4.1 的提示怎么写 | 🟡 |
| V-15 | `config.toml` 里放**假密钥**、由转发注入真密钥，桌面版是否照常工作 | 🟢 这是本方案少有的净收益，值得早点确认 |

> ⚠️ **V-11 的做法要注意**：本项目在 V-2′ 上被"粗糙的单次读 TCP 脚本"误导过一次
> （桌面版只留下两个空 TCP 连接，看起来像没发请求）。
> 这次必须用**能正确应答的 HTTP + SSE 服务**，否则抓到的又是假象。

## 6. 与 Paseo 那条路的关系：互补，不是二选一

| 产品目标 | 该走哪条 |
|---|---|
| 手机上**看**电脑上正在进行的 ChatGPT 对话 | **本地转发**（Paseo 看不到桌面版的会话） |
| 手机上用同一账号**聊天** | 两条都行；Paw 直连服务端已经能做（§0.2） |
| 手机上让 AI **动文件、跑命令、改代码** | **Paseo**（转发只是聊天通道，没有 agent 能力） |
| 手机上**接管桌面版界面** | 都不行，只能 CDP 注入 |
| 体积与依赖 | 转发：无 Node、无 400 MB；Paseo：私有 node + 预构建 node_modules |

一句话：**转发拿到的是"桌面版在聊什么"，Paseo 拿到的是"手机上能干什么"**。
两者放在同一个客户端里并不冲突——它们连的甚至不是同一个上游面。

## 7. 建议的下一步

1. **先做 V-11 + V-12**（各半天量级，材料现成：起一个能回 SSE 的本地服务，
   把 `config.toml` 的 base_url 指过去，跑一轮真实对话）。
   两条都过，本方案才谈得上排期。
2. V-11 通过后，先做**形态 B（转发 + 镜像）**，把 §4.2 的隐私表态和 §4.1 的
   自启/还原一起定下来——这两件不是实现细节，是产品前提。
3. 形态 C/D 各自独立评估，别捆进第一版。
