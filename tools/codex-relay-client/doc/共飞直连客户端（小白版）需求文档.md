> 硬性约束：仓库根 `AGENTS.md`（数据权威 + 发布安装策略）。

## 1. 背景与定位

现有 `共飞AI工作台`（`tools/manufactor_app/ai-switch-gui`）是**运营者/开发者向**的重型客户端：
它自带本机 Sub2API 后台、账号池、贡献账号、终端、聊天、统计等 13 个页面，
启动时用**本机控制令牌**自动登录 `127.0.0.1:8080`。这套形态对小白用户过重。

本文定义一个**独立的、面向小白用户的直连客户端**：

- **不带**本机后台、不管理账号池、不做调度 —— 只是中转站的一个瘦客户端；
- **直连远端中转站服务器**（HTTPS），而非 `127.0.0.1`；
- 用户只需要做一件事：**登录**。此后余额、用量、分组、授权、拉起 Codex 全部自动；
- **用户永远不接触"中转站授权 key"**——由客户端代持、代写、代轮换。

### 1.1 与现有工作台的差异

| 维度 | 共飞AI工作台（现有） | 直连客户端（本文） |
|---|---|---|
| 目标用户 | 运营者 / 开发者 | 小白用户 |
| 后台 | 自带并托管本机 Sub2API | 无，连远端服务器 |
| 认证 | 本机控制令牌自动登录（见 `MainWindowViewModel.EnsureLocalAdministratorSessionAsync`） | **仅**账号密码登录，无任何免登录旁路 |
| 中转站授权 key | 用户在页面里能看见、能管理 | 用户看不见，客户端代管 |
| 页面数 | 13 | 主界面 + 登录/注册页 + 充值页 + **项目中心/项目会话** + 备选聊天页 + 设置页 |
| 项目中心 | 项目 → 会话 → **自研聊天 UI** | 项目 → 会话 → **拉起官方 Codex 到该项目**（F11）；自研聊天 UI 保留为**备选**（F12） |
| 聊天引擎 | Codex / Claude / Gemini 三套 | 只接 Codex 一套（F12.3） |
| 分组 | admin 分组管理全量 | 只读展示 + 单击切换 |
| 打包 | 自解压安装器 + 本机 PG/Redis | 单文件 exe，**无服务端依赖**（无需 PG/Redis/Node）。仍有两项客户端侧外部件：WebView2 Runtime（仅当服务器开 Turnstile，F1.8）、Codex CLI（仅当用 F12 备选聊天） |

### 1.2 明确不做（v1 范围外）

不做终端、不做账号贡献、不做账号池管理、不做管理员功能、
不做本机后台托管、不做多语言（先中文）、不做 macOS/Linux、
**不做 OAuth 第三方登录**（六种回跳流程成本高，v1 只做邮箱密码，见 F1′.5）、
**不做客户端内的银行卡表单**（充值只走扫码与支付方页面，见 F10.0）。

## 2. 名词澄清：三种"凭据"必须区分

这是本项目最容易出错的地方，实现前必须统一口径。

| # | 名称 | 形态 | 来源 | 用户是否可见 | 存放位置 |
|---|---|---|---|---|---|
| 1 | **登录令牌** | JWT `access_token` / `refresh_token` | `POST /api/v1/auth/login` | 否 | 客户端本地，DPAPI 加密 |
| 2 | **中转站授权 key** | `sk-...`，对应后端 `api_keys` 表 | `POST /api/v1/keys`（需 1） | **否**（本产品的关键决策） | ① 客户端本地加密缓存 ② `~/.codex/auth.json` |
| 3 | **官方 ChatGPT 令牌** | OAuth token | 官方客户端自己登录写入 | 否 | `~/.codex/auth.json`（官方写） |

> 用户需求原文"不需要中转站授权key什么的"指的是 **#2 对用户不可见**，
> 而不是"请求不带 key"。协议层仍然需要 #2，只是由客户端静默创建与写入。

## 3. 可行性前提（**动手前必须先验证**）

《注入草稿》已验证的事实可以直接复用（CDP 注入、COM 激活拉起、限额哨兵、
切换编排）。但本产品新增了若干**未经验证、且能否成立会改变产品形态**的前提。

**M0 待验证项总表**（详细说明见各自条目，出口标准见 §9）：

| 编号 | 待验证 | 不成立时的影响 | 详见 |
|---|---|---|---|
| V-1′ | `auth.json` 同时有 OAuth 与 API key 时谁优先 | 用户"看着切了、其实没切" | 本节 |
| V-2 | `.msix` 直链是否存在 / 依赖包 / 签名信任 | F2 退化为引导安装 | 本节 |
| V-3 | 目标服务器允许用户建 key 吗 | F3.2 走不通，需服务器预置 key | 本节 |
| V-T | 目标服务器是否开启 Turnstile | 决定要不要背 WebView2 依赖 | F1.8 |
| V-4 | 能否按目录拉起官方 Codex + 单实例锁行为 | F11.3 走 A/B/C/D 哪条路 | F11.4、F11.5 |
| V-5 | Codex CLI 安装渠道 + 引入聊天后的冷启动耗时 | F12 兜底能力与 §7 达标 | F12.1、F12.2 |

**已提前结清的部分（2026-07-30，查后端源码而非打接口）**：

| 结论 | 依据 | 影响 |
|---|---|---|
| ✅ `GET /keys` 返回**完整明文 key**，未脱敏 | `dto/mappers.go:85` | F3.2.1 成立，无需本地长期缓存 key |
| ✅ `PUT /keys/:id` 的 `expires_at` 为 **RFC3339**；**空串会清除过期时间** | `api_key_handler.go:226-231` | F3.2.3 新增两条实现约束 |
| ✅ `/settings/public` 已含 `api_base_url`、`contact_info` | `dto/settings.go:335-336` | 写 `config.toml` 的 base URL 与 F10.6【联系我们】都有来源，无需新增接口 |
| ⚠️ `registration_email_suffix_whitelist` 是 **`[]string` 数组**，不是逗号分隔字符串 | `dto/settings.go:320` | 客户端契约曾按字符串写，会导致整个设置拉取反序列化失败，已修正 |
| 🔶 `turnstile_enabled` **缺省为 false** | `setting_parse.go:317` 按 `== "true"` 判定 | 本机开发服大概率无需 WebView2；**生产中转站仍需单独确认**（V-T 未结清） |

### V-1 官方账号：**已决策 —— 不管**

产品**只支持"仅中转站 key"这一种模式**，不介入官方 ChatGPT 账号的登录状态。
若用户本来就登录着官方账号，由**用户自己在 Codex 内退出/登录**，客户端不代劳、
也不检测、不提示"你必须先退出"。

> 这条决策把原先的阻塞级风险降级：产品定位不再依赖"桌面应用能否无账号可用"这个未知量。

但派生出一个**仍需实测**的小问题（不阻塞开工，只影响文案与写入内容）：

**V-1′：`auth.json` 里同时存在官方 OAuth 令牌和 `OPENAI_API_KEY` 时，Codex 以谁为准？**

- 若以 API key 为准 → 什么都不用做；
- 若以 OAuth 为准 → 用户不手动退出就会"看着切了、其实没切"，是最难排查的一类问题。
  此时客户端需要**在状态条上如实显示当前实际走的是哪一路**，并提供一句可操作的提示
  （"在 Codex 里退出官方账号后即可使用共飞额度"）。
- 候选缓解手段：`config.toml` 的 `preferred_auth_method = "apikey"`。
  **注意：本仓库全局搜索无此键，它来自对 Codex CLI 的印象，未经证实。**
  写入前必须先确认该键在当前版本真实存在且有效，否则就是往用户配置里塞垃圾键。

**验证方法**：造一个两者都有的 `auth.json`，发一轮对话，看请求是否落到中转站。

### V-2 安装渠道：**已决策 —— 直接下载 MSIX 安装**

采用 **下载 `.msix` + `Add-AppxPackage`** 路线，不走 winget、不走 Store 深链。
理由：winget 走 WinHTTP 直连、不吃系统代理，且依赖 App Installer 是否存在；
Store 深链需要用户手点"获取"，不满足"点一下就装好"。

**网络可达性问题（下载源被墙/慢）本期不处理**，后续再考虑镜像或自建分发。
本期的失败路径就是"下载失败 → 明确报错 + 一键复制详情 + 打开 Store 手动安装的兜底链接"。

**仍需在 M0 确认的事实**（是事实性未知，不是方案选择）：

1. 官方 `.msix`（或 `.msixbundle`）的**稳定下载直链是否存在**、如何获取版本号；
2. `Add-AppxPackage` 是否需要**依赖包**（VCLibs / WindowsAppRuntime 等 `-DependencyPath`）；
3. 是否需要开发者模式或证书信任（官方签名包一般不需要，但要实测确认）。

若第 1 项不成立（拿不到直链），F2 退化为"引导到 Store 安装"，需要回来改本节。

### V-3（P2）远端服务器上 `POST /api/v1/keys` 的可用性

后端接口存在且用户态可调（`internal/server/routes/user.go:67`），
但生产实例可能通过 `BackendModeUserGuard` / 合规开关限制建 key。需在目标服务器上实测一次。

### F1 首次启动与登录

**F1.1 登录是唯一入口。** 未登录状态下主界面不可达，不提供"跳过""离线使用"
"输入 API key 直接用"等任何旁路。

**F1.2 登录表单**：**邮箱** + 密码 + "记住我"（只做邮箱登录，见 F1′.5）。
调 `POST /api/v1/auth/login`。

**F1.3 二次验证**：若响应为 `{"requires_2fa": true, "temp_token": ..., "user_email_masked": ...}`，
切换到 6 位验证码输入，调 `POST /api/v1/auth/login/2fa`。

**F1.4 会话保持**：`access_token` 过期时用 `refresh_token` 静默续期
（`POST /api/v1/auth/refresh`）。续期失败 → 回登录页并说明原因，**不弹裸 401**。

**F1.5 服务器地址**：编译期内置默认中转站地址；设置页可改（供自建用户）。
地址必须是 `https://`，非 HTTPS 需二次确认并明示风险。

**F1.6 退出登录**：清除本地令牌，并按 F3.2.4 撤销托管 key，回到登录页。
**不**清除 `~/.codex` 下的任何文件（那是用户的数据）。

**F1.7 表单形态由服务器决定（硬性要求）**

登录/注册界面**不得把字段写死**，必须由 `GET /api/v1/settings/public` 驱动。
该接口已返回全部所需开关（`internal/handler/setting_handler.go:46` 起），至少要用到：

| 字段 | 用途 |
|---|---|
| `registration_enabled` | 为 false 时隐藏注册入口，而不是点了才报错 |
| `email_verify_enabled` | 决定注册是否需要邮箱验证码 |
| `registration_email_suffix_whitelist` | 提前提示可用邮箱后缀，别等提交才失败 |
| `invitation_code_enabled` / `promo_code_enabled` | 决定是否显示邀请码 / 优惠码输入框 |
| `password_reset_enabled` | 决定是否显示"忘记密码" |
| `turnstile_enabled` / `turnstile_site_key` | 见 F1.8 |
| `login_agreement_enabled` / `_mode` / `_documents` | 见 F1.9 |
| `totp_enabled` | 决定是否准备 2FA 步骤 |
| `payment_enabled` | 为 false 时整个充值模块隐藏（F10） |
| `site_name` / `site_logo` | 客户端标题与品牌 |

启动时拉一次并缓存；拉取失败时按**最保守**形态渲染（只留登录），不要瞎猜。

**F1.8 人机验证（Turnstile）——桌面端的真正难点**

`POST /auth/register` 与 `POST /auth/send-verify-code` 都接受 `turnstile_token`
（`internal/handler/auth_handler.go:60,69`）。若服务器开了 Turnstile，
**WPF 原生控件无法产出这个 token**——它必须由 Cloudflare 的浏览器组件生成。

方案：内嵌 **WebView2** 加载一个只承载 Turnstile 组件的极小页面，
**由用户本人完成验证**，客户端读回 token 后随注册请求提交。

> 明确边界：这是**正常渲染人机验证让用户自己过**，不是绕过。
> 任何"自动过验证"的做法都不在本方案内，也不允许实现。

派生约束（必须在 M0 一并确认）：
- WebView2 Runtime 在 Win10/11 上通常预装，但**不保证**。安装程序需检测并按需引导安装；
- 承载页面从哪来？建议由**服务器**提供一个 `/turnstile-widget` 极简页，
  避免客户端内置站点密钥与域名假设（Turnstile 校验绑定域名）；
- 若目标服务器**未开启** Turnstile，则完全不需要 WebView2 —— 这条要先查清楚，
  它直接决定客户端要不要背 WebView2 这个依赖。

> ✅ **已实测（2026-07-31，本机 relay v0.1.158）**：`turnstile_enabled = false`、
> site key 为空。**本期不需要 WebView2，也不需要服务器加 `/turnstile-widget` 页。**
> 该结论已由 `LivePublicSettingsContractTests.TurnstileIsOffOnTheCapturedServer`
> 锁定——将来刷新夹具时若这条挂了，就说明 Turnstile 被打开了，本节的工作随即变成真的。
>
> ⚠️ **归因边界**：测的是**本机开发服务器**，不是小白客户端最终要连的**生产中转站**。
> 生产实例可能另有配置，上线前需对生产地址复测一次。

**F1.9 登录协议（用户协议/隐私政策）**

`login_agreement_enabled` 为 true 时，注册/登录界面必须按
`login_agreement_mode` 展示 `login_agreement_documents` 并由**用户本人勾选同意**。
文档内容用内置阅读器展示，**不得**替用户默认勾选、不得把勾选框预置为选中。

**AC**：
- 全新安装、无任何本地状态时启动，第一屏必为登录页；
- 服务器关闭注册后，客户端**看不到**注册入口（而不是点进去报错）；
- 断网时登录失败给出"连不上服务器"而非"密码错误"；
- 杀掉进程重开，7 天内不需要重新输密码（refresh 有效期内）；
- 登录页与设置页之外，任何界面都不出现"API key"字样。

### F1′ 注册（客户端内完成）

**F1′.1 表单字段**：邮箱 + 密码（≥6 位，与后端 `binding:"min=6"` 一致）+ 确认密码，
再按 F1.7 的开关**动态**追加：邮箱验证码、邀请码、优惠码、协议勾选、Turnstile。

**F1′.2 邮箱验证码**：`POST /api/v1/auth/send-verify-code`，
响应里的 `countdown` 是**服务器给的倒计时秒数**，客户端必须用它驱动重发按钮，
不要自己拍一个 60 秒。该接口有服务端限流（每分钟 5 次，Redis 故障时 fail-close），
UI 要能体面地呈现"太频繁"。

**F1′.3 提交**：`POST /api/v1/auth/register`，成功后**自动登录**进入主界面，
不要让小白用户再手输一遍账号密码。

**F1′.4 邀请码/优惠码可预校验**：`POST /auth/validate-invitation-code` /
`POST /auth/validate-promo-code`，在用户离开输入框时校验，
**在提交前**就告诉他码是否有效。

**F1′.5 只做邮箱登录（已决策，非待定项）**

客户端**只支持邮箱 + 密码**一种登录方式。
LinuxDo / GitHub / Google / 微信 / 钉钉 / OIDC 六种 OAuth **一律不做**——
它们都要浏览器回跳与 state 交换，桌面端复刻成本高且随服务端持续腐化。

即使 `/settings/public` 返回某个 OAuth 已启用，客户端也**不显示**对应按钮，
并在登录页给一句"其他登录方式请使用网页版"。

> 副作用（需要知道，但不改变决策）：**用 OAuth 注册且从未设置过密码的用户，
> 无法登录本客户端。** 客户端在登录失败时应能识别这种情况并提示
> "该账号未设置密码，请先在网页版设置密码"，而不是笼统报"密码错误"。
> 能否从错误码区分这两种情况，需在 M1 实测确认。

**F1′.6 忘记密码**：`password_reset_enabled` 为 true 时提供入口，
走 `POST /auth/forgot-password` + `POST /auth/reset-password`（邮箱验证码流程）。

**AC**：
- 服务器开启邮箱验证时，注册表单必须出现验证码框且重发倒计时来自服务器；
- 邮箱后缀不在白名单时，在**输入阶段**就提示，而不是提交后报错；
- 注册成功直接进主界面，全程无需二次登录；
- 服务器开启 Turnstile 时，未完成验证不允许提交（按钮置灰而非提交后报错）。

### F2 环境检查与安装官方 Codex 桌面应用

**F2.1 安装检测**：复用 `CodexAppLauncher.IsInstalled`
（探测 `%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0`）。

**F2.2 未安装时**：主界面显示"未检测到 Codex 桌面版"卡片 + 【安装】按钮。
点击后执行 **下载 `.msix` → 校验 → `Add-AppxPackage` 安装**（V-2 已决策）。
安装过程按四步展示：下载中（带百分比与速度）→ 校验中 → 安装中 → 完成。

**F2.3 下载与校验**：
- 下载到本地临时目录，走**系统代理**（与 winget 的行为差异正是不选 winget 的原因之一）；
- 必须校验：文件大小 + 数字签名发布者。**签名校验不可省略**——
  这是从网络取一个可执行包并安装到系统，未验签的包不许装；
- 支持断点续传或失败重试（≤3 次，指数退避），安装完成后**删除临时文件**。

**F2.4 安装后自动复检**，检测到即把卡片切换为【启动 Codex】。

**F2.5 失败可诊断**：下载或安装失败必须给出**可执行的下一步**——
错误摘要 + 一键复制详情 + 【打开 Microsoft Store 手动安装】兜底按钮，不允许只显示错误码。
本期不为网络不可达做镜像/加速，但**必须把"很可能是网络问题"这句话说出来**。

**AC**：
- 未安装 → 卡片可见且按钮可点；已安装 → 卡片不出现；
- 下载中断（用户取消/断网）后，客户端仍可用，临时文件被清理，重试不产生残留；
- 签名校验失败时**拒绝安装**并明确告知，不给"仍要继续"的选项；
- 检测逻辑与工作台共用同一份实现（`CodexAppLauncher.IsInstalled`），不出现两套判定标准。

### F3 授权注入与拉起 Codex（本产品的核心）

**F3.1 一键流程**。用户点【启动 Codex】后，客户端依次：

1. 确保有一把可用的中转站授权 key（见 F3.2）；
2. **快照** `~/.codex/config.toml` 与 `auth.json` 的**完整内容**（见 F3.4）；
3. 写入路由：`config.toml` 的 `model_provider` + `[model_providers.sub2api]`
   （`base_url` = 服务器 `/v1`、`wire_api = "responses"`），
   `auth.json` 的 `OPENAI_API_KEY` = 中转站 key；
4. 以调试端口拉起官方应用（`CodexAppLauncher.EnsureDebugPortAsync`）；
5. 注入共飞状态条并启动限额哨兵与路由守护（`CodexInjectionSession`）。

**F3.2 授权 key 的静默生命周期：租约 + 心跳**

**目标**：授权**只在客户端运行期间有效**。关闭客户端、关机、崩溃、断电之后，
key 必须自动失效，不需要任何人工干预。

**F3.2.0 为什么不是"退出时销毁"（关键设计决策）**

"在退出事件里 `DELETE` 掉 key"看起来直接，但它**在最需要它生效的场景下恰好失效**：
任务管理器强杀、蓝屏、断电、Windows 关机超时——进程根本没有机会执行清理代码。
Windows 的 `WM_QUERYENDSESSION` 有超时，不保证跑完。
**依赖"优雅退出"的安全机制等于没有安全机制。**

因此采用**租约（lease）**模型：key 的有效期本身就很短，靠客户端持续心跳续租维持。
不续 = 自动死。优雅退出时的主动撤销只是**加速**，不是唯一保障。

> **后端已具备的性质（已查证，无需改动）**：
> `IsExpired()` 是 `time.Now().After(ExpiresAt)`（`internal/service/api_key.go:77`），
> 在**每一次计费请求**上现算（`internal/server/middleware/api_key_auth.go:237`）。
> 即使认证缓存里是旧快照，只要快照中的 `ExpiresAt` 是那个短值，到点照样拒绝。
> **过期是自执行的，不依赖缓存失效通知** —— 这正是租约比"删 key"稳的根本原因。

**F3.2.1 识别**：登录后 `GET /api/v1/keys`，按固定命名规则找出本客户端托管的 key，
如 `共飞直连客户端-<机器名>-<客户端安装ID>`。**认名不认值**。找不到 → 视为不存在。

> ✅ **已查证（2026-07-30）**：列表接口返回的 `key` 字段是**完整明文，未脱敏**
> （`dto/mappers.go:85` 直接 `Key: k.Key`）。因此客户端**不需要**在本地长期缓存
> key 明文——随时可以重新取回并写入 `auth.json`。
> 这同时排除了一个曾经的备选设计（"只能在创建那一刻拿到值，丢了就得轮换"）。
同时**清理孤儿**：名字匹配本机规则但不是当前这把的，一律删除
（上次崩溃残留的租约，虽然已过期，但不该留在用户的 key 列表里碍眼）。

**F3.2.2 签发：一步到位，租约就是 1 天**

`POST /api/v1/keys`，`group_id` 取当前选中分组（F5），
**`expires_in_days = 1`**（已决策：租约粒度取到天为止）。

> **这个决策消掉了一个坑。** 创建接口只有 `expires_in_days`（天粒度，
> `api_key_handler.go:39`）。若要分钟级租约，就得"先建 1 天、再 `PUT` 收紧"两步走，
> 中间留一个"这把 key 有 1 天有效期"的窗口，且收紧失败还要回滚删除。
> **现在 1 天就是租约本身，签发一步完成，没有窗口，也不需要给后端加
> `expires_in_minutes`。** 本产品因此对后端零改动。
>
> 备注：更新接口的 `expires_at` 是 ISO 8601 字符串且**无最小值校验**，
> 所以将来若想收紧到小时/分钟级，随时可以，不需要后端配合。

**F3.2.3 在线自动续签（核心机制）**

| 参数 | 默认值 | 说明 |
|---|---|---|
| 租约时长 TTL | **1 天** | 客户端不在之后，授权最长存活时间 |
| 续签方式 | `PUT expires_at = now + 1 天` | 滚动 24 小时窗口 |
| 续签时机 | 启动并登录成功后立即 / 每次点【启动 Codex】前 / 常驻期间每 **6 小时** | |
| 容错 | 连续 3 次失败才告警 | 短暂断网不该打断用户 |

> ⚠️ **续签的两个实现陷阱（已查源码确认，2026-07-30）**：
> 1. `expires_at` 必须是 **RFC3339**，服务端用 `time.Parse(time.RFC3339, ...)` 解析
>    （`api_key_handler.go:231`），格式不对直接 400。C# 用 `DateTimeOffset.ToString("O")` 即可；
> 2. **传空字符串 `""` 会清除过期时间**（`api_key_handler.go:226-229` 走 `ClearExpiration`），
>    把租约变成**永不过期**——与本节的全部安全目标正好相反。
>    因此续签路径必须**断言待写入的值非空**，不允许空串流到请求体里。

- 续签**不改变 key 的值**，因此不重写 `auth.json`，不影响正在运行的 Codex；
- 续签只在**已登录且客户端进程存活**时发出。登录令牌失效 → 停止续签 → 租约自然到期；
- 只要客户端在线，用户永远碰不到过期；**过期只发生在客户端长时间不运行的情况下**，
  这正是想要的语义；
- 若续签连续失败且租约剩余不足 6 小时，主界面必须**提前预警**
  （"网络异常，Codex 将在 x 小时后无法使用"），而不是等用户被 403 打脸。

**F3.2.4 撤销（三条路径，逐级兜底）**

| 场景 | 机制 | 生效时间 |
|---|---|---|
| 正常退出客户端 / 退出登录 | 主动 `PUT status=inactive` 后 `DELETE` | **立即**（多副本部署下 ≤15 秒，见下） |
| 强杀 / 崩溃 / 断电 / 关机来不及 | 停止续签，租约到期 | ≤ TTL（1 天） |
| 客户端再也不启动 | 同上，且下次登录时清理孤儿 | ≤ TTL |

> ⚠️ **这里必须诚实记录代价**：把 TTL 从分钟级放宽到 1 天之后，
> **"关机后 key 失效"这个目标只在正常退出路径上是立即达成的**；
> 强杀 / 断电 / 蓝屏这类异常路径下，key 最长还能再活 **1 天**。
> 分钟级 TTL 的价值恰恰在异常路径，取舍点就在这里。
> 换来的是：不必两步签发、不必改后端、断网时用户有一整天的缓冲而不是 10 分钟。
> **若日后认为 1 天太长，只需调小续签写入的 `expires_at`，不涉及任何后端改动。**

> **撤销传播延迟（已查证）**：认证缓存 L1 是**进程内** ristretto，TTL **15 秒**；
> L2 是 Redis，TTL 300 秒但会被 `InvalidateAuthCacheByKey` 显式清除
> （`Update`/`Delete` 路径都调了）。
> 所以**单实例部署撤销是立即的；多副本部署其他副本最多滞后 15 秒**。
> 这 15 秒对本场景可以接受；若不可接受，只能改后端加跨副本失效广播。

**F3.2.5 已知豁免口（必须知道，不要当成漏洞排查）**

计费分支在 `skipBilling` 时**整块跳过**，包括过期检查
（`api_key_auth.go:171`）。命中条件是 `/v1/usage`、billing-info 类请求、
异步图片任务读取——**都是只读元数据端点，不含模型推理**。
即：租约过期后 key **仍能读 `/v1/usage`**，但**发不出任何一轮对话**。
产品意义上"授权已失效"成立，但描述时不要说成"key 完全无效"。

**F3.2.6 轮换（换 key 值）**：租约模型下，客户端每次启动本就会签发新租约，
定期轮换的必要性大幅下降。仍保留强制轮换：
key 被服务端禁用 / 额度耗尽 / 返回 401，或用户手动点【重置授权】。
**轮换只在"拉起 Codex 之前"这个边界执行**——Codex 是否每次请求重读 `auth.json`
未经验证，若只在启动时读一次，运行中换值会打断当前会话。

**F3.2.7 `auth.json` 的收尾**：撤销时把 `OPENAI_API_KEY` 恢复为快照中的原值
（原本没有则移除该字段）。**不得**因为撤销去动其他字段，尤其是官方 OAuth 令牌。

**F3.2.8 不可见性**：以上全部对用户不可见，只在主界面留一行状态
（如"授权有效 · 客户端运行中"）。**永远不回显 key 值本身。**

**F3.2.9 直接后果：客户端长期不运行 = Codex 用不了**

这是本需求的必然推论，不是缺陷。缓解手段见 **F9（托盘常驻与开机自启）**——
两者是一套设计：**自启 + 托盘让客户端事实上一直在线，用户几乎察觉不到租约的存在**，
而租约只在"用户真的把它关了很久"时才生效。

**AC**：
- 签发后在服务器上查该 key，`expires_at` ≈ 签发时刻 + 1 天；
- 客户端连续运行 3 天，key 始终有效且 `auth.json` **一次都没被重写**；
- **任务管理器强杀客户端**并保持不启动，1 天后 Codex 发对话必须收到 403 `API_KEY_EXPIRED`；
- 正常退出客户端，服务器上该 key 立即消失（单实例部署下下一次请求即被拒）；
- 断网并让租约剩余降到 6 小时以内，主界面应给出预警，而非事后报错；
- 崩溃重启客户端后，旧租约被清理，key 列表里不留孤儿。

**F3.3 分组切换必须与 key 同步**：用户在 F5 切换分组后，
`PUT /api/v1/keys/:id` 更新该 key 的 `group_id`。生效范围为**后续请求**，
不需要重启 Codex —— 界面必须如实这样告知，不能说"需要重启"。

**F3.4 写入前强制完整快照（硬性要求）**：
《注入草稿》§3.6 已实测官方应用会**按自己的 schema 整体重写 `config.toml`**，
丢弃 `[projects.*]`、`[hooks.*]`、`[env]` 等用户设置。因此：
- 每次写入前必须落盘**完整文件**副本（不是"只备份关注字段"）；
- 快照目录与保留策略需在设置页可见，并提供"恢复到写入前"按钮。

> 与 `AGENTS.md`「Release Installation Policy」的关系：该条禁止的是
> **打包/安装/升级时备份应用安装目录**；此处是**备份用户自己的 CLI 配置文件**，
> 两件事，不受该条约束。**勿以合规为由删掉此机制。**

**F3.5 路由守护**：按《注入草稿》§3.11.2，周期性复查 `config.toml` 是否仍指向共飞。
**小白版与工作台的差异**：工作台是弹卡片问用户；**小白版默认静默自动重新应用**，
只在状态条上留一行提示。理由：小白用户无法理解"官方重新登录会重置路由"这件事。
设置页可关掉自动重应用。

**F3.6 纯增强原则不变**：注入层任何失败都不得影响官方应用正常使用；
注入失败时 Codex 仍应正常启动，客户端只降级为"无状态条"。

**AC（F3 整体）**：
- 点一次按钮，Codex 起来后发一轮对话，服务器 usage 里能看到这条记录；
- 全流程用户没有看到、也没有输入过任何 `sk-` 字符串；
- 写入前的 `config.toml` 能在快照目录里逐字节找回；
- 手工把 `config.toml` 改回官方 provider，守护应在一个轮询周期内改回来并留痕；
- 拔掉注入（如强杀调试端口）后，官方应用不崩、不报错。

### F11 项目中心（保留，但第三层改为拉起官方 Codex）

**F11.0 与现有工作台的关键差异**

工作台的层级是 **项目中心 → 项目会话 → 自有 AI 对话**
（见 `ProjectSessionsViewModel` 的类注释）。本客户端保留前两层，
**第三层换成"在该项目目录下拉起官方 Codex 桌面应用"**：

```
工作台：  项目中心 → 项目会话 → 自研聊天 UI
本客户端：项目中心 → 项目会话 → 官方 Codex 桌面应用（定位到该项目）
```

默认路径不跟官方 UI 竞争：客户端只负责**把用户送到正确的项目里**，
并在此之前把授权准备好（F3）。自研聊天 UI 作为**备选**保留在 F12，
在 F11.4 的 A/B 都不成立时会升为该项目的默认动作。

**F11.1 项目中心（第一层）**：项目列表，每项显示名称、路径、最近打开时间、
路径是否仍存在。支持添加（选目录）、重命名、移除、归档。
数据模型直接复用 `ProjectRecord` 与 `IProjectRepository`（`AiSwitch.Core`，零依赖）
及其 SQLite 实现（`AiSwitch.Infrastructure`，仅依赖 `Microsoft.Data.Sqlite`）。
**路径失效的项目要明确标记**，不能点了才报错。

**F11.2 项目会话（第二层）**：列出属于该项目的既有 Codex 会话
（来源 `~/.codex/sessions/**/rollout-*.jsonl`，按项目路径归属），
显示时间、首条消息摘要。复用 `CodexConversationTranscriptReader`。
**只读展示，不在本客户端里渲染完整对话内容。**

**F11.3 启动（第三层）**：无论"新建会话"还是"继续某会话"，动作都是：

1. 先跑完 F3.1 的授权准备（确保租约有效、路由已写入）；
2. 拉起官方 Codex 桌面应用，**定位到该项目目录**；
3. 更新 `LastOpenedAt`。

**F11.4 ⚠️ 阻塞级未知：官方桌面应用能否被指定项目目录拉起？**

这是 F11 能否成立的前提，**必须在 M0 验证**，与 V-1′/V-2 同批。

已知：我们通过 COM `ActivateApplication(AUMID, args)` 传参是可行的
（`--remote-debugging-port` 已实机跑通，见《注入草稿》§3.5）。
但那个参数是 **Electron/Chromium 自己消费**的；
**"打开某目录"必须由 Codex 应用自身的参数解析支持，这一点完全未验证。**
Codex **CLI** 有 `--cd`，但桌面应用不等于 CLI。

按可行性递减的四条路，M0 逐条试：

| # | 路径 | 说明 |
|---|---|---|
| A | 命令行参数直接指定目录 | 最干净。需实测桌面应用接受什么参数 |
| B | **CDP 驱动 UI 打开目录** | 我们已有 CDP 通道（`CodexInjectionSession`），可脚本化点击其"打开文件夹"。**可行但脆弱**，官方改 DOM 即失效，须按纯增强原则失败即降级 |
| C | 降级：拉起 Codex + 把项目路径复制到剪贴板 + 提示用户自行打开 | 保底，一定能用，但不是"一键" |
| **D** | **改用自研聊天 UI 在该项目下开会话（F12）** | **A/B 不成立时真正的一键方案**——它本来就按指定工作目录启动 |

**若 A、B 都不成立**，把 **D 作为该项目的默认动作**，C 作为"仍要用官方客户端"时的退路。
走 C 时界面文案必须如实写成"已复制路径"，不得假装是一键定位。

**F11.5 ⚠️ 单实例锁的冲突**

《注入草稿》§3.5 已实测：Electron 单实例锁会让**新参数被既有实例吞掉**。
因此"Codex 已在项目 A 打开时，再从客户端打开项目 B"很可能**无效**。
必须先测清行为，再决定 UX：
- 若确实无效 → 客户端要检测到已有实例并明确提示（"Codex 已在运行，请在其中自行切换项目"），
  **绝不允许静默失败**；
- **绝不为此强杀官方进程**——§3.9 已确立"未授权不强杀"，会打断用户正在跑的任务。

**F11.6 ⚠️ "继续某会话"可能做不到**

《注入草稿》§6 风险 2 记录了官方 issue #14389：桌面应用可能不列出共享
`CODEX_HOME` 里的既有会话。若桌面端无法按 id 恢复指定会话，
F11.2 的"继续"退化为**只把项目打开**，由用户在 Codex 自己的界面里选会话。
**此时列表仍有价值**（让用户知道有哪些历史），但按钮文案必须改为"打开项目"，
不能叫"继续会话"——名不副实是最伤信任的一类 bug。

**AC**：
- 添加一个项目后，能列出该项目下的既有 Codex 会话；
- 点击启动后，Codex 打开且**当前工作目录就是该项目**（若 A/B 成立）；
- 路径已被删除的项目，在列表上就标记不可用，点击不产生异常；
- Codex 已在运行时再启动另一个项目，行为可预期且有明确提示，不静默失败；
- 全流程不出现强杀官方进程的行为。

### F12 自研聊天 UI（备选路径）

**F12.0 定位：兜底，不是主路径**

主路径始终是**拉起官方 Codex**。自研聊天 UI 的价值在于：
**它是 M0 全部未知项的共同兜底**——上面每一个"如果不成立怎么办"，答案都是它。

| 未知项 | 不成立时的后果 | 有了 F12 之后 |
|---|---|---|
| V-1′ 官方 OAuth 优先于 API key | 用户切了等于没切 | 自研 UI 直接用中转 key，不受 `auth.json` 优先级影响 |
| V-2 `.msix` 下载不通 / 装不上 | 用户根本用不上产品 | 无需桌面应用即可开始对话 |
| V-4 无法按目录拉起 Codex（F11.4） | 项目中心核心动作降级 | 自研 UI 天然就在指定目录里开会话 |

因此 F12 **不是锦上添花，是把产品的单点依赖拆掉**。

**F12.1 ⚠️ 必须先说清楚：它依赖的是 Codex CLI，不是桌面应用**

查证结果：`AiSwitch.Chat` 的 `CodexAppServerEngine` 启动的是
**`codex app-server --stdio`**（`CodexAppServerEngine.cs:399`），
即**官方 Codex CLI**，与 F2 要装的**桌面 MSIX 应用是两个东西**。

好消息与坏消息各一条：

- ✅ **授权工作零额外成本**：CLI 与桌面端共用 `CODEX_HOME`，读同一份
  `config.toml` / `auth.json`。《注入草稿》§3.8 证据 3 已实测 CLI 在这份配置下
  向中转站发出了 `POST /v1/responses`。**F3 写的路由对 CLI 直接生效。**
- ❌ **安装问题只是被搬家、没被消灭**：用户仍需装 Codex CLI。
  本机现状是 `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`（《注入草稿》§3.4），
  但**小白机器上不能假定它存在**。因此 F2 的检测与安装能力要覆盖 CLI，
  而不只是桌面应用。CLI 的安装渠道（npm / 官方安装器 / 随桌面应用附带）
  **未查证，列入 M0**。

> 所以"有了 F12 就不怕装不上桌面应用"这句话**只在 CLI 能装上时成立**。
> 不要在评审时把它说成万能兜底。

**F12.2 复用与代价**

复用 `AiSwitch.Chat`（`net8.0-windows`）。但它的依赖链是：

```
AiSwitch.Chat → AiSwitch.Core（零包依赖）
              → AiSwitch.Terminal → Porta.Pty + XTerm.NET
```

即**引入聊天会顺带引入一整套终端模拟器依赖**（两个 NuGet 包）。

**体积已按决策放宽（§7）**，因此：

- ✅ **聊天模块直接随主包分发**，不做按需下载、不做可选组件——
  给小白用户装一个"还要再下点东西才能用"的兜底方案，等于没有兜底；
- ✅ 也**不必**为了瘦身去收窄 `AiSwitch.Chat` 对 `AiSwitch.Terminal` 的依赖。
  若将来出于架构整洁想收窄，那是重构议题，不是本文的约束。

**但冷启动 < 2 秒没有放宽**（§7 中它仍是硬指标）。两者是不同的东西：
体积影响的是"下载一次"，启动耗时影响的是"每天开机都要等"。因此仍需在 M0 量一次
**引入聊天模块后的冷启动耗时**；若被拖慢，出路是**延迟加载**——
聊天相关程序集只在用户真正点开聊天时才加载，而不是在启动路径上初始化。

**F12.3 范围裁剪（v1）**

`AiSwitch.Chat` 自带三套引擎：`CodexAppServerEngine`、`ClaudeStreamJsonEngine`、
`GeminiAcpEngine`。本客户端 v1 **只接 Codex 一套**，另外两套不暴露入口——
小白版不做多 CLI 选择。终端页同样不做（§1.2 不变）。

**F12.4 入口与切换**

- **项目会话页**：在 F11.3 的启动按钮旁提供【在共飞里对话】作为并列选项。
  这同时是 F11.4 的**降级路径 D**：A/B 都不成立时，它是唯一能做到
  "点一下就在这个项目里开始对话"的方案（C 能用但不是一键）；
- **主界面**：提供一个不依赖项目的【快速对话】入口；
- 用户选择哪条路要**记住**（按项目记忆），不要每次都问。

**F12.5 不与官方抢**

- 自研 UI 与官方 Codex **不得同时对同一项目发起会话**——都写同一份
  `CODEX_HOME`，并发写入会话文件的行为未验证。检测到官方 Codex 正在运行时，
  【在共飞里对话】需给出提示；
- 自研 UI 产生的会话同样落在 `~/.codex/sessions/`，因此 F11.2 的会话列表
  **对两条路径是统一的**——这是把它们放在同一个项目中心下的正当理由。

**AC**：
- 桌面应用完全没安装的机器上，只要 CLI 在，用户能完成一轮完整对话；
- 自研 UI 发出的请求出现在中转站 usage 记录里，分组与倍率与 F5 显示一致；
- 自研 UI 开的会话，能在 F11.2 的会话列表里看到；
- CLI 未安装时，给出明确的安装引导，而不是抛进程启动异常；
- 引入聊天模块后，**冷启动仍 < 2 秒**（体积不再是验收项，见 §7）。

### F10 充值（客户端内完成）

**F10.0 一条不可退让的安全红线**

**客户端绝不收集任何支付凭据**——不做银行卡号、CVV、有效期、网银密码的输入框，
一个都不做。客户端只做两件事：**展示收款二维码**、**把用户送到支付方页面**。
真正的付款动作始终发生在支付方（微信/支付宝/Stripe 等）自己的界面里。

> 这不只是合规姿态：一旦客户端碰卡号，PCI 相关责任、本地日志泄漏风险、
> 以及"小白客户端被仿冒"的钓鱼面全部落到我们头上。**评审时这条不接受例外。**

**F10.1 入口**：主界面余额卡片的【去充值】、以及余额不足时的提示。
`payment_enabled` 为 false 时**整个模块隐藏**。

**F10.2 拉取可用方式**：`GET /api/v1/payment/checkout-info`
（一次拿到支付方式、限额区间、套餐列表，优于分别调 `/config` + `/plans` + `/limits`）。
客户端**不得**自行硬编码支付方式清单或金额区间——两者都由服务器下发。

**F10.3 两种订单类型**（后端 `order_type` 已区分）：

| 类型 | 含义 | 界面 |
|---|---|---|
| 余额充值 | 用户填金额（须落在服务器给的限额区间内） | 金额输入 + 常用面额快捷键 |
| 套餐订阅 | 选 `plan_id` | 套餐卡片，须显示分组名与**倍率**（`/checkout-info` 已带 `rate_multiplier` 等字段），口径与 F5.2 一致 |

**F10.4 下单与付款**：`POST /api/v1/payment/orders`，
携带 `amount` / `payment_type` / `order_type` / `plan_id`，并显式传 `is_mobile: false`
（后端在未传时会用 User-Agent 猜，桌面客户端不该让它猜）。

响应含 `pay_url` 与 `qr_code`（`internal/service/payment_order.go:742-743`），据此分两路：

- `qr_code` 非空 → **在客户端内原生渲染二维码**给用户扫。这是小白版的主路径：
  不跳出、不开浏览器，体验最短；
- 否则 `pay_url` → **用系统浏览器打开**。不要用内嵌 WebView 承载支付页——
  内嵌浏览器会隐藏地址栏与证书信息，恰好剥夺用户识别钓鱼的能力。

**F10.5 结果确认（不能只靠回调）**：下单后轮询
`POST /api/v1/payment/orders/verify` 或 `GET /api/v1/payment/orders/:id`
确认到账；同时**必须**刷新余额（F4）。

- 轮询要有上限（如 5 分钟后转为手动【我已支付，刷新】）；
- **超时不等于失败**：文案必须是"尚未确认到账"并给出订单号 + 【查看订单】，
  绝不能说"支付失败"——用户的钱可能已经出去了，这是最不能含糊的一处文案。

**F10.6 订单记录**：`GET /api/v1/payment/orders/my`，展示时间、金额、状态、订单号，
支持复制订单号。未支付订单可 `POST /orders/:id/cancel`。

**退款：已决策 —— 客户端不做退款流程**，只在订单详情提供【联系我们】
（取 `/settings/public` 的 `contact_info`）。不调 `/orders/:id/refund-request`。
> 理由：退款是需要人工判断的低频操作，做成自助入口会带来"点了没反应"的预期落差；
> 小白用户此时最需要的是一个能对话的人。

**F10.7 卡密兑换**：`POST /api/v1/redeem` + `GET /api/v1/redeem/history`。
这条链路无需支付方参与，实现成本最低，**建议优先做**——
它同时是支付方全挂时的兜底充值途径。

**AC**：
- 客户端全程不存在任何银行卡/CVV 输入控件（代码评审 + UI 走查双重确认）；
- 支付方式与金额区间全部来自 `/checkout-info`，改服务器配置后客户端无需发版；
- 扫码支付成功后 60 秒内主界面余额自动更新；
- 拔网/关闭支付页后重新进入，订单状态可查、不产生重复下单；
- 轮询超时的文案经过评审，不含"失败"字样。

### F9 托盘常驻与开机自启

F3.2 的租约模型要求客户端尽量在线，F9 是让这件事对小白用户**自然发生**的配套设计。
两者必须一起实现，只做其一都会让产品变得难用。

**F9.1 安装时勾选开机自启**：安装程序提供【开机时自动启动共飞客户端】复选框，
**默认勾选**。理由：客户端不在线 Codex 最终会用不了，默认关闭等于默认把产品做坏。
复选框旁必须有一句说明，不能只有一个光秃秃的选项。

**F9.2 自启的实现约束**：
- 写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（当前用户），
  **不得**写 HKLM、不得创建计划任务、**不得要求管理员权限**；
- 自启时以**最小化到托盘**的方式启动，不弹主窗口、不抢焦点；
- 自启启动后自动完成续签（F3.2.3），全程无需用户交互。

**F9.3 托盘常驻**：
- 点窗口的关闭按钮 **= 最小化到托盘**，不退出进程。首次这样做时给一次气泡提示
  说明"程序仍在后台运行"，之后不再打扰；
- 托盘图标菜单（自上而下）：
  **当前分组 + 倍率（不可点，纯状态行）** → **切换分组（子菜单，见 F9.7）** →
  分隔线 → 显示主界面 → 启动 Codex → 分隔线 → 【退出】；
- 托盘图标需体现状态（正常 / 授权异常 / 未登录），让用户一眼看出是否还在线；
- 鼠标悬停 tooltip 显示：当前分组 · 倍率 · 余额。

**F9.4 真正退出的确认**：只有托盘菜单的【退出】才结束进程。执行前：
- 若检测到 Codex 正在运行，**必须二次确认**并说明"退出后 Codex 将无法继续使用共飞额度"；
- 退出时执行 F3.2.4 的主动撤销。

**F9.5 设置页可改**：开机自启开关必须能在设置页（F8）里随时改，
不能只有安装时那一次机会。改动即时生效。

**F9.6 主界面常驻说明**：主界面固定显示一句"客户端保持运行，Codex 才能使用共飞额度"，
配当前授权状态。**不允许把这件事只写在帮助文档里。**

**F9.7 托盘快速切换分组（重点）**

最小化到托盘后，用户**不需要唤回主窗口**就能换组——这是常驻形态下最高频的操作。

- 子菜单列出 F5.3 的可选分组，每项文案形如 **`标准组  ×1.0`**，
  当前组打勾。倍率必须直接印在菜单项上，**不能只显示组名**——
  倍率就是用户切组的唯一理由，藏起来这个功能就没意义了；
- 处于高峰时段的组，文案追加高峰标记（如 `×1.0 → ×1.5 高峰`）。
  由于高峰随时间变化，**菜单项文案必须在每次菜单弹出时现算**，不能缓存成品字符串；
- 点击即切，走 F5.4 同一条 `PUT /api/v1/keys/:id`。切换结果用**气泡通知**告知
  （成功："已切换到 标准组 ×1.0"；失败：说明原因并**回滚勾选态**）；
- 切换后主窗口（若开着）与托盘 tooltip 必须同步更新，两处不允许出现不一致；
- 与 F3.3 一致：**切换即时生效于后续请求，不需要重启 Codex**，气泡文案要这样写。

**性能约束**：托盘菜单必须**瞬开**，不允许在弹出时同步等网络。
分组列表与倍率走本地缓存，缓存在登录后、每 6 小时、以及每次切换成功后刷新。
缓存为空时（如刚启动还没拉到）子菜单显示"加载中"并禁用，而不是卡住菜单。

**未登录时**：整个分组区域（状态行 + 子菜单）隐藏，只留【显示主界面】与【退出】。

**AC**：
- 勾选自启后重启电脑，客户端自动起来且**只在托盘**，主窗口不弹出；
- 自启后不做任何操作，租约在后台完成续签；
- 点关闭按钮后进程仍在，托盘图标可唤回主界面；
- 托盘【退出】+ Codex 正在运行 → 必须弹确认；确认后服务器上 key 立即消失；
- **主窗口全程不打开，仅用托盘菜单即可完成一次分组切换**，且下一轮 Codex 请求
  按新分组计费；
- 托盘菜单每一项都印着倍率，且高峰时段的标记会随时间变化；
- 断网时点切换 → 气泡报错并回滚勾选态，菜单不出现"看起来切成功了"的假象；
- 托盘菜单在弱网下依然瞬开（不等网络）；
- 全程不出现 UAC 提权弹窗。

### F4 主界面信息卡（余额与用量）

对标网页版用户面板，**做减法**。v1 展示：

| 卡片 | 字段 | 数据源 |
|---|---|---|
| 账户 | 用户名、余额、冻结余额 | `GET /api/v1/auth/me` 或 `/api/v1/user/profile` |
| 今日用量 | 请求数、token 数、消费金额 | `GET /api/v1/usage/dashboard/stats` |
| 近 7 日趋势 | 一条迷你折线 | `GET /api/v1/usage/dashboard/snapshot-v2?granularity=day` |
| 订阅（如有） | 套餐名 + 剩余进度 | `GET /api/v1/subscriptions/summary`；无订阅则整卡不显示 |

**F4.1 刷新策略**：进入主界面刷新一次 + 每 60 秒轮询 + 手动刷新按钮。
**F4.2 失败降级**：某个卡片取数失败只置灰该卡片并显示"暂时取不到"，
**不允许**整页报错或退出登录。

> ⚠️ **与 M1 会话管理器的冲突（2026-08-01 记，实现时必须处理）**：
> M1 定的规则是"只有服务器**明确拒绝**才登出"，而卡片端点返回的 401
> 恰恰就是一次明确拒绝。若直接沿用，**一张卡片 401 就会把用户踢下线**，
> 直接违反本条。两条实现约束：
> - 四张卡必须**各自独立失败**。一个 `Task.WhenAll` 套一个 try/catch
>   在结构上就违反本条——任一卡失败会连坐其余三张。
> - 卡片层的 `Unauthenticated` 只能降级该卡片，**不得**接到
>   `RelaySessionManager` 的登出路径。只有刷新令牌与 `auth/me`
>   这两条路径才有资格结束会话。
**F4.3 余额不足**：余额低于阈值时卡片变色并给出【去充值】，跳 F10 充值页。
阈值**不要在客户端写死**——`/settings/public` 已提供 `balance_low_notify_threshold`
与 `balance_low_notify_recharge_url`（`setting_handler.go:93-94`），直接用服务器的值。

**AC**：
- 断网 60 秒再恢复，界面自行恢复，无需重启；
- 后端限流（面板有按用户限流）触发时不刷屏报错，退避重试。

### F5 分组显示与切换

**对标物已明确**：网页版**新建/编辑 API Key 对话框里的「分组」属性**——
即 `frontend/src/views/user/KeysView.vue` 的 `groupOptions`（第 1411 行起）
喂给的那个下拉。本客户端把这个"藏在 key 编辑弹窗里的属性"提升为**主界面一等公民**，
因为对小白用户来说，选哪个组、倍率多少，是他唯一需要理解的计费概念。

网页版该下拉每个选项携带的字段（客户端应保持同一套，不多不少）：

| 网页版字段 | 来源 | 客户端是否展示 |
|---|---|---|
| `label` | `group.name` | ✅ 主要标识 |
| `description` | `group.description` | ✅ 副标题 |
| `rate` | `group.rate_multiplier` | ✅ 见 F5.2 |
| `userRate` | `GET /groups/rates` 中该组的专属倍率 | ✅ **优先于 `rate`** |
| `peakRateEnabled` / `peakStart` / `peakEnd` / `peakRateMultiplier` | group 同名字段 | ✅ 见 F5.2 |
| `subscriptionType` | `group.subscription_type` | ✅ 标签 |
| `platform` | `group.platform` | 🔶 仅用于过滤（F5.3） |

网页版还给这个下拉配了**按名称/描述搜索**的过滤框；客户端在组数量多时同样需要，
组少时可省略。

**F5.1 显示当前分组**：名称、描述、**倍率**、平台标识。
**F5.2 倍率的计算口径**（必须与网页版一致，见 `frontend/src/views/user/KeysView.vue`）：

```
基础倍率 = 用户专属倍率(GET /api/v1/groups/rates 中该 group 的值)
          ?? 分组默认倍率(group.rate_multiplier)
高峰时段：不在客户端计算"当前是否高峰"，只展示时段标签
          "peak_start-peak_end ×peak_rate_multiplier (UTC±HH:MM)"
```

> ⚠️ **本条已按实现修正（2026-08-01，M2）**。原伪代码有两处会导致显示与实际扣费不符：
>
> 1. **高峰倍率只对订阅类型分组生效。** 后端 `Group.PeakMultiplierAt`
>    第一个判断就是 `!g.IsSubscriptionType() → 1.0`（`internal/service/group.go:257`）。
>    原伪代码缺这个前提，会给标准组显示一个永远不会被计费的高峰倍率。
> 2. **不要在客户端算"当前时刻是否落在窗口内"。** `peak_start`/`peak_end`
>    是**服务器时区**的墙上时间（`now.In(timezone.Location())`），
>    按本机时区判定会让跨时区用户看到的倍率和实际扣费对不上。
>    网页版**故意**只展示时段标签而不折算（`frontend/src/utils/peak-rate.ts`），
>    客户端保持一致。时区标注取 `/settings/public` 的 `server_utc_offset`。
>
> 另两条实现约束：
> - **窗口不跨天**。后端 `start >= end` 直接返回 1.0，且 `ValidatePeakRateConfig`
>   明确"不支持跨天"，客户端不做环绕处理。
> - **`?? ` 是 nullish 语义**。`/groups/rates` 中"没有该组"与"该组为 0 倍（免费）"
>   是两回事，后者是合法配置。C# 侧必须用 `TryGetValue` 而非 `GetValueOrDefault`。

**F5.3 可选分组列表**：`GET /api/v1/groups/available`（后端已按订阅/权限过滤，
客户端**不得**再自行放宽）。列表按平台过滤，只展示与 Codex 相关的平台分组。

**F5.4 切换分组**：点击即切，落到 `PUT /api/v1/keys/:id` 的 `group_id`。
切换成功后主界面即时反映新分组与新倍率。

> ⚠️ **请求体只能带 `group_id`，不得附带 `expires_at`。**
> 该接口对 `expires_at` 是三态语义（`api_key_handler.go:225-238`）：
> 字段缺失=不改，**空串=清除过期时间**，RFC3339=设为该值。
> 若请求体带上一个默认空串的 `expires_at`，用户点一下"切换分组"
> 就会把 F3.2 的 1 天租约变成**永不过期的 key**，且完全无感——
> 租约模型整个失效。已由测试 `SwitchingGroupsSendsGroupIdAndNothingElse` 钉死。
>
> **无托管 key 时的分支**：托管 key 由 F3.2（M3）签发。M2 阶段若尚无 key，
> 分组选择存本地，M3 签发时按 `POST /keys` 的 `group_id` 落地（F3.2.2 本就如此规定）。
> 这是正常分支，不是占位实现。

**F5.5 切换失败**：如分组已下线、订阅过期，回滚 UI 选中态并说明原因。

**AC**：
- 同一账号在网页版看到的可选分组集合与倍率数值，与客户端**完全一致**；
- 切换后无需重启 Codex，下一轮请求即按新分组计费；
- 独占/需订阅的分组不会出现在列表里。

### F6 注入状态条与限额切换（复用）

直接复用 `CodexInjectionSession` + `CodexLimitSentinel` + `RelaySwitchOrchestrator`。
**差异点**：

- 状态条内容改为"共飞 · <分组名> · 余额 <x>"，数据由 WPF 侧经 CDP `PushStateAsync` 推送；
- **注入的 JS 绝对不允许自己发起对中转站的网络请求**。工作台时代的"只连 127.0.0.1"
  原则在直连场景下不再成立——远端调用意味着把登录令牌或授权 key 暴露到官方应用的
  渲染进程里。**状态一律由宿主进程推送，页内只负责渲染。**
- 限额提示的措辞沿用已单测锁定的两条要点（本机记录保留 / 云端任务暂停）。

### F7 凭据存储与安全

**F7.1** 登录令牌与缓存的中转站 key 用 **DPAPI（`CurrentUser` 作用域）** 加密落盘，
与工作台 `LocalSub2ApiAccountSessionStore` 同一套做法。
**F7.2** 任何凭据不得写入日志、不得进临时文件明文、不得出现在窗口标题或错误弹窗。
**F7.3** `auth.json` 里的 key 是必需的（Codex 只认这个文件），
但客户端不得在自己的 UI 中回显它。
**F7.4** 卸载/退出登录时清除本地凭据缓存。

### F8 设置与诊断

服务器地址、开机自启、是否自动重应用路由（F3.5）、快照目录与恢复、
"一键收集诊断信息"（脱敏后的日志 + 环境检测结果，供支持人员排查）、版本与更新。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 启动速度 | 冷启动到登录页 **< 2 秒（硬指标，未放宽）** |
| 体积 | **不设硬上限**（已放宽）。参考区间 250 MB 以内；超出时需说明换来了什么 |
| 首次下载体验 | 体积放宽的代价落在**用户下载我们的安装包**上。若最终体积明显偏大，安装程序必须显示进度与预计剩余，并支持断点续传 |
| 网络 | 全程 HTTPS；支持系统代理；超时与重试必须有上限，不得无限重试 |
| 错误呈现 | 每条错误都要有"用户能做的下一步"，禁止裸露 HTTP 码/堆栈 |
| 隐私 | 不采集对话内容；注入的 JS 不得回传页面文本（沿用哨兵现有约束） |
| 日志 | 本地滚动日志，默认 7 天；脱敏后方可导出 |
| 可访问性 | 全键盘可达；主界面文字对比度达 WCAG AA |
| 数据权威 | 服务器是用量与余额的唯一权威；客户端只缓存展示，不做本地推算 |
