# 共飞 Paw 远程操作 —— 整体架构

> 状态：**整体架构梳理，未动代码**。整理于 2026-09-01。
> 本篇是拓扑与职责的**唯一权威**，前两篇里与拓扑相关的部分以本篇为准：
> - [`共飞客户端寄宿 Paseo 手机远程方案.md`](共飞客户端寄宿%20Paseo%20手机远程方案.md) 的 **§7（手机端三阶段接入）作废** ——
>   不再有"官方 Paseo App → 自建 relay → 自有品牌"的分期，直接就是自建 relay + Paw。
>   其余部分（可行性、V-1 实测、体积、通知选型）继续有效。
> - [`共飞客户端 × Paseo 核心封装架构设计.md`](共飞客户端%20×%20Paseo%20核心封装架构设计.md) 的 **§0 结论与 §2 表格里"🔴 不可强制"三行需按本篇 §1 重新解读**；
>   能力矩阵、生命周期状态机、配置生成规范、工程结构继续有效。

前提（用户 2026-09-01 给定）：

1. 手机端是**正在做的共飞 Paw 端**，**不含任何 Paseo 逻辑**；
2. Paw 有一个**共联模式**（目前是构想，后面要做），用于连通 PC 客户端并实施操作；
3. **Paseo 的转发服务（relay）与共飞服务端部署在同一台服务器上**。

## 1. 结论：这个拓扑把上一版最大的问题解决了

上一篇卡住的地方是：Paseo 里**每个通过鉴权的会话都是 owner**
（`websocket-server.ts:502`），所以只要手机端是官方 Paseo App，
"只封装核心"就只是界面级的——手机能开终端、能读写文件，拦不住。

**换成 Paw 之后，这个问题不是被缓解，是被绕开了：**

> Paw 不说 Paseo 协议。整条链路上**唯一的 Paseo 客户端是我们自己写的适配层**。
> `create_terminal_request` 之所以到不了 daemon，不是因为 daemon 拒绝，
> 而是因为**我们的栈里没有任何一处能发出这条消息**。

能力矩阵里那三行 🔴 的等级因此改写：

| | 上一版（官方 App） | 本拓扑（Paw） |
|---|---|---|
| 终端 / 文件读写 / workspace | 🔴 不可强制（会话是 owner） | ⚫ **不可达**（栈里没有发出口） |
| 封装边界在哪 | 只在 UI 上 | 在**协议上**——共联协议里没有的东西就是不存在 |
| owner 权限归谁 | 用户的手机 | **我们的服务端适配层**（受我们自己的代码约束） |

代价见 §8：这条链路把"零知识"换掉了，需要产品上明确接受。

## 2. 全链路拓扑（每一跳的协议都写清楚）

```
┌──────────────┐
│  共飞 Paw 端  │  手机 / 桌面；不含任何 Paseo 逻辑
└──────┬───────┘
       │ ① 共飞自有协议（JWT session，共联模式）
       ▼
╔══════════════════════════════════════════════════════════╗
║  共飞服务端（一台机器）                                      ║
║                                                          ║
║  ┌────────────────┐        ┌───────────────────────────┐ ║
║  │ sub2api / Paw   │◄──②──►│ Paseo 客户端适配层           │ ║
║  │ 业务与鉴权       │  进程内 │ Node + @getpaseo/client    │ ║
║  └────────────────┘  或本机  │ （窄契约的服务端消费者）      │ ║
║                              └─────────────┬─────────────┘ ║
║                                            │ ③ Paseo WS    ║
║                              ┌─────────────▼─────────────┐ ║
║                              │ paseo-relay（同机部署）      │ ║
║                              └─────────────▲─────────────┘ ║
╚════════════════════════════════════════════╪══════════════╝
                                             │ ④ 出站长连（PC 主动连出，
                                             │    不开入站端口、不做端口映射）
╔════════════════════════════════════════════╪══════════════╗
║  用户 PC —— 共飞小白客户端（宿主）             │              ║
║                                  ┌─────────┴─────────┐    ║
║  生命周期 / 路由 / 同意 / 目录白名单 │ paseo daemon      │    ║
║  ──────────────────────────────► │ 仅监听 127.0.0.1   │    ║
║          （本机窄契约，见 §6）      └─────────┬─────────┘    ║
║                                              │ spawn       ║
║                                    ┌─────────▼─────────┐   ║
║                                    │ codex app-server   │   ║
║                                    └─────────┬─────────┘   ║
║                                              │ 读           ║
║                                    ~/.codex/config.toml    ║
╚══════════════════════════════════════════════╪═════════════╝
                                               │ HTTPS
                                        共飞中转站 (sub2api)
```

四跳的性质：

| 跳 | 两端 | 协议 | 谁实现 |
|---|---|---|---|
| ① | Paw ↔ 共飞服务端 | **共飞自有**（共联模式，JWT 会话） | 我们（新做，见 §6） |
| ② | 共飞业务 ↔ Paseo 适配层 | 进程内调用 / 本机 IPC | 我们（新做） |
| ③ | 适配层 ↔ relay ↔ daemon | **Paseo 官方协议 + relay E2EE** | Paseo（我们只当客户端） |
| ④ | daemon → relay | Paseo relay 出站长连 | Paseo |

**支撑这个拓扑成立的关键事实**：官方 SDK `PaseoClientConfig` 同时接受
`url`（指向 relay 的客户端入口）与 `e2ee.daemonPublicKeyB64`
（`packages/client/src/index.ts:58-80`）。也就是说
**服务端适配层用发布版 `@getpaseo/client` 就能经 relay 连到用户 PC 的 daemon，不需要 fork Paseo。**

## 3. 组件职责（谁负责什么，谁不许碰什么）

| 组件 | 负责 | 明确不负责 |
|---|---|---|
| **Paw 端** | 会话 UI、发提问、看时间线、收通知、选"操作哪台电脑" | 不认识 Paseo，不持有 offer/口令，不选工作目录 |
| **共飞服务端（业务）** | 用户鉴权、绑定关系、共联通道、把共联请求翻成窄契约 | 不直接说 Paseo 协议 |
| **Paseo 客户端适配层** | 唯一说 Paseo 协议的地方；连 relay、建会话、订阅时间线与通知 | 不做业务判断（不选目录、不定沙箱、不管计费） |
| **paseo-relay（同机）** | 转发加密字节，打通 NAT | 不做鉴权与授权 |
| **PC 小白客户端** | daemon 生命周期与进程笼、`~/.codex` 路由与沙箱地板、目录白名单、用户同意、本机 UI | 不承载手机业务逻辑 |
| **paseo daemon** | 拉起并管理 codex 会话、时间线、通知 | 只监听 127.0.0.1，永不对外 |
| **codex app-server** | 真正干活 | —— |

一条要写进评审清单的规则：**`cwd` 永远由 PC 客户端决定**。
服务端适配层只能引用 PC 侧登记过的"目录键"，不能传路径（沿用架构设计 §3）。
否则手机端就能把爆炸半径扩到全盘。

## 4. 绑定：不再需要扫码

Paseo 的配对凭据就是一小段 JSON（`packages/protocol/src/connection-offer.ts`）：

```json
{ "v": 2, "serverId": "...", "daemonPublicKeyB64": "...", "relay": { "endpoint": "...", "useTls": true } }
```

PC 客户端**本来就持有一个已登录的共飞会话**，所以：

```
用户在 PC 客户端点"允许手机操作这台电脑"
  → 弹一次授权告知（能干什么、爆炸半径在哪）
  → 客户端开 relay，取 pairing offer
  → 通过已有的登录会话 POST 给共飞服务端（连同 daemon 口令）
  → 服务端记为"该用户的已绑定电脑：<机器名>"
  → Paw 端刷新，多出一台可操作的电脑
```

**QRCoder 那条路可以删掉**，二维码只在"跨账号绑定"这种非小白场景才需要（当前不做）。

解绑要求（两端都要能发起）：
- PC 端"停止手机操作" → 关 relay + 通知服务端删除绑定；
- Paw / 服务端侧"解绑这台电脑" → 服务端删凭据；PC 端下次心跳感知后关 relay。
- **必须支持轮换**：换 `PASEO_HOME`（`serverId` 随之变）即可作废旧 offer，不需要重装客户端。

## 5. 一次远程对话的时序

```
Paw: 「帮我把这个测试修好」
  ①→ 共飞服务端：校验 JWT、查该用户的已绑定电脑、查目录键是否合法
  ②→ 适配层：agents.create{model, cwdKey, prompt}
  ③→ relay → daemon：create_agent（cwd 由 PC 侧登记的键解析）
      daemon → codex app-server：一轮
      daemon → agent_stream / agent_attention_required(finished)
  ③← 适配层收流，做 100ms 合并
  ②← 共飞服务端
  ①← Paw：增量渲染 + 完成通知
```

同一时刻 PC 客户端本机也订阅着同一个 daemon（本机窄契约），
所以**PC 上能看到手机发起的会话**，这是"同一台电脑、两块屏"的自然结果，不需要额外同步机制。

## 6. 共联模式要承载什么（契约有两个消费者）

共联是构想阶段，所以这里定的是**它必须能表达什么**，不是怎么实现。

窄契约（架构设计 §5.3 那 12 个操作）现在有**两个消费者、两种传输**：

| 消费者 | 传输 | 说明 |
|---|---|---|
| PC 客户端 C# | 本机命名管道 JSONL | 本机 UI 用 |
| 共飞服务端适配层 | 进程内 / 本机 IPC | 给 Paw 用 |

共联协议（跳 ①）要能表达的，就是同一组操作**再加两个多机语义**：

```
devices.list                     # 我有哪些已绑定电脑，在线否
devices.select <deviceId>        # 本次会话操作哪一台
agents.list / create / send / stop / archive
timeline.subscribe / unsubscribe
notifications.subscribe
workdirs.list                    # PC 侧登记过的目录键（只回键与显示名，不回真实路径）
```

**不在表里的一律不做**：终端、文件浏览、git、schedule、插件、语音。
这不是"暂时不做"，是**协议上不存在**——这正是 §1 那条"不可达"的落点。

要求：两个消费者**共用同一份操作定义**（同一份 schema 生成两边的类型），
否则手机能干的和 PC 能干的会慢慢漂开，最后没人说得清封装边界在哪。

## 7. 多用户模型（这是本拓扑新增的最大一块服务端工作）

前两篇都默认"单用户单机"。放到共飞服务端上以后不成立了，必须显式设计：

| 需要的东西 | 说明 |
|---|---|
| 绑定表 | `用户 ↔ 已绑定电脑（serverId, 机器名, offer, 口令, 最后在线时间）` |
| 凭据存储 | offer + daemon 口令**按用户加密存储**，不明文落库（§8.2） |
| 连接池 | 适配层不能给每个手机请求新建一条 relay 连接；按 `serverId` 复用，空闲回收 |
| 在线态 | PC 离线时 Paw 要显示"这台电脑不在线"，而不是超时报错 |
| 隔离 | 一个用户的适配层连接绝不能被另一个用户的请求复用；`serverId` 必须校验归属 |
| 并发 | 同一台 PC 可能同时被 Paw 与 PC 本机操作；会话本身是 daemon 侧串行的，UI 要能表达"正在忙" |
| 配额 | 计费仍在中转站（codex 请求经 `~/.codex` 路由过去），**服务端适配层不参与计费** |

估算：这块比 PC 侧的宿主工作更重，且是新代码，不复用 Paseo。

## 8. 信任边界：两处明显变差，必须产品上认下来

### 8.1 relay 的"零知识"在这个部署下不成立

Paseo relay 的设计前提是**中继方看不到内容**（Curve25519 + NaCl box，端到端在
daemon 与客户端之间）。但在本拓扑里，**客户端那一端也是我们**——
适配层持有会话密钥，明文在共飞服务端内存里。

后果：

- Paseo 官方那句"你的代码不离开你的机器"**不再适用于这个部署**，不要照抄进宣传；
- 用户通过 Paw 发起的提问、agent 的输出、文件片段，**共飞服务端在技术上可读**；
- 这需要一次明确的产品决定 + 用户告知，不能塞进协议附录。

可选的缓解（成本递增，先记着不一定做）：
① 服务端只做转发不落盘（内存中转，不持久化时间线）；
② 端到端加密上移到 Paw ↔ PC 客户端之间，服务端只转密文——
   但那样服务端就没法做"会话列表/搜索/通知"这些业务，等于放弃一部分产品能力；
③ 明确的数据保留策略 + 用户可删。

### 8.2 凭据集中化：一次服务端泄露 = 一批用户电脑被远程操作

绑定表里的 offer + daemon 口令，合起来就是"连上这台 PC 的 daemon"的完整凭据。

硬要求：

- **按用户加密存储**，密钥不与业务库同权限；
- **可撤销**：PC 端一键作废（换 `PASEO_HOME` → `serverId` 变），不需要重装；
- **可审计**：每次适配层建立连接都记 `用户 / serverId / 时间 / 来源`；
- PC 端必须能看到"当前有几台设备/几条会话在操作我这台电脑"。

> ✅ **V-9 已实测（2026-09-01），答案是否定的，而且比预想更严重：
> relay 路径完全绕过 daemon 口令。**
> 实测：daemon 开着口令（`authRequired:true`），直连 `http://127.0.0.1:6799/api/agents`
> 无 bearer → **401**；但同一时刻用**不带任何口令**的客户端经 relay 连上去，
> `agents.list` / `projects.list` 全部成功（见 §12）。
> 代码侧对得上：`bootstrap.ts:1697` 的 relay 挂载调用
> `attachExternalSocket(ws, metadata)` **不传 admission**，
> 于是落到默认的 `OWNER_SESSION_ADMISSION`（`websocket-server.ts:500`）；
> 只有 Hub（`bootstrap.ts:1209`）才传缩权的 admission。
> 而 relay 客户端侧只需要 offer 里的 **公钥**——那不是秘密。
>
> **结论：offer 就是完整的 owner 凭据，等价于"这台电脑的 root 会话"。**
> §8.2 的所有要求因此从"建议"升级为"必须"，并额外增加两条：
> ① 绑定表里的 offer **必须按用户加密存储**，任何日志/工单/客服系统都不得出现它；
> ② PC 端必须提供**一键作废**（换 `PASEO_HOME` → `serverId` 变），
> 因为口令轮换对 relay 路径**没有任何效果**。

## 9. 部署形态

同一台服务器上三样东西：

| 进程 | 说明 |
|---|---|
| 共飞服务端（sub2api，Go） | 现有 |
| `paseo-relay`（**Elixir**，独立仓库 `getpaseo/paseo-relay`） | 新增运维负担；本仓库里那份 Cloudflare 实现是遗留代码，官方已不部署 |
| Paseo 客户端适配层（Node） | 新增；建议与业务同机不同进程，用本机 IPC，便于单独重启与限权 |

要点：

- daemon 侧配置 `daemon.relay.endpoint` 指向我们自己的 relay，
  `useTls` / `publicUseTls` 按证书情况开；**不再走 `relay.paseo.sh`**；
- relay 是**唯一对公网暴露**的入口，PC daemon 与适配层都不开公网端口；
- 三个进程的版本要一起发：daemon（PC 上）与适配层用的 `@getpaseo/client`
  必须同一 Paseo 大版本，relay 的协议版本（`CURRENT_RELAY_PROTOCOL_VERSION = "2"`）也要对齐。
  **升级 Paseo 是一次三处联动**，写进发布清单。

## 10. 与前两篇的差异一览

| 主题 | 前两篇 | 本篇 |
|---|---|---|
| 手机端 | 官方 Paseo App（MVP）→ 以后自研 | **共飞 Paw**，从头就是自己的 |
| 手机端是否懂 Paseo | 懂（就是 Paseo 客户端） | **完全不懂** |
| 配对 | 扫二维码（QRCoder） | **服务端静默绑定**，无需扫码 |
| relay | 先用官方公用，再自建 | **一步到位自建、与业务同机** |
| owner 权限问题 | 🔴 拦不住 | ⚫ **不可达**（栈里发不出那些消息） |
| 窄契约消费者 | 只有 PC 的 C# | **两个**：PC C# + 服务端适配层 |
| 多用户 | 不涉及 | **新增一整块服务端工作**（§7） |
| 零知识 | 保持（官方 App 端到端） | **作废**（客户端那端在我们服务器上） |
| PC 客户端职责 | 宿主 + 手机入口 | **只剩宿主**：生命周期、路由、同意、目录白名单 |

## 12. V-10 实测记录（2026-09-01，本机 DESKTOP-9GRMVU2）

### 12.1 结论

**协议链路成立。** 用**发布版** `@getpaseo/client`，经**自己跑起来的 relay**，
带 E2EE 连上 PC 上的 daemon，并完成了真实的鉴权往返。
也就是说 §2 里的跳 ③ 不需要改 Paseo 任何一行代码。

### 12.2 做法与结果

链路：`Node 客户端脚本（模拟共飞服务端适配层）` → `本机 relay:8799` → `PC daemon:6799`。

1. **relay**：本仓库 `packages/relay` 的 Cloudflare 实现，用 `wrangler dev --local`（workerd）跑起来。
   关键动作：**必须去掉 `PASEO_RELAY_UPSTREAM`**——生产 `wrangler.toml` 里设了它，
   一旦存在，Worker 只是把请求代理到 `paseo-relay-next.fly.dev`（`cloudflare-adapter.ts:577`），
   根本不会走本地 Durable Object。
2. **daemon**：沿用 V-1 的私有 node + 私有 `PASEO_HOME`，配置改为
   `daemon.relay = {enabled:true, endpoint:"127.0.0.1:8799", useTls:false}`，
   并用 `PASEO_PASSWORD` 开了口令。
3. **客户端**：`createPaseoClient({ url, e2ee:{enabled:true, daemonPublicKeyB64}, password })`，
   URL 形如
   `ws://127.0.0.1:8799/ws?serverId=<srv_...>&role=client&connectionId=<uuid>&v=2`。

| 观测点 | 结果 |
|---|---|
| daemon 出站连 relay | `relay_control_connected`；relay 侧 `v2:server(control) connected to session srv_QI6W_CnLT6Pn` |

### 12.3 顺带确认的部署事实（V-10b 的前置调研）

上游 `getpaseo/paseo-relay`（GitHub 可达，Elixir，最近更新 2026-08-22）：

- **不绑定任何部署平台**，`scripts/ci.sh` 会构建**全部 Docker 交付物**并
  跑通 `/health`、`/ready` 冒烟；
- 全部用环境变量配置：`PASEO_RELAY_HOST`（默认 `127.0.0.1`）、
  `PASEO_RELAY_PORT`（默认 **4000**）、`PASEO_RELAY_DRAIN`、集群相关的
  `PASEO_RELAY_CLUSTER_QUERY` / `PASEO_RELAY_MIN_CLUSTER_SIZE` 等；
- 单节点部署把 `PASEO_RELAY_MIN_CLUSTER_SIZE` 保持 `1` 即可，不需要组 BEAM 集群。

**所以"同机部署"预期是跑一个容器，不需要在服务器上装 Elixir 工具链。**
V-10b 剩下要验的是：容器与 sub2api 同机共存、TLS 终结在谁那里、
以及 `daemon.relay.endpoint` / `publicUseTls` 的取值组合。

### 12.4 这次测试暴露的两件事

1. **本仓库那份 Cloudflare relay 是"壳"**：生产配置下它只代理到 fly.dev 上的 Elixir 实现。
   它可以用来**本地验证协议**（我们就是这么做的），但**不能当作自建方案**。
2. **relay 的准入模型和直连不是一回事**（§8.2）。这条不是性能或兼容问题，是安全模型问题，
   必须在服务端适配层与绑定表的设计里当作前提，而不是当作待办。
