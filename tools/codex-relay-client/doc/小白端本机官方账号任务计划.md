# 小白端「本机官方账号」—— 任务计划

> 状态：方案待确认（2026-09-28）。尚未动代码。
> 背景：现有「本地代理」页（见 `小白端本地代理任务计划.md`）只能用用户**贡献到中转站的账号**：客户端向中转站要短期
> access token，再从本机直连官方。用户要的是另一种来源——**这台电脑上 Codex / Claude Code 已经登录的官方账号**，
> 账号不上传中转站。本计划在同一个「本地代理」页里加上这第二种来源，直发、压缩、用量统计沿用现有实现。

## 1. 需求

- 「本地代理」页每个工具（Codex、Claude Code）在三者中选一个：**经中转站**（现状默认）/ **本机官方账号** /
  **中转站上的某个账号**（现有功能）。两个工具各选各的，互不影响。
- 本机官方账号 = 这台电脑上已有的官方登录：
  - Codex：`codex login` 登录的 ChatGPT 账号（`~/.codex/auth.json` 里的 `tokens`）；
  - Claude Code：`claude` 登录的 Claude 订阅账号（Windows / Linux 为 `~/.claude/.credentials.json` 的 `claudeAiOauth`，
    macOS 为钥匙串 `Claude Code-credentials`）。
- **凭据不出本机**：不上传共飞服务器、不写日志、只在内存里用；刷新后只写回它原来所在的位置。
- 开启后请求不经过中转站、不扣余额；Codex 仍做上下文压缩；本地用量照现有 L4 单独记录。
- 出错只提醒、不回退中转站（与现有本地代理一致）。
- 不需要服务端「我的账号」功能开通；仍需登录共飞客户端（本机 relay 只在登录后运行）。

## 3. 设计

### 3.1 凭据来源

- `LocalProxyTarget` 增加来源字段 `Source`（`Relay` / `LocalMachine`）；本机账号不占中转站账号 id。
  偏好存储（`LocalProxyPreferenceStore`）、加密推理拒收记录（`EncryptedContentRecovery`）、本地用量都改按「来源 + id」区分，
  避免本机账号和中转站账号串记录。
- 新增 `LocalMachineCredentialSource : ILocalProxyCredentialSource`；再加一个按 `Source` 分派的组合来源，
  `LocalPawRelay` 其余代码不动（它只认 `ILocalProxyCredentialSource`）。

### 3.2 Codex：谁持有、谁刷新

- 接入中转站时，客户端已经把用户的 `auth.json`（含 ChatGPT `tokens`）**移进加密快照**，`auth.json` 里只剩中转站 key
  （`CodexConfigWriter.WriteAuth`，原因见该方法注释）。所以接入期间**客户端是这份登录唯一的持有者**，Codex 自己看不到它、
  也不会去刷新——由客户端刷新不会和 Codex 打架。
- 读取：`tokens.access_token` / `refresh_token` / `id_token` / `account_id`。`chatgpt-account-id` 取 `account_id`，缺省时取
  `id_token` 里 `https://api.openai.com/auth.chatgpt_account_id`；FedRAMP 取同一处的 `chatgpt_account_is_fedramp`（与服务端
  `IsChatGPTAccountFedRAMP` 同口径）。页面显示名取 `id_token` 的 email 和套餐。
- 刷新：access token（JWT）到期前 5 分钟，或官方返回 401 时；`POST https://auth.openai.com/oauth/token`，
  `client_id=app_EMoamEEZ73f0CkXaXp7hrann`、`grant_type=refresh_token`、`scope=openid profile email`（与 Codex CLI、服务端
  `internal/pkg/openai/oauth.go` 一致）。单飞锁，同一时间只刷一次。
- **先写回、再使用**：新 token 连同 `last_refresh` 先原子写回两份快照（`CodexFileSnapshot` 的 `auth.bin` 与旧版
  `CodexAuthSnapshot`），写成功才用。OpenAI 的 refresh token 用一次就作废，写回失败或进程崩溃而新 token 没落盘，用户的
  Codex 登录就永久失效；退出时 `RestoreOriginalFiles` 还回去的必须是最新的那份。
- 刷新失败（`invalid_grant`、`refresh_token_reused`、过期）：提示「本机 ChatGPT 登录已失效，请在 Codex 里重新登录」，不回退。

### 3.3 Claude Code：谁持有、谁刷新

- 接入时客户端只改 `settings.json` 的 `env`（`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`），**不动 Claude 的登录凭据**。
  这期间 Claude Code 走 `ANTHROPIC_AUTH_TOKEN`，预期不会使用或刷新订阅凭据（M0 验证）。
- 读取：每次取凭据都重新读文件 / 钥匙串（按修改时间缓存）。如果 Claude Code 在别处刷新过，直接用它的新 token，不再自己刷。
- 刷新：`expiresAt`（毫秒）到期前 5 分钟，或官方 401；刷新前**再读一次**，refresh token 已被别人换掉就用别人的；
  否则 `POST https://platform.claude.com/v1/oauth/token`，`client_id=9d1c250a-e61b-44d9-88ed-5944d1962f5e`
  （与服务端 `internal/pkg/oauth/oauth.go` 一致）。
- 写回：只替换 `claudeAiOauth` 的 `accessToken` / `refreshToken` / `expiresAt`（返回了 `scopes` 才替换），文件里其他键
  （如 MCP 的 OAuth）原样保留；Windows / Linux 原子写文件，macOS 用 `security add-generic-password -U` 更新钥匙串项。
- 请求构造沿用现有 §3b 的实现（`oauth-2025-04-20` beta、请求头白名单等），不另写。

### 3.4 顺带修复：客户端运行期间重新登录 ChatGPT 会被丢弃（现有问题）

- 现状：客户端运行时用户执行 `codex login`，`CodexRouteGuardHost` 发现路由被改写后调用 `Apply` 重写回去；
  `CaptureOnce` 见到已有快照就不覆盖，**新登录被直接丢掉**，退出时还原的是旧登录。
- 改为：`auth.json` 里出现与快照不同的账号材料时，用新的替换快照里的认证部分（用户最新的登录为准），`config.toml`
  的快照不变。本机账号模式依赖这一点：用户换号或补登录后，下一轮对话就用新账号。

### 3.5 不做

- 客户端内置官方登录（Q2 备选）。
- Codex 使用系统钥匙串存登录（`cli_auth_credentials_store = "keyring"`）的情况：检测到就显示「暂不支持」，M0 先确认现有接入
  在这种模式下是否本来就有问题。
- 本机账号与中转站账号自动互为后备。

## 4. 任务

```
M0（真机验证）─┐
M1（Codex 快照读写 + §3.4 修复）─► M2（Codex 本机凭据来源）─┐
M3（Claude 本机凭据来源）──────────────────────────────────┼─► M4（目标与偏好扩展）─► M5（界面与文案）─► M6（出货）
```

每个任务单独提交，提交前 `dotnet test LanAi.RelayClient.sln -c Release` 全绿。

- **M0 真机验证**：与现有计划的 L0 合并做。① `auth.json` 实际结构、`id_token` 里的字段；② 刷新接口的真实返回与错误形态；
  ③ Claude Code 在 `ANTHROPIC_AUTH_TOKEN` 模式下会不会读写 `.credentials.json`；④ macOS `security` 读写是否弹框；
  ⑤ 用本机账号直发两边各跑一轮普通对话、工具调用、（Codex）远程压缩。
- **M1**：快照增加「读取 / 替换认证部分」的接口（两份快照一起改、原子写）；§3.4 修复；测试覆盖崩溃中途、两份快照不一致、
  旧版明文快照迁移。
- **M2**：解析、到期判断、单飞刷新、先写回再用、错误分类；用本机假令牌接口做测试（含 401 后重刷一次、`refresh_token_reused`）。
- **M3**：Windows / Linux 文件与 macOS 钥匙串两个存储；刷新前重读、只改三个字段、保留其他键；同样的测试。
- **M4**：`LocalProxyTarget.Source`、组合凭据来源、偏好存储与用量按来源区分（兼容旧偏好文件）。
- **M5**：页面分「本机官方账号」「中转站上的账号」两块，本机账号显示检测结果（已登录 / 未登录 / 已失效 / 暂不支持）和显示名；
  仪表盘、托盘、Codex / Claude 页的「正在使用本地代理：…」写明是本机账号；页首文案按 Q4 改。
- **M6**：裁剪发布 win-x64 / osx-arm64 无新增警告，UTF-16LE 搜到新文字，逐页截图核对，真机按 M0 ⑤ 再走一遍。

## 5. 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| 刷新后新 token 没写回 | 用户本机官方登录永久失效，要重新登录 | 先写回、再使用；单飞锁；写回失败就不用新 token 并报错 |
| Claude Code 与客户端同时刷新同一个 refresh token | 其中一方拿到 `refresh_token_reused`，登录失效 | 刷新前重读、优先采用别人刷新的结果；M0 ③ 确认 AUTH_TOKEN 模式下 Claude Code 不刷新 |
| 订阅账号被官方判为第三方客户端 | 请求被拒，极端情况账号受限 | 与现有本地代理同一风险，同一套 L0 验证；页面提示风险由用户自担 |
| Codex 用钥匙串存登录 | 读不到本机账号 | 显示「暂不支持」 |
| 用户以为本机账号出错会回到中转站 | 以为在用却没在用 | 与现有本地代理相同：通知写明「未切回中转站」 |
