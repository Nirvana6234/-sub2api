## 背景

现在「本地代理」页每个工具（Codex、Claude Code）有三种来源：

1. **经中转站**（默认）：请求走中转站、扣余额。
2. **本机官方账号**：借用这台电脑上 Codex / Claude Code 自己的登录——Codex 的 ChatGPT 登录在客户端接管 Codex 时已移进客户端的
   加密快照（`auth.json` 里只剩中转站 key），Claude Code 的在 `~/.claude/.credentials.json`；客户端刷新并写回原位置，启用时不需要授权。
3. **中转站上的账号**：用户贡献到中转站的账号，客户端每次向 `POST /api/v1/account-contributions/:id/local-proxy-token`
   取短期 access token，refresh token 只在服务端、刷新只由中转站做。

用户要去掉第 3 种，改成**在客户端里直接登录官方账号**：把中转站「贡献账号」的授权流程（生成授权链接 → 用户在浏览器登录 →
拿授权码换 token）搬到客户端，token 加密存在本机、由客户端自己刷新，**不上传中转站**。

一次新的授权得到的是一套独立的 token，与中转站手里的那份、与本机 Codex / Claude Code 自己的登录互不相干，
所以由客户端持有 refresh token 不会和别人抢着刷新——当初「refresh token 永不离开服务器」防的正是两边刷同一个 token。

## 1. 需求

- 「本地代理」页每个工具在三者中选一个：**经中转站** / **本机已登录的账号** / **在共飞里登录的某个账号**（新）。
  「中转站上的账号」去掉。两个工具各选各的。
- **本机账号优先（D9）**：目的是无缝衔接——用户在这台电脑上已经登录过 Codex / Claude Code 的，点「启用」直接能用，不再拉起任何授权。
  - 本机已登录的账号自动识别，排在账号列表最上面；第一次打开本地代理页、检测到本机账号时，默认推荐它。
  - **只有本机没有可用账号时**（没登录过、Codex 用 API Key 登录或把登录存进了系统 keyring、macOS 上用户拒绝了钥匙串授权），
    才出现「在共飞里登录」，走 §3.3 / §3.4 的浏览器授权；它取代现在「请到终端执行 `codex login` / 运行 `claude`」的提示。
  - 本机账号与在共飞里登录的账号可以随时互相切换，下一轮对话即生效，不重启工具。
- 「在共飞里登录的账号」：
  - Codex：ChatGPT 账号（OpenAI OAuth，Codex CLI 的 client）；
  - Claude Code：Claude 订阅账号（Anthropic OAuth，Claude Code 的 client）。
  - 可以登录**多个**，每个工具选用其中一个；同一个官方账号再登录一次就更新原记录，不新增。
- 页面上「添加账号」→ 打开浏览器登录 → 回到客户端即完成；已添加的账号可「重新登录」「删除」，并显示邮箱、套餐、状态
  （可用 / 已失效 / 刷新失败）。
- **凭据不出本机**：token 只存在本机的加密文件里，不上传共飞服务器，不写日志；刷新后只写回这个文件。
- 开启后与现有本地代理一致：请求不经过中转站、不扣余额；Codex 仍做上下文压缩；本地用量照记；出错只提醒、不回退中转站。
- 仍需登录共飞客户端（本机 relay 只在登录后运行；账号库按共飞用户分开，见 D5）。

## 3. 设计

### 3.0 本机账号：在原处借用，不复制

- 两家的 refresh token 都是**用一次就作废**：谁先拿它换了新 token，别人手里那份就失效。把本机登录的 token 复制一份存进账号库，
  客户端一刷新，本机的 Codex / Claude Code 就被踢下线（反之亦然）。所以本机账号只能与原主**共用同一份**、刷新后写回原位置——
  这正是现有 `LocalCodexAccount` / `LocalClaudeAccount` 的做法，本计划不改它们的凭据逻辑。
  - Codex：接管期间登录在客户端快照里，Codex 看不到也不会刷新，客户端是唯一刷新者；退出时把最新的那份还回 `auth.json`。
  - Claude Code：登录留在原文件；每次请求重新读，Claude Code 自己刷新过就直接用它的；刷新前再读一次，别人已换过就用别人的。
- 在共飞里登录的账号则是一次**新的授权**，得到独立的一套 token，与本机登录互不相干，所以可以放进自己的账号库、由客户端独占刷新。

### 3.1 账号标识

- 沿用「本机官方账号」的做法：本地代理的账号一律用 `long` id 区分，**不加来源字段**。
  - 中转站账号：正数（本计划后不再出现）；
  - 本机账号：保留的 −1（Codex）、−2（Claude）；
  - 在共飞里登录的账号：**−1000 及以下**，本机按序分配（−1000、−1001…），删除后不复用。
- 好处：`LocalProxyChoice`、本地用量、`EncryptedContentRecovery` 的拒收记录都按 id 区分，无需改结构，也天然不会串到别的账号上。

### 3.2 本地账号库 `OfficialAccountStore`

- 位置：`AppPaths.InData("official-accounts", <scope>, "accounts.bin")`，`<scope>` 即 D5 的 `ScopeFor`。一个文件存该共飞用户的全部账号，
  整体用 `CreateSnapshotProtector` 加密，**原子写**（临时文件 + 替换），写失败不破坏旧文件。
- 每个账号记：id、平台、显示名（邮箱）、套餐、订阅到期时间、状态与原因、添加时间、最近刷新时间；
  凭据：access token、refresh token、到期时间；OpenAI 另记 id_token、`chatgpt_account_id`、`fedramp`；Claude 另记 `account_uuid`、`org_uuid`、scope。
- 去重：OpenAI 按 `chatgpt_account_id`（缺省用邮箱）、Claude 按 `account_uuid`；再次登录同一账号就更新原记录、沿用原 id，
  这样工具的选择和本地用量都接得上。
- 下一个可用 id 也存在这个文件里。

### 3.3 OpenAI 授权

参数与中转站一致（`backend/internal/pkg/openai/oauth.go`、`repository/openai_oauth_service.go`）：

- PKCE：`code_verifier` 为 64 个随机字节的十六进制，`code_challenge = base64url(SHA256(verifier))`，`S256`；`state` 随机。
- 授权链接：`https://auth.openai.com/oauth/authorize?response_type=code&client_id=app_EMoamEEZ73f0CkXaXp7hrann`
  `&redirect_uri=http://localhost:1455/auth/callback&scope=openid profile email offline_access&state&code_challenge`
  `&code_challenge_method=S256&id_token_add_organizations=true&codex_cli_simplified_flow=true`。
- 接回调（D2）：点「添加账号」时在 `localhost:1455` 起一个一次性监听，只认 `/auth/callback` 且 `state` 相符的那一次请求，
  回给浏览器一页「授权完成，可以回到共飞助手了」，随即关闭监听。10 分钟无回调自动放弃，可手动取消。
  1455 被占用（例如 Codex 正在登录）就直接进入粘贴模式；粘贴框接受完整网址或 `code=…&state=…` 片段（解析规则照前端
  `OAuthAuthorizationFlow.vue` 的提取逻辑），同样校验 `state`。
- 换 token：`POST https://auth.openai.com/oauth/token`，表单 `grant_type=authorization_code`、`client_id`、`code`、`redirect_uri`、
  `code_verifier`；请求头 `originator: codex_cli_rs` 与 UA 与现有 `OfficialTokenRefresher` 一致。
- 解析 id_token：邮箱、`chatgpt_account_id`、套餐、`fedramp`（与「本机官方账号」同口径，复用 `JwtPayload`）。
- D6：用 access token 只读查询套餐与到期时间（中转站 `enrichTokenInfo` 的只读部分：`accounts/check`，必要时个人订阅端点），失败不影响添加；
  **不调**关闭训练数据的接口。

### 3.4 Claude 授权

参数与中转站一致（`backend/internal/pkg/oauth/oauth.go`、`repository/claude_oauth_service.go`）：

- PKCE 同上；授权链接：`https://claude.com/cai/oauth/authorize?code=true&client_id=9d1c250a-e61b-44d9-88ed-5944d1962f5e`
  `&response_type=code&redirect_uri=https://platform.claude.com/oauth/code/callback`
  `&scope=org:create_api_key user:profile user:inference user:sessions:claude_code user:mcp_servers user:file_upload`
  `&code_challenge&code_challenge_method=S256&state`。
- 用户登录后官方回调页显示授权码（形如 `授权码#state`），复制回客户端粘贴；按 `#` 拆开，校验 `state`。
- 换 token：`POST https://platform.claude.com/v1/oauth/token`，JSON `{code, grant_type: authorization_code, client_id, redirect_uri,
  code_verifier, state}`。返回里取 access/refresh token、`expires_in`、scope、`account.uuid`、`account.email_address`、`organization.uuid`。
- 自动回调（D2）：A0 验证这个 client_id 是否接受 `http://localhost:<端口>/callback` 这类回调地址（Claude Code 自己用的方式）；
  接受就与 OpenAI 一样起一次性监听、以粘贴为后备，不接受就只做粘贴。
- 套餐：A0 查清有没有可用的只读接口能拿到订阅类型；没有就只显示邮箱。

### 3.5 刷新与使用

- 新增 `OfficialAccountSource : ILocalProxyCredentialSource`，由 `LocalProxyCredentialRouter` 按 id 分派（−1000 及以下归它）。
- 刷新复用 `OfficialTokenRefresher`（两家的刷新接口与 client_id 已实现）：到期前 5 分钟或官方 401 时刷新，**同一账号同一时间只刷一次**。
- **先写回、再使用**：新 token 先原子写回 `accounts.bin` 再用；写回失败时与「本机官方账号」一致——保留新凭据继续用、之后每次请求重试写回
  （旧 refresh token 此时已作废）。
- 刷新失败（`invalid_grant`、`refresh_token_reused`、过期）：该账号标为「已失效」，通知「<邮箱> 的登录已失效，请在本地代理页重新登录」，
  不回退中转站；「重新登录」成功后沿用原 id，恢复可用。
- Codex 请求照旧补 `chatgpt-account-id` 与 FedRAMP 头；Claude 照旧补 oauth beta（现有 §3 / §3b 实现不动）。

### 3.6 网络

- 授权页由系统浏览器打开，走浏览器自己的网络。
- 换 token、刷新、查套餐都经客户端直连官方的 `HttpClient`，沿用本地代理「按当前代理设置建连接」的实现；
  连不上官方时提示「连不上 auth.openai.com / platform.claude.com，请检查代理或 VPN」，与开启本地代理前的网络提醒同一套措辞。

### 3.7 日志与隐私

- 日志只记：平台、账号 id、授权开始 / 成功 / 失败及错误码、回调方式（自动 / 粘贴）、刷新结果。
- **不记**：token、授权码、code_verifier、state、id_token、邮箱原文（界面上显示，日志里不写）。
- 本地回调监听只绑本机回环地址，只接受一次、`state` 不符一律拒绝。

### 3.8 链路与压缩（不因账号来源而变）

- Codex：Codex → 上下文压缩器（`context-filter.exe`）→ 本机 relay → 按账号取 token → 官方。Codex 的 `base_url` 指向压缩器
  （`CodexStartup`，包里带压缩器时），本地代理的分流在 relay 里、压缩之后（`LocalPawRelay` 按 `_codexLocalProxy` 转 `HandleLocalProxyAsync`），
  取 token 是最后一步（`LocalProxyCredentialRouter` 按 id 分派）。所以本机账号、在共飞里登录的账号都**照样经过压缩**；
  「启用」只改 relay 里的上游状态，不改 `config.toml`、不还原 `auth.json`、不切 Codex 的登录模式。
- Claude Code：按原设计不经压缩，直发官方。
- 压缩不生效的情况：包里没带 `context-filter.exe`；页面关了「启用上下文压缩」（压缩器仍在链路上但原样转发）；macOS（压缩器只有 Windows 版）。
- 核对方法：`client.log` 每轮一行「本轮转发（本地代理「<账号>」）：本轮上下文压缩生效：…」；出现「本轮未经过上下文压缩」即链路里没有压缩器。

### 3.9 macOS：Claude Code 存在钥匙串里的登录（D10）

Claude Code 在 macOS 上把登录存在登录钥匙串的通用密码项里（服务名 `Claude Code-credentials`，账户为当前用户名，内容与
Windows 上 `.credentials.json` 同结构的 JSON——服务名、账户名与内容格式在 A0 ⑧ 核实）。读取别的程序建的项会触发系统授权框。

- **何时弹**：只在用户点「启用」本机 Claude 账号时第一次读取；弹框前页面先说明「接下来 macOS 会询问是否允许读取 Claude Code 的登录，
  请点『始终允许』」。**打开本地代理页、检测本机账号时不读密码**：只查这一项是否存在（只读属性、不取密码数据，不触发弹框），
  存在就显示「已登录（启用时需要授权读取）」。
- **读**：用 `/usr/bin/security find-generic-password -s "Claude Code-credentials" -a <用户名> -w`，密码从子进程的标准输出读回，
  不经命令行参数。选它而不是本进程直接调 Security.framework，是因为此时向钥匙串要数据的是 Apple 签名的 `security`：
  用户点「始终允许」后记住的是它，**客户端每次升级（ad-hoc 签名会变）都不必重新授权**；若 Claude Code 本身就是经 `security`
  写的这一项，可能根本不弹（A0 ⑧ 确认）。
- **写回**（刷新后，§3.5「先写回再使用」）：**不用** `security add-generic-password -w <值>`——值会进命令行参数，本机其他进程
  用 `ps` 就能看到，这正是 `KeychainMasterKeyStore` 拒绝它的原因。改为本进程经 Security.framework 查到这一项、
  用 `SecKeychainItemModifyAttributesAndData` 只改数据（与 `KeychainMasterKeyStore` 同一套 P/Invoke 写法），只替换 JSON 里
  `claudeAiOauth` 的 `accessToken` / `refreshToken` / `expiresAt`（返回了才换 `scopes`），其余键原样保留。
  写回可能对客户端本身再弹一次框；ad-hoc 签名下「始终允许」可能在客户端升级后失效，届时刷新时会再问一次（写不成就按现有做法
  保留新凭据、之后每次请求重试写回）。
- **不每请求都读密码**：读到的凭据留在内存；每次请求只查这一项的修改时间（属性，不弹框），变了（Claude Code 自己刷新过）才重读。
- **拒绝与超时**：用户点「拒绝」或 60 秒没回应——本机 Claude 账号标为「未授权读取」，给「重试」和「在共飞里登录」两个按钮；
  弹框期间不占用请求线程，已经启用的对话不受影响。
- Windows / Linux 不变，仍是 `.credentials.json`。

  ② Claude 粘贴授权码走通一次；试 `http://localhost:<端口>/callback` 是否被接受（决定 §3.4 的自动回调）；
  ③ 两家刷新接口对客户端自己换来的 token 可用；
  ④ **新登录是否会让同一账号已有的会话失效**（本机 Codex / Claude Code 自己的登录、中转站里同一账号）——预期互不影响，必须确认；
  ⑤ Claude 有没有只读接口能拿到订阅类型；
  ⑥ 用这样登录的账号经本地代理各跑一轮普通对话与工具调用（Codex 另跑一次远程压缩）；
  ⑦ **本机账号**（合并「本机官方账号」计划尚未做的 M0）：本机 Codex 的 ChatGPT 登录与 Claude Code 的订阅登录各启用一次，
  确认启用时不弹授权、`client.log` 有带「本地代理」的「上下文压缩生效」行（Codex）；Claude Code 在 `ANTHROPIC_AUTH_TOKEN`
  模式下不会自己读写 `.credentials.json`；客户端退出后本机 Codex 仍能正常登录使用；
  ⑧ **macOS 钥匙串**（需要一台登录了 Claude 订阅的 Mac）：核实服务名、账户名与内容格式；经 `security` 读取是否弹框、
  「始终允许」后是否不再弹、客户端升级后是否仍不弹；客户端写回数据是否弹框；Claude Code 自己刷新时是删了重建还是原地改
  （重建会让「始终允许」失效）。
- **A1 本地账号库**：`OfficialAccountStore`（按 scope 分文件、加密、原子写、去重、id 分配、下一个 id 持久化）；
  `LocalProxyCredentialRouter` 增加 −1000 及以下的分派。测试：加密往返、写一半崩溃不坏旧文件、同账号再登录沿用 id、
  删除后 id 不复用、两个共飞用户互相看不到、日志里没有 token。
- **A2 OpenAI 授权**：PKCE 与链接、一次性回调监听（端口占用 → 粘贴）、粘贴解析、state 校验、换 token、解析 id_token、只读查套餐。
  测试用本机假授权服务：自动回调、端口被占改粘贴、state 不符拒绝、超时、换 token 失败的各种返回、网址与片段两种粘贴格式。
- **A3 Claude 授权**：链接、粘贴解析（`码#state`）、换 token、取账号信息；若 A0 ② 允许，加自动回调。测试同 A2。
- **A4 刷新接入**：`OfficialAccountSource`（到期前 / 401 刷新、单飞、先写回再用、失败标「已失效」并上报）。
  测试：401 后重刷一次、`refresh_token_reused`、写回失败继续用并重试、两个工具同时用同一账号只刷一次。
- **A8 macOS 钥匙串**（§3.9，与 A1–A4 并行；按约定只写代码、不交叉编译验证，真机结论以 A0 ⑧ 为准）：
  `ClaudeKeychainStore : IClaudeCredentialStore`——存在性检查只读属性；读取经 `security … -w`；写回经 Security.framework 只改数据；
  按修改时间决定是否重读；拒绝 / 超时的状态与重试。`App.axaml.cs` 在 macOS 上用它代替 `ClaudeCredentialFile`（文件存在时仍优先用文件，
  与 Claude Code 退回文件存储的情况一致）。测试（Windows 上跑）：把 `security` 子进程与 Security.framework 调用都抽成接口、用假实现，
  覆盖只改三个字段且保留其余键、修改时间不变不重读、拒绝与超时、写回失败保留新凭据并重试、检测阶段绝不读密码。
- **A5 界面**（按 D9）：本地代理页每个工具一组，从上到下：「经中转站」；**本机已登录的账号**（自动识别，显示邮箱与状态，
  一键「启用」、不授权）；在共飞里登录的账号列表。本机有可用账号时，首次进入默认推荐它；「在共飞里登录」按钮只在本机没有可用账号时
  突出显示（其余时候收在列表下方的次要入口），本机账号的「未登录 / 暂不支持」说明里直接给出这个按钮，取代「去终端 `codex login`」。
  添加流程：打开浏览器 → 等待中（可取消）→ 自动完成或显示粘贴框；账号行显示邮箱、套餐、到期、状态，可「使用」「重新登录」「删除」；
  删除正在使用的账号时先确认，并把该工具切回经中转站。仪表盘、托盘、Codex / Claude 页的「正在使用本地代理：…」写出是哪个账号。
- **A6 移除「中转站上的账号」**：删掉 `LocalProxyCredentialCache` 及其在 `IRelayServerClient` 里的贡献账号列表 / 取 token 调用、

## 5. 不做

- D3 列出的其他授权方式（refresh token / PAT / setup-token 导入）。
- 替用户关闭「用对话训练模型」（D6）。
- 把在共飞里登录的账号贡献到中转站，或反过来从中转站导入。
- 删除账号时向官方吊销 token（Codex CLI 的公共 client 没有可用的吊销接口；只删本地）。
- 把本机账号的 token 复制进账号库（§3.0：会与本机 Codex / Claude Code 互相把对方刷掉）。
- 删除服务端 `local-proxy-token` 接口（D7，等旧客户端淘汰后另议）。

## 6. 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| macOS 钥匙串授权被拒或反复弹框 | 本机 Claude 账号用不了，或刷新时又问一次 | 只在「启用」时读、先说明；读取经 Apple 签名的 `security`，「始终允许」不随客户端升级失效；被拒就引导「在共飞里登录」；A0 ⑧ 摸清 Claude Code 重建钥匙串项的情况 |
| 本机账号与 Claude Code 同时刷新同一个 refresh token | 一方拿到 `refresh_token_reused`，本机 Claude 登录失效 | 沿用现有做法：刷新前重读、优先用别人刷新的结果；A0 ⑦ 确认 AUTH_TOKEN 模式下 Claude Code 不刷新 |
| 新登录让同一账号的其他会话失效 | 用户本机 Codex / Claude Code 被登出，或中转站里同一账号失效 | A0 ④ 必须确认；若确有影响，页面在添加前明确提示 |
| 刷新后新 token 没写回 | 这个账号的登录永久失效，要重新登录 | 先写回再用；单飞；写回失败保留新凭据并持续重试 |
| 1455 端口被占用 | 自动回调接不到 | 直接转粘贴模式，文案告诉用户复制地址栏 |
| Claude 不接受本机回调地址 | 只能粘贴授权码 | A0 ② 确认；粘贴流程本来就要做 |
| 本机其他程序读 `accounts.bin` | 账号被盗用 | 按当前用户加密（DPAPI / 钥匙串主密钥）；日志不落 token |
| 冒用官方客户端的 client_id | 官方判为第三方客户端，请求被拒，极端情况账号受限 | 与中转站、现有本地代理同一风险，页面提示风险由用户自担 |
| 国内直连官方被墙 | 授权后换 token 或刷新失败 | 复用本地代理的网络检测与提醒 |
| 旧版选了中转站账号的用户升级 | 以为还在用本地代理 | A6 清掉选择、切回中转站并提示一次 |
